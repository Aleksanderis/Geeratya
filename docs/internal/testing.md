# Testing

*Internal design note for maintainers and agents. Not needed to use or contribute to Geeratya.*

Strategy and layers. The procedure for writing, recording and running tests is the `testing` skill; budgets and measured numbers are in `docs/internal/performance.md`.

## Layers

| Layer | What it covers | Where |
|---|---|---|
| Pure tests | State, commands, keymap, JQL building, mappers over recorded JSON, layout | `tests/Geeratya.<Project>.Tests`, no terminal, no socket |
| Transport and store tests | Jira calls, paging, refresh, caches against the in-process fake | `FakeJiraHandler` in `tests/Geeratya.Jira.Tests/Fakes` |
| Frame snapshots | Rendering as text at several sizes (help pages and scrolled, `--help-page`, `--help-scroll`) | Tui tests |
| Fake Jira server | The real binary against recorded data (tmux, screenshots, measurements) | `tools/FakeJira` |
| Live tests | Behaviour the fake might get wrong, on the dev site only | Opt-in, `Live=true` |

xUnit throughout, one test project per source project, same folder layout as the code. `[Trait("Os", "Independent")]` marks pure classes the Windows leg runs (`testing` skill). `tools/FakeJira` has its own test project, `tests/Geeratya.FakeJira.Tests`, which starts the server on a free loopback port and talks to it with a real `HttpClient`, so those tests are not marked OS independent.

To regenerate snapshots after adding key rows or palette commands, run `GEERATYA_UPDATE_SNAPSHOTS=1 dotnet test tests/Geeratya.Tui.Tests`. The switch is project-wide for the families that honour it: `help-*`, `popup-*`, `network-*` and the issue detail snapshots. Those tests then write the current output into `tests/Geeratya.Tui.Tests/Snapshots/` instead of asserting; review the diff and commit it. Unset, they assert as usual.

## Fixtures

Real responses recorded from the dev site, scrubbed and stored under `tests/Geeratya.Jira.Tests/Fixtures/<area>/<name>.json`. What each one shows, and how Jira behaves, is the survey in `docs/internal/jira-layer.md`. Recording (`scripts/record-fixture.sh`) refuses hosts outside `GEERATYA_LIVE_HOSTS`; scrubbing (`scripts/scrub-fixture.py`) rewrites host, account ids, emails and display names. Never hand-write a response shape you have not recorded. Generated datasets (below) are the one exception, and only for size: their shape is the recorded search shape reduced to the fields the app asks for.

## Fake Jira

Two fakes share the fixture folder, for different consumers:

- `FakeJiraHandler`: an `HttpMessageHandler` for unit and store tests. No socket. Scripted statuses, `Retry-After`, latency and hangs; records every request.
- `ScriptedJiraHandler` (`tests/Geeratya.App.Tests/Fakes`): the same idea for the App tests (handlers, runner, connections), which do not reference the Jira test project; `Geeratya.Tui.Tests` links every file of that `Fakes` folder (so a fake added there is compiled into both test assemblies) to build board states through the real loading path: a queue of scripted replies (status, body, optional gate, `Retry-After`) and the recorded request URIs. Bodies are small inline JSON; recorded responses belong to the Jira layer's tests.
- Gateway fixtures (#681): `Fixtures/gateway/` holds the tenant lookup and the GraphQL replies that give a Kanban board's done cutoff (`tenant-info`, `navigation-*`, `cutoff-*`, recorded from boards 4, 3 and 6 of the dev site; scrubbed: cloud and activation ids become stable fakes). `scripts/record-fixture.sh` allows `POST /gateway/api/graphql` only for a read-only `query` document and refuses a `mutation` or `subscription`. `ScriptedJiraHandler` answers the gateway from its own queue (`Gateway(...)`, 404 when nothing is scripted, not counted in `Requests`) so the agile reply scripts keep their order; `tools/FakeJira` serves the same chain (`FakeGateway`).
- `tools/FakeJira` (`fakejira`): a local HTTP server on `127.0.0.1` for running the real binary. Prints its base URL as the first line on standard output and runs until interrupted. It serves `GET issue/{key}/editmeta` from the recorded edit metadata of the key's project kind (GTM team-managed, otherwise GCM) for any key, and edits only the recorded issues (a generated `GEN-n` answers 404 on a write).

```sh
dotnet run --project tools/FakeJira -- --issues 10000 --latency-ms 50 --rate-limit-every 20
# or the AOT build: dotnet publish tools/FakeJira -c Release -o <dir>; <dir>/fakejira
```

| Option | Meaning |
|---|---|
| `--fixtures <dir>` | Fixture folder; default found by walking up from the binary or the current directory to `tests/Geeratya.Jira.Tests/Fixtures` |
| `--port <n>` | Listen port; default 0 picks a free one (probe-then-bind, retried on a race) |
| `--issues <n>` | Search serves `GEN-1..GEN-n` generated issues, paged with `maxResults` (default 50, cap 5000) and `nextPageToken`; `approximate-count` answers `n`; the generated issues carry a story point estimate (`customfield_10047`) |
| `--latency-ms <n>` | Delay added to every reply |
| `--rate-limit-every <n>` | Every nth request is answered `429` with `Retry-After: 1` |
| `--drop-write-every <n>` | Every nth write (POST, PUT, DELETE) is applied, then the connection is cut after the headers, so the client fails reading the reply and cannot tell whether the write happened (the "unknown outcome" path) |
| `--no-active-sprint` | With `--issues`: the generated Scrum board has no active sprint (closed and one future only), for the "No open sprint on this board." state. The Sprint view's own "No active sprint on this board." state has no scenario: no key opens an `active` Sprint source (#496). Takes no value |

Without `--issues`, search serves the recorded three-page fixtures (`search-page1..3-last`). Routes are a fixed table in `FakeJiraRouter` over recorded fixtures: `myself`, `project/search`, `field`, `issuetype`, `filter/my`, `filter/search`, `filter/favourite`, `search/jql` (GET and POST), the agile board list, boards 3 (GTM) and 4 (GCM) with configuration and `epic`, board 3 and 4 `issue` and `backlog` (board 3 from the `hierarchy/` fixtures), `issue/GTM-9` and `issue/GCM-8` (epics) whose `parent = KEY` search answers the `hierarchy/search-epic-children-*` fixtures, a `key = KEY` (or `issuekey`) search of any routed issue, which answers one page holding that recorded issue (also with `--issues`; there `parent = KEY` of an epic likewise answers the recorded children), `issue/picker` (the recorded picker reply for any query, GCM keys), a `key in (A, B)` search (the suggestion client's issue type lookup: the listed keys found among the board pages, each with its `issuetype` only), and `filter/10001` (any other numeric filter id answers the recorded 404 "not available"). Anything else (including a POST to any path except `search/jql`, with `--issues` `search/approximate-count`, and the write routes below) is the recorded 404. It ignores credentials. Add a route when a feature needs one: map the path to a recorded fixture in `FakeJiraRouter`. Point the app at it with a profile whose site URL is the printed address and any token.

Write routes (`FakeJiraWriteStore`) keep their state in memory for the life of the process and never touch Jira: `POST /issue` (create in `GCM` or `GTM`; keys start at `-100`; no summary, an unknown project or no issue type answer the recorded 400s), `PUT /issue/{key}` (edit `summary`, `labels`, `description`, `duedate`; any other field is the recorded unknown-field 400), `DELETE /issue/{key}` (a created issue is removed, a recorded one answers the recorded 403, as `GCM` does), `GET` and `POST /issue/{key}/transitions` (the recorded project transition lists; a valid id changes the status the issue reads with, a bad id is the recorded 400), `POST`, `PUT` and `DELETE` on `/issue/{key}/comment[/{id}]` (the comments list follows), and `PUT /issue/{key}/assignee` (an account id assigns, the recorded account shows its display name, null or `-1` unassigns; #154), and `PUT /rest/agile/1.0/issue/rank` (204 when every named issue exists or is served by a board or backlog list, else the recorded 400; the moves are laid over the `issues` of the board and backlog replies, so a reload shows the new order, within a page for the paged GCM board; #169). Reads of an edited or created issue (`GET issue/{key}`, the `key = KEY` search, comments) show the changes; a restart forgets them. Only `fields` edits are modelled (an `update` body answers the unknown-field 400), and a recorded comment can be edited or deleted too (the change is a copy kept in memory; an unknown id answers 404). A created issue is readable by key but never appears in `search/jql` (apart from `key = KEY`), board, backlog or epic-children replies. Not modelled: the rank field, create/edit metadata changes, links, attachments and the assignable-user search (#213).

Scrum routes (`FakeScrumStore`, #173) serve the survey fixtures of #172 (`Fixtures/scrum/`) for board 5 (`GTS`, team-managed, says `simple`) and board 6 (`GCS`, company-managed, says `scrum`), with state in memory like the write routes. Reads: `GET board` (all four boards, `projectKeyOrId` and `type` narrow it), `board/{5,6}` with `configuration` and `epic`, `board/{5,6}/sprint` (closed, active, future order; `state` filter, an unknown value is the recorded 400; offset paging with `isLast`, cap 50), `board/{5,6}/issue` (every board issue; the JQL forms `sprint in openSprints()`, the Scrum backlog view's `... or sprint in futureSprints() or sprint is EMPTY` (open and future sprints plus issues in no sprint) and `sprint = N` narrow it, any other JQL is ignored), `board/{5,6}/backlog` (issues in no open sprint that are not done, which matches both recorded backlogs, so unfinished issues of a completed sprint come back to it), `sprint/{id}` and `sprint/{id}/issue` (offset paged, no `isLast`). Sprint membership is seeded from the `Sprint` field of the board issues, except an issue the recorded backlog lists (`GTS-35`), which stays in the backlog as on the real site; the `Sprint` field of every issue in a reply is rebuilt from the current membership (closed sprints first, `null` when none). `GET board/{3,4}/sprint` is the recorded 400 `The board does not support sprints`, an unknown board the recorded 404. Writes: `POST sprint` (create, state `future`, boards 5 and 6 only, ids from 1000), `PUT sprint/{id}` (replace: an omitted `goal` is dropped) and `POST sprint/{id}` (partial), with the recorded rules: start needs a start and an end date, future to closed and closed to active are 400, completing a closed sprint again is 200, and `moveIssuesTo` is 400 `Invalid request payload`, so completing leaves unfinished issues in the closed sprint (and in the backlog) and a client moves them with a second call; `DELETE sprint/{id}` (204, any state); `POST sprint/{id}/issue` (an issue in another open sprint moves, a closed target or an unknown key is 400 and nothing moves); `POST backlog/issue` (leaves every open sprint). Issue detail (`GET issue/GCS-n`, `GTS-n`) and the `key = KEY` search serve the recorded board issues with the `Sprint` field following the current memberships, plus empty comment and remote link lists (#323). With `--issues n` the fake also serves a generated, read-only Scrum board 7 (project `GEN`, listed by `GET board`; configuration from the recorded GCS one, no epics) over the `GEN-n` issues (#320): 3 to 30 sprints (n/100) with ids from 5001, the last future, the one before active, the rest closed, in consecutive blocks over the first four fifths of the issues; the last fifth is in no sprint. `board/7/sprint`, `sprint/{id}`, `sprint/{id}/issue`, `board/7/issue` (the `sprint = N` and `openSprints()` JQL forms) and `board/7/backlog` answer (every fourth issue is Done; unfinished issues of closed sprints are also in the backlog); sprint and backlog moves (`POST sprint/{id}/issue` into a generated open sprint, `POST backlog/issue`) are kept in memory as per-issue overrides, so later reads show them (a closed sprint or an unknown `GEN-n` is 400 and nothing moves; other sprint writes stay 404, #509); sprint dates are laid out in 14-day steps from 2026-01-05 whatever the state, `maxResults` of the issue lists is not capped, `openSprints()` means the active sprint only, and `GET issue/GEN-n` has no `Sprint` field. Quick filters (#192): `GET board/{3,4,5,6}/quickfilter` serve the recorded lists (`quickfilters-gcs.json` for the company-managed boards 4 and 6, the empty `quickfilters-gts.json` for 3 and 5) and the board issue routes of boards 4, 5 and 6 evaluate the two recorded clauses (`assignee = currentUser()`, `updatedDate >= -1d`, `FakeQuickFilters`) in `jql`; every recorded issue is unassigned and older than a day, so each clause narrows to an empty list. Not modelled: the `fields` parameter (replies carry the recorded fields), transitions, edits, comments and assignment of `GCS` and `GTS` issues (their write routes answer 404), sub-tasks following their parent into a sprint, other quick filter clauses. `PUT issue/rank` accepts every Scrum board issue (recorded and generated) and the sprint issue lists are reordered by the ranks like the board lists, within one page (#509). The app opens both boards with `:board GCS` and `:board GTS` (the Kanban layout; the Scrum layout is M5).

`fakejira` is Native AOT compatible (`PublishAot`, `HttpListener`, `Utf8JsonWriter`, no reflection) and follows the same style rules as `src/`.

## Live tests

Only on the owner's dev site, opt-in, never part of the review or CI gate; rules and environment in the `testing` skill. `LiveWriteRoundTripTests` creates a `GTM` task labelled `geeratya-test-<run id>`, edits it, adds, edits and deletes a comment, transitions it, reads the result back and deletes the issue in a `finally`; it skips without the environment.

## Seeded dev-site data

`scripts/seed-dev-site.sh` (details in the `testing` skill) fills the four sandbox projects; every issue carries `geeratya-seed` plus `geeratya-seed-<project>-<slug>`, and a second run adds nothing.

- `GCM`, `GTM` (Kanban): 16 issues each (epics, stories, tasks, bugs, sub-tasks and backlog items; `--dry-run` lists them), a rich comment, an attachment, links and a remote link.
- `GCS` (company-managed, board 6) and `GTS` (team-managed, board 5): 21 issues each. 2 epics, 7 stories, 6 tasks, 4 bugs and 2 sub-tasks, 4 of them left in the backlog, spread over three sprints found by name: `Seed Sprint 1` (closed, 7 issues: 5 done, `story-search` and `task-tests` not finished and carried over), `Seed Sprint 2` (active, 7 issues: the 2 carried over plus 5 more), `Seed Sprint 3` (future, 3 issues). The pre-existing `GCS Sprint 1`/`GTS Sprint 1` stay untouched. Statuses end as 7 Done, 4 In Progress, 10 To Do.
- Story points come from the board's estimation field (`customfield_10047` on GCS, `customfield_10016` on GTS), read from the board configuration. On `GCS` that field is on the screens of Stories only (Jira drops the value for tasks, bugs and sub-tasks), so only the 7 stories carry points there; on `GTS` every issue in the spec with an estimate has one.
- `--reset --yes` deletes the labelled issues and the `Seed Sprint ...` sprints (sprint writes are allowed only on boards 5 and 6).

## Measurement harness

`scripts/measure.sh <binary> <fake url> [runs]` drives the Native AOT binary in a private tmux server with private `XDG_*` directories, so no real profile, token or cache is read. Contract:

- Input: the binary, the base URL of a running FakeJira (written as the site of one active `fake` profile into the private `geeratya/profiles.json`; `GEERATYA_TOKEN=fake` is the token, so the binary talks to the fake and must be a loopback address), the number of sessions (default 20; `KEYS` presses per session, default 5; `TIMEOUT_MS`, default 5000).
- Output: median and p95 in milliseconds for the tmux floor (a trivial command), cold start to first frame and key to frame. Exit 2 for bad arguments, 1 when a frame never appears.
- Needs tmux and GNU `date`: Linux first (macOS needs GNU coreutils). Windows: `scripts/measure.ps1 <binary> <fake url> [runs]` (PowerShell 7 and psmux, `winget install marlocarlo.psmux`; options `-Keys` and `-TimeoutMs`, the `KEYS`/`TIMEOUT_MS` variables are ignored; exit 3 for a missing psmux) runs only the default scenario (tmux floor, cold start, `?` key to frame); it was verified on Windows 11 with psmux 3.4 (#632: psmux starts the pane command through pwsh, reads an empty config through `-f`, and the script sets `GEERATYA_USE_XDG=1` so the private `XDG_*` directories are honoured on Windows, see `docs/internal/decisions.md`; measured against the fake: floor 50-500 ms depending on how fast pwsh starts, cold start ~60 ms, key to frame ~30-80 ms, only comparable with its own earlier runs). The `SCENARIO` runs, `screenshot.sh`, the smoke scripts and `idle-cpu.sh` (reads `/proc`) have no Windows variant. `inspect.ps1` (PowerShell 7) takes the same arguments as `inspect.sh` (`--changed` or `-Changed`, globs).
- Every scenario that types a command first waits for the start picker ("Open a view") and closes it with Escape, because the picker would take the typed text as its filter (#759). It waits for the frame to appear or change; it never sleeps a fixed time (bounded exceptions in the scenarios: 0.5 s before Enter on a fresh list, 2 s for the debounced cache write before the first session is killed, 1 s before the RSS read, and 0.2 s before Enter in the sprint switcher of `SCENARIO=scrum`, and up to 2 s of settling after paging in `SCENARIO=list`).
- `SCENARIO=list` (open a list, `j` and `k` key to frame, 10 000 rows paged in with `G`, RSS; `ROWS`, `JQL`), `SCENARIO=detail` (only the first Enter to issue detail of a session, no settling sleep), `SCENARIO=scrum` (Scrum backlog and sprint switch with and without cache, `j` and `za` keys, RSS; needs a fake with `--issues 5000`; `SPRINT` is the text typed in the switcher) and `SCENARIO=views` (issue detail, second start from the disk cache, 10 tabs, `Tab` key, RSS) time a loaded view instead of the empty shell. `list` needs a fake started with `--issues 10000` (and `--fixtures`, see above); `detail` and `views` only need a JQL that returns `GEN-1` (`--issues 200` is enough) and print their own table; the `?` figures are not printed for `detail`, `scrum` and `views`. A wait that times out prints the last frame lines to stderr.
- `tests/Geeratya.Tui.Tests/Performance/HotPathMeasurements.cs` times the in-process paths (list and board keys at 10 000 rows, column regrouping) when `GEERATYA_BENCH=1`; it is skipped otherwise.
- Numbers go in `docs/internal/performance.md` with environment, dataset and latency; an optimisation PR quotes before and after.

For screenshots and manual tmux runs use the same pattern (`testing` skill, "Driving the real binary").

## Open-in-browser smoke

`scripts/smoke-browser.sh --binary <geeratya>` runs the real binary against the fake Jira with an empty `PATH` directory and no `BROWSER` (no opener can run), presses `<space>o` on a list row and again in the issue detail, and checks the status line. The fake is served over http, which the https-only gate (`BrowserUrlCheck`) refuses before any opener runs, so the first checked message is `Cannot open the link: only https links can be opened`. Then it opens `GEN-2`, whose remote link (the fake serves one https link for that generated issue) passes the gate for any host, and presses `Enter` and `<space>o` on it: the real launcher finds no `xdg-open` on the empty `PATH` and the status line says `Cannot open the link: no browser opener found: copy the URL`. Linux only. `TIMEOUT_MS` bounds each wait. Run it by hand after changing the browser path (nothing runs it automatically).

`scripts/smoke-mouse-overlays.sh --binary <geeratya>` sends SGR mouse press and release sequences (`send-keys -l`) to the real binary against the fake Jira: source picker, create form, jump prompt, field form suggestion, comment editor mention popup, a row dragged onto another Scrum backlog section (Esc keeps; `y` on `GCS` and `GTS` moves it to the backlog, checked against the fake's backlog list) and a card drag to the next column (with and without motion events) and `:profile list` (click and right-click) and the Confirm dialog's answer rows (click on Cancel keeps the profile, click on the yes row removes it). Linux only; `TIMEOUT_MS` bounds each wait, `DUMP=1` prints the frames. Run it by hand after changing the overlay mouse paths.

## Print frame against the fake

`geeratya --print-frame --size WxH --colors truecolor|16|none --source board:<name>|jql:<query>|issue:<KEY> [--layout list|columns] [--profile <name>]` draws a real screen without a terminal (`docs/internal/ux.md`, "Print frame"): start `fakejira` (see above), seed a profile whose site is its address into a private `XDG_CONFIG_HOME`, and run it with `GEERATYA_LIVE_HOSTS=127.0.0.1`. It is the cheap way to look at colours and layouts; the tmux pipeline below is for keys and the live shell. A site outside `GEERATYA_LIVE_HOSTS` is refused before any request. ## Screenshot pipeline

`scripts/screenshot.sh render|publish|clean` (skill `screenshots`) captures the real binary against `tools/FakeJira` (generated issues, `--issues 40`; never a real site). The `comment-*` scenarios use the generated one (editor, delete question) or, as `comment-recorded-*`, the recorded one (a saved comment on GTM-11, the edit warning on its rich comment): the fake keeps added comments in memory, so edit and delete work on added comments and on recorded ones (kept as an in-memory copy); `~` in a scenario's keys sends `Ctrl-s`. The `detail-relations-*` and `detail-epic-*` scenarios use a second fake on the recorded fixtures instead (the epic-scoped issue picker search answers the recorded epics GCM-8 and GCM-9; transitions are answered for every board card, so `status-*` runs on the generated one; every scenario of the table runs, #818; a failed wait prints the screen) and open one issue with `:jql key = KEY` (GTM-11 and GCM-10 for sub-tasks, links, remote links and attachments; the epics GTM-9 and GCM-8 for epic children, since no recorded issue has all five) in a private tmux server with private `XDG_*` directories. `tools/AnsiToSvg` (tests in `tests/Geeratya.AnsiToSvg.Tests`) turns the `capture-pane -p -e` text (SGR colours: 16, 256 and 24-bit; bold, dim, italic, underline, reverse; wide characters) into an SVG, `rsvg-convert` into a PNG. The generated issues carry `subtasks` stubs (3, 1, 2 or none by issue number modulo 4), so `sprint-subtasks` shows the sub-task row on the cards and `sprint-subtasks-expanded` one card expanded with `z a`. `detail-epic-suggest` types `GCM-1` into the parent chooser so the suggestion rows show the issue type in brackets (#794).

- Scenarios are rows of one table in the script (`name;columns;rows;theme;keys;wait-for`, `;` separated because keys hold `:`, and `|` in the keys sends Enter; `wait-for` is text that must be on screen after the keys, because data loads asynchronously and the settle check alone only compares two captures 0.15 s apart): `default` and `help` 120x36, `narrow` 64x30, `list` 120x36 and `list-narrow` 64x24 (a `:jql` view against the generated issues), `detail` 120x36 and `detail-narrow` 64x24 (Enter on `GEN-5`, whose generated detail has a formatted description and 120 comments; the fake serves `GEN-n` issues, comments and an empty remote link list in generated mode), `light` (the SVG's default colours are light) and `theme-latte`, `theme-high-contrast`, `theme-gruvbox` and `theme-list` (`:theme` on a board). Add a row per new screen.
- Needs bash, tmux, rsvg-convert, dotnet (and `gh`, `git` for publish and clean); a missing tool exits 3 naming it, an uncloneable screenshots repository exits 4. Linux only (other systems exit 3).
- The script seeds the private config directory with a `profiles.json` holding one active profile (`fake`, `fake@example.com`, site URL = the fake's loopback address) and exports `GEERATYA_TOKEN=fake` (the single-profile fallback), so the binary reads the fake without a hidden hook; before any key the script waits for the `Connected` banner or the board picker (the profile line is cut off at 100 columns or fewer, #742; the banner is momentary), which is also the smoke check that the binary started against the fake profile (`scripts/screenshot.sh render --binary <geeratya> --scenarios default`).
- It waits until two consecutive captures are equal (never a fixed sleep for the frame); the key delay between scripted key presses is 0.2 s.

## README demo

`scripts/demo.sh --binary <geeratya> --out <dir>` records the README demo (#209): the real binary in a VHS terminal (`scripts/demo-sprint.tape` and `scripts/demo-kanban.tape`: fixed 1400x760 pixels, font 16, Catppuccin Mocha) against `tools/FakeJira`, in private `XDG_*` directories with one fake profile and `GEERATYA_TOKEN=fake` (never a real site). Part one runs on the generated dataset (sprint board, issue), part two on the recorded one (Kanban board, issue GCM-10, a status change confirmed with `y`; since #818 both fakes answer transitions for every board card, so the second fake is kept only to avoid re-recording the tapes: unifying them would mean one tape and a generated-fake Kanban board). The script joins the parts into `demo.webm` and `demo.gif` (roughly 20 s). Needs Linux, `vhs`, `ttyd`, `ffmpeg`, `dotnet`; nothing runs in CI.

No binary media is committed here. The files are hosted on the project's GitHub Pages site (repository `geeratya.github.io`, like the owner's other project): copy `demo.gif` and `demo.webm` to its `media/` folder, which serves them at `https://geeratya.github.io/media/demo.gif` and `.../demo.webm`, the URLs the README uses. Until that repository is published the README image does not load (`landing-page.md`). Regenerate and copy again after a visible change to the shown screens. A tape that depends on a key or a scenario breaks when that changes: the tapes `Wait` for the key screens (board, issue, status picker, confirmation, `Moved GCM-10 to Done`), so a drifted run fails instead of producing a wrong video.
