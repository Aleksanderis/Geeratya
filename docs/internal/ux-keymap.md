# Key design

*Internal design note for maintainers and agents. Not needed to use or contribute to Geeratya.*

Rules for the keymap. The reference of what is bound is generated from `src/Geeratya.Core/Keymap/keymap.default.json` into [keymap.md](../keymap.md) by `scripts/gen-keymap-doc.sh`; a test fails when it is stale or the file has conflicts.

## File format

Rows of `{ "mode", "keys", "action" }`. `keys` is one key or a space-separated sequence (`g g`). A key is a single character (`j`, `?`, `G`) or a name (`Esc`, `Enter`, `Backspace`, `Tab`, `Shift-Tab`, `Space`, `Up`, `Down`, `Left`, `Right`, `Home`, `End`, `PageUp`, `PageDown`, `Delete`), optionally prefixed `Ctrl-` or `Alt-`. Uppercase letters are the character itself (`G`, not `Shift-g`). `action` is an id from `ActionCatalog`, which carries the title shown in help and the reference.

Display notation (Gitunia labelling, `KeyNotation.Display`): everything the user reads shows keys as `<space>g`, `gg`, `gt`, `]]`, `Ctrl-w c`, `<space><Tab>`; a single named key stays bare (`Esc`, `Enter`, `Down`). The file keeps the stored spelling above. A space appears only next to a long key name.

Checks (`KeymapTableTests`): no two rows with the same keys in one mode, no sequence shadowed by a shorter binding (`g` and `g g`), every action known, every key spelled correctly, every catalog action bound. Actions bound ahead of their feature are listed in `ActionCatalog.Unimplemented` (a test checks that pressing them changes nothing); actions that exist only in a modal mode are listed in `ActionCatalog.ModalOnly` (`IsModalOnly`; a test checks they are never bound in Normal mode and all others are). Status bar hints and the start-screen hint carry a short label and an `ActionId`; the key shown is the first one the keymap binds to that action in the mode, so a remapped key shows up in the hints. The which-key popup lists `KeymapTable.NextKeys` for the half-typed sequence (see `ux.md`, "Hints").

## User file

`keymap.json` in the configuration directory adds, replaces and removes rows over the defaults (`UserKeymap`, `UserKeymapStore` in Core); the guide is [customising-keys.md](../customising-keys.md). Rows that fail the checks above (plus printable keys in Command and Insert mode and dialog-only actions in Normal mode) are skipped and reported in the status line, a file that does not parse leaves the defaults, and `:keys reload` swaps the bindings of the running shell (`KeymapTable.Replace`; the reducer and the shell share one table on the UI thread). The user's rows are listed first so hints show their keys.

## Key rule

- Standard vim and neovim keys keep their vim meaning (`h j k l`, `g g`, `G`, `Ctrl-d`, `Ctrl-u`, `/`, `n`, `N`, `:`, `q`).
- A Geeratya-specific action never takes a bare vim normal-mode command. Vim's bare keys include `s u c a x r D M E` and every other letter that vim binds; Geeratya actions use a `<space>` leader chord or a `Ctrl-`/`Alt-` combination instead. Check a new key against vim before binding it.
- Everything doable by keyboard is doable by mouse and the reverse (the mouse table is [ux-mouse.md](ux-mouse.md)).
- Arrow keys, `Home`, `End`, `PageUp` and `PageDown` mirror the vim motions.
- Printable keys are text in Command mode and in any text field; only `Esc`, `Enter`, `Backspace`, `Ctrl-` and `Alt-` combinations act there.

## Layout for writes and Scrum (planned, M2 to M5)

Decided in #152 so that M2 and M5 bind into a plan. Nothing here is in `keymap.default.json` yet: each issue adds its rows (and runs `scripts/gen-keymap-doc.sh`) when its feature lands. Source: Gitunia's keymap redesign (one noun one prefix, no unrelated case pairs, command levels), adapted to Jira.

### Layout rules

1. **One noun, one `<space>` group.** `i` issue, `m` comment, `s` sprint, `k` rank, `v` view options (M6). A verb is the second key: `<space>is` changes the status of the issue. The M1 leaves `t c r l o p` stay leaves, and a leaf is never also a prefix (the conflict test enforces it), so no group may start with them. That is why comment is `m` (`c` closes a tab) and rank is `k` (`r` refreshes).
2. **No bare letters.** Writes never take a bare vim key (see "Key rule"). Two families only: `<space>` chords and `Alt-` chords. `Alt-h/j/k/l` move the selected card or row (status or rank); they mirror the vim motions, so nothing is learned twice. Every `Alt-` action also has a palette command (rule 6), which covers terminals that send no Alt (macOS Terminal.app without "Option as Meta"); `Ctrl-s` in editors needs the same check in #167 (flow control) with a fallback.
3. **No case pairs with unrelated meanings.** A capital is allowed only for the same verb with a narrower or wider target (`ic` create, `iC` create a sub-task of the selected issue).
4. **Everyday and advanced.** Each action has a level (`ActionCatalog`, #196; the generated `keymap.md` shows it); the setting is `commandLevel` (`:set commandlevel`). Everyday is what a normal working day needs, advanced is rare or risky. The level never changes a key: an advanced action stays bound and runs from the palette, it is only left out of the palette's default list, hints and which-key (hidden, never disabled, as in Gitunia); `<space>*` switches the level for the session.
5. **Same keys in every view.** A write acts on the selected issue of the active tab in list, columns, backlog and issue detail alike (in detail: the shown issue, or the comment under the cursor for `m` actions). A key that does not apply (a sprint key on a Kanban board, `Alt-h` in a list) shows a status note naming the reason and does nothing else.
6. **Every action has an id and a palette command** (`issue.create` is `:create`), so keys can be remapped later (M4) and the mouse path runs the same action.
7. **Stray keys never write.** Printable keys act in Normal mode only; text fields, pickers and forms are Insert mode. Destructive actions go through Confirm mode (`y`, `n`, `Esc`; `Enter` never confirms) and say what changes and that Jira cannot undo it.

### Selection and counts

- **Target of a write.** One set, decided in this order: the marked rows (`Alt-m`), else the Visual range, else the selected row. Marks and the range belong to the tab, survive scrolling and refresh by issue key, and `Esc` clears them, but only at the view root: inside an issue the stack pops first (built in #393; the `ux.md` Esc paragraph says so). In Visual mode the first `Esc` leaves the range, the next clears the marks. The status bar shows `N selected` while a set is active, and the badge reads `VISUAL` while the range is open. Built (#393): marks and the range are kept per tab as issue keys (`TabState.Marks`, `TabState.VisualAnchor`); a row in the list or backlog shows `*` (marked) or `+` (in the range) next to the cursor mark; a complete reload drops marks of issues that left the result and deleting an issue unmarks it. `Alt-m` in Visual mode marks the whole range (or unmarks it when every row is marked) and leaves Visual mode. Built (follow-up to #393): the columns layout has marks but no Visual mode (`v` says so, switching to the layout ends Visual mode). `Alt-m` marks the selected card and moves down its column, `Ctrl`-click marks the clicked card in place, and a marked card shows `*` in the cell before its type name (compact cards: the cell after the type marker); single-issue writes refuse with a set active there too.
- **Which writes accept a set.** Only the sprint moves (`sm`, `sb`) and the rank steps (`Alt-j`, `Alt-k`, which move the set as one block, order kept) are meant to take a set. The rank steps are built (#428): the set (in view order, at most 50 issues, all in the list or in one board column) is taken out and put together next to a row that is not in it, `Alt-k` above the row a count of places above the first member, `Alt-j` below the row that many places below the last member, so scattered marks are gathered by the first step; one request to the rank API keeps the order. More than one issue asks in Confirm first (it lists the keys and says Jira has no undo). A block that cannot move further says so. A Visual range becomes marks when it is ranked, so the block stays selected after the rows move. If Jira refuses some issues, the status line names how many and which; the view reloads. `<space>kt`, `<space>kb` and `<space>kk` refuse a set. The sprint moves are built (#181). A single-issue write, with a set active (any mark, or a Visual range of more than one row) refuses (`5 issues selected; clear the selection first`) instead of acting on the cursor row or on all of them. The gate sits in the reducer in front of the action, so keys, the palette, the context menu and the mouse refuse alike; inside an opened issue the open issue is the target and the gate does not apply. A key never widens or narrows its target silently.
- **Confirming a set.** A write on more than one issue always asks in Confirm mode, e.g. `Move 5 issues to sprint "Sprint 12"? Jira has no undo.`; the dialog names the count, the target and the first keys. A move that did not take every issue says so (`4 of 5 moved; GCS-7 not moved: <reason>`); the tabs reload to show what really moved, and only the issues that were not moved stay marked (the moved ones leave the marks and the Visual range), so a retry is one key (moving an issue already in the target is a no-op in the fake Jira; not yet confirmed on the dev site, #502). Issues already in the target are left out of the set before the question (all of them: "already in ..." and nothing is asked). A single issue moves without asking (or is refused with "already in ..." when it is there). Jira lets an issue be in one open sprint at a time, so a move takes it out of its other open sprint; closed sprints cannot be chosen.
- **Counts.** A count prefix (`5j`) repeats a motion or a step: `3 Alt-j` ranks three places. Any other write with a count is refused; a count never selects issues. The count prefix is built (#169, `AppState.Count`, shown in the status line next to pending keys, up to 999): digits `1`-`9` in Normal mode start it, `0` is a count digit only after another digit (as in vim), so a lone `0` stays "first column". `5j` and `5k` repeat the motion, `3 Alt-j` ranks three places in one write, `Esc` or any other key drops it, and a write that takes no count (`<space>kt`, `<space>kb`, `<space>kk`) refuses it with the status line.
- **Visual mode** is in the mode table in `ux.md` (built, #393): `v` enters, the motions (`j k Ctrl-d Ctrl-u g g G`) extend the range, `Esc` leaves, the write keys above work in it. It exists in list and backlog layouts, not in the columns layout (marks work there).

### Text input

- **Terminal key caveat (#462).** `Ctrl-j` is the line feed (0x0A); Terminal.Gui reports it as Ctrl+Enter, and `KeyTranslator` maps it back to `Ctrl-j` (Gitunia does the same, same Terminal.Gui). A real Ctrl+Enter therefore cannot be bound separately. `Ctrl-l` is the same as `Enter` in every picker and form, so in the comment editor and paragraph fields it adds a line. The overlay footers show only the first key of each action (`Up/Down`, `Enter`); the extra keys appear in help and `docs/keymap.md`.
- **Editors** (comment, description, other multi-line fields) are Insert mode: `Enter` is a new line, `Ctrl-s` saves (`Alt-Enter` too, for a terminal that swallows `Ctrl-s`), `Esc` cancels and asks first when the text changed. Single-line fields: `Enter` accepts. Built for comments in #167 (`Left`/`Right`/`Up`/`Down`/`Home`/`End`/`Delete` move and edit; `Ctrl-s` is the form's `form.submit`, the cursor actions are `editor.*`, Insert mode only; `Alt-e` (`editor.external`, #286) hands the text to `$VISUAL`/`$EDITOR`: `Ctrl-e` and `Ctrl-x` are taken in Insert mode, the Alt family is the free one; a terminal without Alt keeps the built-in editor, which has everything but the outside editor); `docs/internal/ux-screens.md`, "Comment editor".
- **Create form: navigate and edit states (#650, #708).** There is no multi-field edit form any more (#762): Summary and Description are edited in place in the detail (`ux-screens.md`, "Editing in place") and every other edit form has one field, always editing. The create form has a navigate state (each field is one stop, nothing is typed) and an edit state: it opens editing on Summary (`Esc` navigates, `Esc` again closes); in its navigate state `h`/`j`/`k`/`l` and `Ctrl-h`/`Ctrl-j`/`Ctrl-k`/`Ctrl-l` move between fields and panes (`ux-screens.md`, "Create form").
- **Forms** (transition, create, edit) show their fields in order; `Tab` and `Shift-Tab` move between fields (inside a form they do not change tab), `Ctrl-s` submits, `Esc` cancels (asks when changed). Required fields are marked and checked before the request. Built (#158): the three keys are Insert-mode rows (`form.field-next`, `form.field-previous`, `form.submit`); `Enter` accepts a field and, on the last one, submits (transition, assign, link and the one-field edit forms; the create form has a navigate state where `Enter` only ends editing, and `Alt-Enter` submits), which is also the way out where a terminal swallows `Ctrl-s`. `Ctrl-o` (`form.open-browser`, #279) opens the issue page in the browser, for fields the form cannot edit; the form stays as it is. The key shows in the form footer only when a field is read-only. In vim `Ctrl-o` jumps back in the jump list; Geeratya has no jump list, so the key is free here. Its mouse path (click the address) comes with #200. In a create form `Ctrl-f` (`form.more-fields`, #708) shows or folds the optional fields past the first five, and `Ctrl-g` (`form.open-after`) switches "open the new issue after it is created" on and off; the footer shows the state (`Ctrl-o` stays the browser key everywhere).
- **Suggestions** (owner's decision, #213 to #215): `@` (people) and `#` plus a project key (issues) open the popup inside text editors; picker fields (labels, components, assignee, selects) suggest by context as you type. No extra key opens a picker field's list. `Up`/`Down` and `Ctrl-p`/`Ctrl-n` choose, `Enter` or `Tab` accepts, `Esc` closes the popup only.
- **Pickers** reuse the source picker's keys (`ux.md`, Insert mode).

### Not planned

A bare-letter shortcut for any write, an undo key (Jira has none), bulk delete, bulk field edit, bulk status change.

## Design details (moved from `decisions.md`)

- **Command levels (#196).** The level is a property of the action in `ActionCatalog`, not of a key row in `keymap.default.json`, so every key of an action shares it; the generated `docs/keymap.md` shows it per row. Two levels only. The palette hides advanced actions only from the unfiltered list (a note counts them); any filter searches them too, because most have no typed command and "exact id only" would make `delete` unreachable. `<space>*` changes the level for the session without saving; `:set commandlevel` saves. Messages and Confirm texts that name a key are not filtered.
- **Quit and cancel (#390).** `Ctrl-c` quits from Confirm and cancels running read loads at once, but still asks while writes run and cancels (never quits) in a text form, where `Esc` asks about changed text. `q` quits in Normal only and does nothing in Confirm, so a stray key never answers a destructive question.

## Copying text

Copying an issue (#876): `<space>y y` copies the key, `<space>y u` the link, `<space>y s` `KEY Summary`; a bare `y` in a list, board or backlog copies the key (in an opened issue it copies text, as below). The target is the focused issue: the selected row or card; in an opened issue the sub-task, linked issue, Parent or Epic field under the cursor, else the shown issue. With a Visual range of several rows or marks set the copy refuses (it takes one issue; `Copy takes one issue: ...`), like the single-issue writes. The chords are leader keys, so vim's `yy` and `Y` stay free for text. Gitunia has no issue copy; its `Y` (copy rows) is the closest relative.

Decided in #773 (owner request; `decisions.md`, 2026-11-05). In an opened issue `v` starts a line selection on the cursor line (the row it is on, inside one pane), `j`, `k`, `Ctrl-d`, `Ctrl-u`, `g g`, `G` and the arrows extend it (the lines are drawn in the range tint, the cursor line stays the selected tint), `y` copies the lines to the system clipboard and ends the selection, `v` or `Esc` ends it without copying (`Esc` drops it before it pops the issue). A selection stays inside the pane it started in: a cursor in another pane stops at that pane's edge. Pressing `v` on a cut Description or comment shows all of it first. `y` with no selection copies the whole field or comment under the cursor, also the part cut off on screen (the Description and comments as the plain text of the rendered lines, a Details field as `label value`). Selected lines are copied as shown (the pane's wrapping), without the frame; the lines of one wrapped field join with a space. The Details sidebar takes no selection (`y` copies its field). Any data reload, resize or `z a` ends a selection, because its lines moved. The status line then says `Copied N lines (wl-copy)` or why not (`Cannot copy: ...`).

The clipboard is an effect (`CopyToClipboardEffect`, run in `Geeratya.App`) over `IClipboard` in `Geeratya.Platform`: Linux tries `wl-copy` (with `WAYLAND_DISPLAY`), `xclip` and `xsel` (with `DISPLAY`), macOS `pbcopy`, Windows `powershell Set-Clipboard` (up to 8000 characters, the text goes base64 encoded in the command), and when none works the terminal's OSC 52 sequence (up to 100 000 base64 characters; the terminal gives no answer, so the status says it was sent and that the terminal must allow it; inside tmux set `set-clipboard on`). With none of them the status line warns that no clipboard is available. Nothing is logged: the text is user content. The OSC 52 write goes through `TerminalWriter` in `Geeratya.Tui`, which runs it on the UI thread (the thread that draws frames), so it is ordered against frame output instead of racing it from an effect thread; the default clipboard of `Geeratya.App` has no OSC 52 fallback.
