# Architecture

Solution layout, layering, composition, threading and cross-platform rules. Code style is in `.claude/rules/csharp-style.md`; the Jira contract is in `docs/jira-layer.md`.

## Projects

`Geeratya.slnx` holds five source projects and one test project per source project. Shared settings live in `Directory.Build.props` (net10.0, nullable, warnings as errors, `EnforceCodeStyleInBuild`, trim and AOT analyzers), versions in `Directory.Packages.props` (central package management), the SDK pin in `global.json`, formatting in `.editorconfig`. The product version is `Version` in `Directory.Build.props`; `ApplicationInfo.Version` reads it from the assembly.

Layering is `Jira -> Core -> App -> Tui` (Tui references all of them), with `Platform` beside them (App and Tui use it): Jira never references Core, Core never references App or Tui, App never references Tui, and only Tui touches Terminal.Gui. Core takes platform facts (paths, capabilities) as plain values from the composition root rather than referencing Platform, so the state layer stays testable with literals.

## View model

A view is a source plus a layout (`docs/decisions.md`, 2026-11-01). `ViewDefinition(ViewSourceKind Source, string SourceValue, ViewLayout Layout)` in `Core/Views`: sources are JQL, saved filter, board, backlog, sprint (`SprintSource` value `boardId:sprintId` or `boardId:active`, load filtered by `sprint = <id>` or `openSprints()`) and Scrum backlog (every issue of a Scrum board, board id as value); layouts are list and columns (columns also for a sprint). `SprintSwitched` changes a sprint tab to another sprint: the old load is cancelled, a late reply ignored. The Scrum backlog shows its rows as sprint sections in the list layout (`Core/Backlog`, `docs/ux-screens.md`, "Scrum backlog"): the tab keeps its rows in section order, a pure `BacklogSections.Build(tab)` derives the sections and display lines from the rows, the sprint list and the collapsed sections, and the cursor is always a row. Issue details and every write work the same in every view. A new board kind is a new source or layout, not new loading code. All view state belongs to a tab; nothing is global.

## Views and tabs

Design for M1 (#64). The code issues build on the names below; a name in a table is the name the code uses. Everything is per tab and per site session; there is no static or global "current" anything.

**State shape.** `AppState.Session` (`SiteSession`) holds `IReadOnlyList<TabState> Tabs` (open order), `TabId? Active` and the site-level `SiteLink Link`. `AppState.Sequence` (a `long`, outside the session; `AppState.ViewportRows` next to it holds the last viewport height so a tab opened later starts with it) is the one counter every `TabId`, `RequestId` and recency stamp is drawn from; it only grows and survives a session swap. The placeholder `SiteSession.Views` is gone (#75); `SiteSession.Cache` (the string map) is removed rather than replaced, because the cache is not view state (see "Cache and refresh"). A profile change still replaces the whole session with `SiteSession.Empty(profile)`, which has no tabs.

`TabState` (record, `Core/Views`):

| Member | Meaning |

A property of `TabState`, not a constructor parameter (#84). |

`LoadState` replaces the `Idle/Loading/Loaded/Failed/Stale` list in the first draft of #75: "loaded" is `Idle` with rows, "stale" is the flag. `SiteLink` is `Online`, `Offline(since)`, `RateLimited(until)` or `Rejected`, driven by commands (`LinkChanged`) and failures, not by tab data.

**Tab rules.** Opening a view appends a tab and activates it. Closing the active tab activates its right neighbour, else its left; closing the last tab leaves `Active` null (start screen). Closing emits `CancelTabEffect(TabId)`. A tab keeps selection, scroll and layout while hidden (all in `TabState`); hidden tabs are not rendered, not polled and do no work on `Tick`.

**Memory bound across tabs.** At most 10 000 rows per tab (about 5 MB of `IssueSummary`, roughly 500 bytes each) and 50 000 across tabs, counting `PendingRows` too (a refresh gathers at most the tab cap again, so a board tab can briefly hold twice its rows). When an append or an activation exceeds the total, the hidden tabs with the lowest `LastActiveSeq` go `Cold` until it fits. Going cold drops `Rows`, `Next` and `PendingRows`, sets `RequestId = 0` and `Load = Idle`, and emits `CancelTabEffect`, so a reply still on its way finds no matching id. Definition, layout, selection key and scroll are kept; activation reloads the first page (`LoadReason.Open`: cache first, then network). A cold tab cannot restore a position deeper than its first page: the key is kept, the scroll falls back to the top. This is the cap #81 left to #64.

**Remembered tabs (#542).** The tab definitions (source, layout, quick filters, swimlane, lane, active tab; never rows or tokens) are kept per profile in `tabs.json` in the profile's state folder (`RememberedTabsStore`, same file handling as saved views). The reducer drives it: `StartupRequested` after the first frame emits `LoadTabsEffect`; `TabsLoaded` reopens the tabs (`SiteSession.Startup` tracks the phase, and nothing is saved while the file is still being read); every reduction whose tabs differ in definition emits `SaveTabsEffect`, written latest-wins off the UI thread. Nothing waits for the network.

**Request ids.** The reducer draws `RequestId` from `AppState.Sequence` and stamps it on the effect and on `TabState.RequestId`. A result is applied only if its tab exists and its id equals `TabState.RequestId`; anything else returns the state unchanged. Starting a new load for a tab (refresh, retry, reload after "page expired") supersedes the old id, so an old reply is ignored even when the host could not cancel it in time.

**Profile switch.** `ProfilesChanged` with another active profile (or removal of the active one) replaces `Session` with `SiteSession.Empty` and emits `DropSiteCacheEffect(oldProfile)`, as today. `AppState.Sequence` is kept, so a tab or request id of the old session never matches a tab of the new one. Replies of the old profile are stopped by two checks that cover each other: the reducer (unknown tab or id, which also catches a reply that was already queued to the UI thread before the switch) and the host, which drops a result whose site generation is not current (`SiteConnections.Generation`, see "Loading") before it is posted. This resolves the remaining parts of #57 and #59.

## Composition root

Dependencies are wired by hand in `Program.cs` (through `ApplicationRunner`) and `JiraServices.Create` once the Jira layer exists. No DI container: it needs reflection or code generation and costs startup. Tests build the same records or swap one part with `with` and a fake. `Program.cs` stays a few lines; the logic sits in `ApplicationRunner` so tests drive it without a process. Interfaces exist only where another layer consumes a class and tests need a fake.

## Threading

- The UI thread renders and handles input. It never waits on the network or the file system for long.
- Every Jira call is async, cancellable, has a timeout and honours rate limits; requests run on background tasks and report back as commands into the state layer, which the UI thread applies.
- The first frame is drawn before any network reply (startup target well under 100 ms).

## Loading

Effects stay data (`Effect` records). The code that talks to Jira lives in the UI-free `Geeratya.App` project (#153), next to `ProfileEffectHandler`: Core must not reference the host's connections, and a handler in App cannot draw. The Jira clients themselves are in `Geeratya.Jira`. The host hands itself to the runner as an `ICommandSink` (one `Post(Command)` method) and `SiteConnections` builds transports through an `ITransportFactory` (`DefaultTransportFactory` in the app, one over a fake HTTP handler in tests), so nothing in App depends on a delegate or is wired after construction.

| Type | Project | Issue | Role |
|---|---|---|---|
| `JiraServices` | App | #57 | Bundle of clients (search, board, filter, issue) built from `SiteConnections.Current`; no DI container. Not available while no transport exists. |
| `NetworkRunner` | App | #57 | Runs network effects on background tasks with a `CancellationTokenSource` per tab; stamps each run with `SiteConnections.Generation` at start; drops the result when `IsCurrent(generation)` is false or the token is cancelled; posts the rest through `ShellHost.Post`. `CancelScope(tabId)` serves `CancelTabEffect`, `CancelAll()` serves `DropSiteCacheEffect`. |
| `ViewLoadHandler` | App | #77, #78 | Turns `LoadViewPageEffect` into `ViewPageLoaded`, `ViewLoadFailed` (and `BoardConfigurationLoaded`), scoped to the tab id on the `NetworkRunner`. List sources (typed JQL, `filter = <id>` for a saved filter) share one search path through `ViewQuery.JqlFor` and `JiraServices.Search`; board and backlog go through `BoardClient`. The network call of a first board page (`Open`/`Retry`, no cursor) fetches the configuration first and reports it as `BoardConfigurationLoaded` through `NetworkRunner.StartReporting` (same currency check as the final command; a Sprint view also reports `SprintLoaded` with the named or first active sprint, null when none or the lookup failed), then asks for the issues. A failing configuration is the load failure (no issue request); later pages and refreshes reuse the configuration in the tab. The board id comes from the source value (a non-number fails the tab). `Background` selects `AsBackground()`; user opens use the user lane. |
| `ShellHost.Post(Command)` (`ICommandSink`) | Tui | #57 | Thread-safe entry that marshals to the UI thread, where the reducer runs; the only way a background thread changes state. |

Flow: key or `Tick` -> reducer -> `(state, effects)` -> the host draws the state and hands the effects to the runner -> a task calls Jira -> the result becomes a command -> `Post` -> reducer. The first frame is drawn from the initial state before any task exists, and a reply never touches state directly.

**Paging.** A tab holds only the cursor of the next page (`TabState.Next`): the opaque `nextPageToken` for `/search/jql`, the next `startAt` for the agile API (`PageCursor`; jira-layer.md, "Paging models"). Search has no total and tokens only go forward, so there is no jump to row N and a deep scroll pages through every earlier page.

- The next page is requested automatically when `Next` is not null, the load state is `Idle` (a `Failed` tab waits for an explicit retry, so a held key never hammers a failing Jira) and the selection is within one screen of the end (`Selected >= Rows.Count - VisibleRows`). One page in flight per tab: while `Loading`, scrolling asks for nothing; when a reply arrives the reducer checks again and may request the next page.
- Page size 100 (`ViewPaging.PageSize`; #66 records the real cap). At 10 000 rows `Next` is cleared, `Truncated` is set and the status line says "load more stopped at 10 000 rows".
- Board and backlog sources (agile API, offset paging, last page computed from `total`) load all pages one after another until the last page or the cap, because the columns layout needs every card. List sources (JQL, saved filter) load on demand. The reducer requests the next page of such a tab as soon as the previous one arrived (no selection rule, hidden tabs included); a failed page stops the walk until an explicit retry. The 10 000-row cap ends the walk with the same truncation notice. The Kanban board has no per-column paging. The cached first page holds only 100 rows, so a board opened from the cache shows stale partial columns until the walk ends. A page that repeats an issue already held (offset paging shifts when the board changes mid-walk) is skipped by key.
- `SelectionMoved(TabId, Index)` (sent by the list motion, #79) sets the selection and applies this rule; a page reply applies it too, so a viewport taller than the rows loads on without input. Only the active tab asks for more.
- A load that carried a page token and comes back 400 (token expired, jira-layer.md, "JQL search") is not shown as an error: the Jira layer reports it as `PageExpired`, and the reducer restarts at the first page with `LoadReason.Retry` (the old rows stay on screen) and keeps the selection by issue key.

**Stale replies and cancellation.** Closing a tab cancels its work (`CancelTabEffect`); a profile switch cancels everything (`DropSiteCacheEffect` makes the host call `NetworkRunner.CancelAll()`, `SiteConnections.Drop` and drop the cache). Cancellation is best effort; the guarantee is the request-id rule in the reducer plus the generation rule in the host ("Views and tabs").

**No connection.** When `JiraServices` is not available (no profile, no token, still connecting) the handler answers a load at once with `ViewLoadFailed` carrying a `JiraErrorKind.Unexpected` error whose text is a fixed "Not connected to Jira" line (the precise reason, such as a missing token, is the status-line notice from `ConnectionFailed`), so the tab shows an error instead of loading forever; a manual refresh after the connection is up loads it. `NetworkRunner.Start` takes the `whenUnavailable` command for this case: it is posted off the calling thread when no transport exists at start.

**Failures.** A failed load keeps the existing rows, sets `Load = Failed(kind, message)` and marks a tab with rows stale. The message comes from one pure table in Core keyed by `JiraErrorKind` (`LoadErrorText`, #77), so the reducer builds it and it is shared by refresh and the banners (#90); which kinds mean what is in jira-layer.md, "Errors to UI states".

**Network states** (#90, drawn with the existing `PaletteRole`s; never colour alone, every state also has a text marker). One status per tab, highest first, from the pure `TabStatus.Of(tab, session.Link, now)`:

| Status | When |
|---|---|
| Error (rejected token) | `Link` is `Rejected`, or the tab failed with `Unauthorized`: the whole site, every tab |
| Rate limited | `Link` is `RateLimited(until)` with `until > now`; shows the wait end |
| Offline | `Link` is `Offline`, or the tab failed with `Network`, `Timeout` or `HostRefused`; last data kept |
| Error | `Failed` with another kind (`Unexpected`, `ServerError`, ...): banner with the message and a hint (403/404 not found or no access; 400 Jira's own text) |
| Stale | `IsStale`, with the age from `LoadedAt` (also while its refresh runs: the banner says `Refreshing…`) |
| Loading | `Load` is `Loading` on the user lane (a background refresh is `Fresh`) |
| Fresh | none of the above |

`TabStatus.Of` and `NetworkBanner` (Core, `Views/`) are pure; the frame builder takes the `now` of the host, so the banner (blank row under the tab bar, `FrameBuilder.HeaderRows`) and the status word count down without any state change. `TabStatus.ShowsTime` tells the host to redraw on a tick. The rate-limit wait reaches the reducer as `LinkChanged(SiteLink.FromRateLimit(until))`, posted from the transport's event through `ShellHost.Post` (never a UI call from that thread).

**Cold start.** The first frame comes from a state with no tabs; the remembered tabs reopen right after it (see "Remembered tabs"). Opening a view issues the load; the handler answers from the cache first (memory, then disk, off the UI thread) with `ViewCacheLoaded`, then asks Jira ("Cache and refresh").

## Cache and refresh

**Cache.** Memory plus disk behind one host-owned object, `SiteCache` (`Core/Cache`; it takes its root directory from the composition root, Core never references Platform). It is not part of `AppState`: LRU order and byte counts are infrastructure, not view state, and keeping them out keeps the reducer pure and cheap. The load handler reads it; the reducer asks for writes with `WriteCacheEffect`. The host holds one `SiteCache` per active profile and `DropSiteCacheEffect` disposes it. (This differs from the first draft of #82, which put the memory part in the session.)

- Memory, per session: views by `CacheKey(ViewSourceKind, SourceValue)` (at most 32, LRU) and issue details by issue key (LRU, default 200). The view entry is the first page (`CachedView`: rows, optional `BoardConfiguration`, `SavedAt`).
- Disk: below the cache directory of `ApplicationDirectories`, one folder per profile named by the first 16 hex characters of SHA-256 of `Profile.CredentialKey` (that key contains site and email, so only the hash is used; the token is never involved), holding `view-<hash of CacheKey>.json` and `issue-<hash of issue key>.json`. Cached (#82): the first page of every opened view (at most `ViewPaging.PageSize` rows, so memory is bounded by 32 views times one page); nothing from `Authorization`. Issue details (#122): `SiteCache.GetIssue(key)` / `PutIssue(CachedIssue)`, at most 200 in memory (LRU), one `issue-<hash of upper-cased key>.json` each (same atomic write, debounce, schema check, size cap and oldest-first eviction as view files, shared in one folder), with their own DTOs (`CachedIssueFile`, ADF as the flat `CachedAdfNode`) and the mappers `IssueCacheMapper` / `AdfCacheMapper`. A file of another schema, corrupt or with a wrong key is a miss and is deleted. The detail flow reads `GetIssue` first (shown with the `STALE` banner) and calls `PutIssue` after a successful load (#221); a 404 or 403 on the issue load emits `RemoveIssueCacheEffect`, which calls `RemoveIssue(key)` (memory at once, the file deleted with the next flush; a later `PutIssue` cancels it) (#243); the handler also calls it itself, so the entry goes even when the reply arrives after the issue was popped or the tab closed (#250); comments, links and children are not cached.
- Files are JSON through a Core source-generated context (`CacheJsonContext`) with its own DTOs (`CachedIssueRow`, ...) and a mapper to and from the Jira models, and `{"schema": n}` in every file. A Jira model change then breaks the mapper at compile time instead of silently changing cached files. A schema mismatch, parse failure or foreign file is ignored and deleted, and the data is refetched. The duplication is at this boundary only; core state uses the Jira models directly.
- Writes are off the UI thread, debounced (2 s after the last change), atomic (temp file in the same folder, then replace); a failed write is dropped with a one-line notice, since a cache is never a reason to fail a read. Cap 20 MB per profile folder, oldest files evicted first. Best-effort flush on exit.
- Removal: `DropSiteCacheEffect` disposes the memory part, discards pending writes and cancels work; the disk folder stays, so a view reopens at once when the profile comes back. Removing a profile also deletes its folder: `RemoveProfileEffect`'s handler calls `SiteCaches.Delete(profile)`, which first disposes that profile's `SiteCache` (no pending write or exit flush can recreate the folder) and then deletes the folder. Other profiles' folders are never touched, and two profiles on one site with different accounts have different credential keys, so different folders. (A switch keeping the disk folder differs from #82 and CLAUDE.md wording "drops that site's views and cache": the views and memory cache are dropped, the disk files are kept; `docs/decisions.md`.)
- Permissions: the cache folders and files are created readable by the user only (mode 0700/0600 on Linux and macOS through a Platform helper; on Windows the default ACL of `%LOCALAPPDATA%` already restricts them, an explicit branch). Cached summaries are plain text of the user's own issues.

**Opening a view.** The reducer opens the tab as `Loading` with no rows and emits `LoadViewPageEffect(Open)`. The handler (for `LoadReason.Open` only, never for refreshes or next pages) reads the cache first on a background task through `NetworkRunner.StartLocal`, which needs no connection, so an offline start still shows the cached rows; on a hit it posts `ViewCacheLoaded` and only then asks Jira, so the cached rows always precede a reply or failure; the reducer shows those rows at once with `IsStale` (only if the tab still has no rows and the request id is current). The network reply then replaces the rows, clears `IsStale`, keeps the selection on `SelectedKey` (if the key is gone the index is clamped) and emits `WriteCacheEffect`. A miss shows the loading state. A failed load keeps the cached rows, stale; with no cache the empty body explains the error.

**Refresh rules.** Only the active tab, ever; hidden tabs neither poll nor render.

- Time is injected: a host timer posts `Tick(now)` once a second (the reducer ignores it without an active tab), and commands carry their own `At`. `AppState` stores no "now". The reducer returns the same state instance when a tick changes nothing, and the host skips the redraw when the state reference is unchanged and nothing on screen shows time. Time-dependent text (the rate-limit countdown, the age of stale data at minute granularity) is drawn by the renderer from the `now` the host passes in, and the host redraws on a tick only while such text is visible. An idle tick costs a comparison and at most the small `ReduceResult` record.
- Schedule: refresh when `now >= NextRefreshAt` (`LoadedAt + 60 s` after a success); the next `Tick` decides, the reducer never reads a clock of its own. `TabActivated` carries no time, so it sets `NextRefreshAt = min(NextRefreshAt, LoadedAt + 30 s)` and the next tick (at most a second later) refreshes when that is already past. The manual refresh key (`RefreshRequested`) refreshes unless a load of that tab is in flight and always uses the user lane. Never more than one load in flight per tab.
- Scope: list sources reload the first page only; board and backlog sources reload every page (gathered in `PendingRows`, swapped in with the last one). Rows are replaced as a whole, selection stays on its issue key, scroll is kept; the board configuration is refetched only by a manual refresh. Automatic and activation refresh are skipped for a list tab that has loaded more than the first page (`Rows.Count > PageSize`), because tokens only go forward and replacing the rows would throw the reader's position away every minute; such a tab is refreshed by the manual key, which resets it to the first page (selection kept by key if it is there, else nearest row).
- Priority: automatic and activation refreshes are `LoadViewPageEffect(Background: true)`, i.e. `AsBackground()`, so they never queue ahead of a key press; open, next page, retry and manual refresh use the user lane.
- Pauses: no automatic refresh while `Link` is `RateLimited` (the transport publishes `JiraTransport.RateLimitedUntil` and `RateLimitWaitChanged` on a non-UI thread; the host maps them to `LinkChanged`) until the end passes, nor while `Link` is `Rejected`. While `Offline` the interval gives way to the backoff probe below, which is how recovery is noticed.
- Backoff: after a failure `Failures` grows and `NextRefreshAt = At + min(300 s, 60 s * 2^(Failures-1))` (60, 120, 240, 300 s); a success resets it and sets `Link` to `Online`. A 401 sets `Link = Rejected` and stops automatic refresh until the connection check (#83) succeeds; a manual refresh is still allowed.
- A failed refresh never destroys rows: they stay, `IsStale` is set and the error is shown.
- A failed next page is not a refresh failure: it does not count towards the backoff, blocks automatic refresh of that tab (which would replace the rows under the reader) and is retried by the refresh key. Pages that shift between requests can repeat an issue; an appended page drops keys that are already loaded.

**Writes.** Automatic and activation refresh wait while a write runs, and a load keeps the optimistic row of a key under an operation: "Write pipeline".

**Bounds.** Every cache and list has a size bound and an owner that drops it (`docs/performance.md`): 10 000 rows per tab, 50 000 across tabs, 32 cached views, 200 cached details, 20 MB of disk per profile. #91 measured them (`docs/performance.md`, "M1 measurements").

## Write pipeline

Design for M2 (#151); the operations part is built (#154, `Core/Writes`, `WriteHandler` in App) with `AssignRequest` (`<space>ia`, `<space>im`, #164), the first confirmed write `DeleteIssueRequest` (#165, `<space>id`) and `RankRequest` (#169); optimistic rollback is built for assign and rank, the cache part follows with its features. Issue links are writes too (#190: `LinkIssuesRequest` from the field form, `UnlinkIssuesRequest` after a Confirm, both a `LinkWriteRequest`: not optimistic, no row read-back, the details of both issues reload, a lost reply is checked by reading the issue). Every M2 feature (transition, rank, edit, assign, create, comment, delete) is a write and goes through the parts below, so they are settled once. It follows the Loading rules (reducer pure, effects are data, replies matched by id) and adds what writes need: Jira has no undo, a started write cannot be cancelled, and a lost reply leaves the outcome unknown. Gitunia retrofitted most of this in its M7; here it comes first.

**Where it lives.** State and reducer in `Geeratya.Core` (`Core/Writes`, `WriteReducer` routed from `AppReducer` like `ViewReducer`). The effect handlers go in the UI-free `Geeratya.App` project, not in `Geeratya.Tui`: a handler there cannot draw. `Geeratya.Jira` gets the write clients and returns typed `JiraResult<T>`, never touching the UI.

### Running operations

An operation is one user action that writes. Operations are recorded in `SiteSession.Operations` (site level), each stamped with the tab that started it, not in `TabState`. Reason: the target is an issue, and the same issue can be on screen in several tabs, so exclusion must see all of them; a tab close must not forget a write that is already on the wire. Everything else stays tab scoped.

| Type | Meaning |
|---|---|
| `Operation(long Id, WriteRequest Request, TabId Origin, OperationPhase Phase, IReadOnlyList<RowChange> Undo, DateTimeOffset StartedAt)` | `Id` is drawn from `AppState.Sequence` (never reused, survives a session swap). `Kind` and `Keys` are read from the request: the issues written (the moved issue for a rank, not its reference issue; empty for create until the reply). `Undo` is what an optimistic update changed (below). `StartedAt` is the time carried by the command. |
| `OperationKind` | `Transition`, `Rank`, `Assign`, `EditFields`, `AddComment`, `EditComment`, `DeleteComment`, `CreateIssue`, `DeleteIssue`, `Bulk`. |
| `OperationPhase` | `Resolving` (a transition id or form metadata is being fetched, read only), `Sending` (the write is on the wire), `Verifying` (outcome unknown, the issue is being re-read). Removed from the list when finished; there is no `Done` phase. |
| `WriteRequest` (closed record hierarchy) | What to write, with ids already resolved: `TransitionRequest(Key, TargetStatusId, Fields)`, `RankRequest(Key, ReferenceKey, Before, RankFieldId, WasAfter, WasBefore, HiddenBetween)`, `AssignRequest(Key, AccountId?)`, `EditRequest(Key, FieldValues)`, `AddCommentRequest(Key, Adf)`, `CreateRequest(Fields)`, `DeleteRequest(Key, DeleteSubtasks)`, ... Pure data, so a test can build one. |
| `WriteRequested(TabId, WriteRequest, At)` | Command from a key or a submitted form. The reducer applies the rules below and returns `ExecuteWriteEffect(OperationId, WriteRequest)` or only a status line. A request subclass knows its keys, its optimistic `RowChange`, how to tell from a re-read row that it was applied (`IsShownBy`) and its status texts. |
| `OperationPhaseChanged`, `WriteSucceeded(OperationId, At, Rows)`, `WriteFailed(OperationId, At, WriteError)`, `WriteOutcomeUnknown(OperationId, At, WriteError)`, `WriteVerified(OperationId, At, VerifyOutcome, Rows)` | Replies, applied only while an operation with that `Id` exists (the request-id rule of "Views and tabs", with the operation id as the request id). `At` is injected like everywhere. The handler decides failed or unknown from `WriteError.IsOutcomeUnknown`; a `WriteFailed` that is unknown anyway is verified, never rolled back. The text of a definite failure comes from the pure table `WriteFailureText` (Core). |
| `ExecuteWriteEffect`, `VerifyWriteEffect`, `InvalidateCacheEffect` | Effects, run by `WriteHandler` (App); `InvalidateCacheEffect` by the host (`SiteCache.RemoveIssue` per key and `RemoveViews`). The read of the written issues after a success is part of the handler (one search, `key in (...)`) and comes back inside `WriteSucceeded` as the server rows; rows that do not yet show the change (the search index lags) are dropped, so a stale read never undoes the optimistic row. |

**Mutual exclusion.**

- A write whose `Keys` intersect the keys of a running operation is refused: no state change except the status line, `GCM-3 is busy (moving to In Progress)`. It is not queued: a queued write was composed against a state that is about to change, and the user can repeat the key in a second.
- Writes on disjoint issues run in parallel (the transport cap of 4 and the user lane order them). A create has no key and never conflicts, except that one form submits once.
- Deleting an issue also locks its known sub-tasks (the parent's `subtasks` field, as far as it is loaded; best effort, a sub-task that is not loaded is not locked and Jira decides); a rank locks only the moved issue, because the reference issue is only read.
- Reads never wait for writes: opening an issue, comments and loads continue, with the merge rule below.

**Refresh while a write runs.** Automatic refresh and activation refresh of every tab wait while `Session.Operations` is not empty: `Tick` skips them (`NextRefreshAt` stays in the past, so the first tick after the last operation ends refreshes; this is one list-empty check per tick). A manual refresh (`<space>r`) is not dropped: it sets the tab's `RefreshQueued` and runs when the last operation ends (after a failure too), with the status line `Refresh after the write`; a queued tab that is loading by then needs no second load. A load already in flight when a write starts is not cancelled; its reply is applied with one extra rule (`WriteMerge.KeepHeldRows`): for a key under an operation the tab keeps its current (possibly optimistic) row and takes every other row from the reply. So the card does not flicker back, and the finish of the write (below) brings the truth for that key. The rule must also hold after the operation ends: when an operation is applied, every tab that is loading gets the keys in `TabState.ProtectedKeys` (the load may have started before the write), and its reply keeps the tab's row for those keys; the list is cleared when that load ends. A failed write protects nothing: its rows went back, so the reply's row is the truth. A next-page append follows the same rule: a row of the page for a key the tab holds is dropped by the append's own key check (the tab's row stays), and for a key it does not hold yet the page row is replaced by the server row of the write (`TabState.ProtectedRows`, set when the write ends) or, while the write runs, patched with its optimistic change. Board loads walk many pages, so a reply can arrive well after the write. An issue detail reply follows the rule for the fields the write changed (`WriteMerge.KeepHeldFields`: the running operations' changes, plus `DetailState.HeldChanges` for a request that was in flight when the write ended; cleared by the reply). A success also marks the shown issue of every tab holding the key `IssueStale` and reloads it under a new request id (at once in the active tab, on activation in the others), so a reply that predates the write is dropped (active tab) or patched with `HeldChanges` (hidden tab). Only changes of writes that ended reach the cache, never an optimistic value of a running write; a failed write marks and reloads the shown issue the same way, because a reply during the write may have carried its optimistic value.

**Tab close.** Closing a tab cancels its loads (`CancelTabEffect`) but not its operations: a write that was sent cannot be undone, and cancelling the `HttpClient` call only hides the answer. The operation stays in `Session.Operations` with `Origin` pointing to a tab that no longer exists; on finish the reducer updates every tab that holds the keys and puts the result on the status line of the active tab. Writes run detached (`NetworkRunner.StartDetached`: no tab scope, nothing kept after they end), cancelled only by `CancelAll()` of a profile switch or exit; so no scope dictionary grows with every write. Switching profile or quitting with operations running asks first (`1 write is still running; its result will not be shown. Quit anyway?`, built; `y`/`n`/`Esc`), because those results are dropped by the generation check. The prompts use the existing string `ActionOnConfirm` (the switch keeps the profile name in `Target`). After the `y`, quit waits up to 5 s for running writes to settle (`WriteHandler.WaitForRunningAsync`, called by `ShellHost` on `QuitEffect`; the UI keeps running meanwhile), then stops (the status line says it is waiting; writes started during the wait are not awaited); a write still on the wire after that is cancelled by the shutdown.

### Optimistic update and rollback

Rank (#169) is the one optimistic write that moves a row instead of changing a field: its `RowChange` is an `OrderRowChange(Key, ReferenceKey, Before, WasAfter, WasBefore)`, applied through `RowChange.PatchOrder(tab)` and undone through `RevertOrder(tab)` (only where the moved row still sits next to the reference, so a newer order from a reload wins), in every tab whose source is a board or a backlog (a JQL tab is not ordered by rank and is left alone). The selection follows its key. `RankActions` (Core) turns the keys into a `RankRequest` for the active tab (reference = the next shown row or column card; a card shown under its parent moves with its group); `WriteHandler` sends it with `RankClient` (no read after it, `ReadsBack` is false; a 207 that names the issue as not moved is a definite `Validation` failure) and the success, a refusal that doubts the shown order (400, 404, 409) and a lost reply queue a reload of the tabs holding the issue.

| Update the row at once | Wait for the reply |
|---|---|
| Transition (card to another column), rank (card to the new position), assignee, priority, labels, summary and other fields that a row shows | Create (no key, no row), delete (Jira may refuse because of sub-tasks or permission, and a row that comes back is worse than a wait), add/edit/delete comment (the comment id and body come from Jira), description edits (ADF conversion; the row does not show it) |

Optimistic means: on `WriteRequested` the reducer changes the held `IssueSummary` of that key in every tab that has it, records `RowChange(Key, Field, Before, After)` in `Operation.Undo`, and emits the effect. Rows are immutable records, so a patch builds a new row and a new array of references (O(rows) per tab, 80 KB of references at the 10 000-row cap; to be measured in the first implementing issue per `docs/performance.md`). Selection stays on the key; the cursor follows the card in the columns layout (`BoardCursor` is recomputed from the rows).

Success: the optimistic row stays only until the truth arrives. The handler re-reads the written issues with one search (`key in (...)`, the row field list, user lane) and the reducer replaces rows by key in every tab from `WriteSucceeded`. This is the whole refresh for transition, assign and edit: one call, not a reload, so a list tab that has paged past the first page (which automatic refresh skips) is still correct. Rank, create and delete change membership or order, so they mark every tab holding the view `IsStale` and reload the origin tab (board tabs reload all pages as in "Cache and refresh"); the server order is the truth after a rank, never re-sorted locally (`docs/jira-layer.md`, "Ranking").

Failure with a definite result (the request was not applied): the reducer undoes each `RowChange` only where the field still equals `After` (a newer patch from a reload wins and is left alone), removes the operation, and shows the error (below). Failure with an unknown outcome: no rollback yet, see "Lost reply".

The stale-reply rules of "Loading" hold with the operation id in place of the request id: a reply for an operation that is gone (a profile switch dropped the session) matches nothing and is ignored; the host also drops replies of an older `SiteConnections.Generation`.

### Write errors as typed results

The Jira layer returns `JiraResult<T>` with the existing `JiraError(Kind, Status, Message)`. For field errors it gains `IReadOnlyDictionary<string, string> FieldErrors` (the `errors` object of a 400, `docs/jira-layer.md`, "Errors"; empty otherwise). A pure Core table, `WriteFailure.Of(JiraError, OperationKind)`, maps it once (like `LoadErrorText`) so the reducer builds the text and the result is testable without Jira. It switches on the HTTP status first and on `JiraErrorKind` second: the mapper has no kind for 409, 405, 413, 415, 422 or 423 (they arrive as `Unexpected` with the status) and no kind is added, the status stays the source. Any other 4xx is a definite `Refused(message)`; only `Unexpected` without a 4xx status is unknown. When a 400 carries both `errors` and `errorMessages`, the fields go to their fields and the messages to the form's top line. `Definite` says whether the request is known not to have been applied.

| Jira result | `WriteFailure` | Definite | Behaviour |
|---|---|---|---|
| 400 with `errors` | `FieldRejected(fields)` | yes | Roll back; if a form is open it stays open with each message at its field (form state, below); a field the form does not show goes to the form's top line. Without a form (inline move) the first message goes to the status line. |
| 400 with only `errorMessages` | `Refused(message)` | yes | Roll back; show Jira's text. Workflow validators and conditions that refuse a transition are expected here (text from the workflow); the dev workflows have none (#31), so this rests on Atlassian's docs and is unverified. |
| 401 | `Unauthorized` | yes | Roll back; `Link = Rejected` as for loads; the user fixes the token. |
| 403 | `NoPermission` | yes | Roll back; names the action and the issue: `No permission to transition GCM-3`, then Jira's own text (it names the permission, `docs/jira-layer.md`, "Errors"). |
| 404 | `Gone` | yes | Roll back; `GCM-3 not found or no access` (Jira cannot tell them apart); the tab is marked stale and refreshed, so a deleted issue disappears. |
| 409 | `Conflict` | yes | Roll back and reload the issue: `GCM-3 changed meanwhile`. Jira's issue API sends no ETag and edits are last write wins, so a 409 is not expected on plain edits; it is mapped in case agile calls send one (unverified). |
| 429 | `RateLimited(wait)` | yes | Roll back and say `Try again in N s`. Not retried automatically: the transport retries only idempotent reads, and a retry the user did not choose is wrong while the banner already counts the wait down. |
| `HostRefused` | `Offline` | yes (nothing was sent) | Roll back. |
| `Timeout`, `Network`, 5xx, `InvalidResponse`, `Unexpected` | `OutcomeUnknown` | no | See "Lost reply". `Unexpected` is included because a client bug after sending must not claim "not done". |

**Lost reply (unknown outcome).** The transport never retries a write (`JiraRequest.Write`), and neither does the app: a transition may be idempotent, a create or an added comment is not. The reducer sets `Phase = Verifying`, keeps the optimistic row, shows `GCM-3: not sure the move worked, checking`, and emits `VerifyWriteEffect`, which reads the issue (user lane, a read, so the usual retries apply) and compares with what was meant:

- transition: status equals the target; edit/assign: the fields equal the request; delete: 404 means done; rank (built, #169): not decidable, because no field of one issue shows the order and the docs warn against comparing rank values; the verify is skipped (`WriteRequest.ReadsBack` is false), the outcome is `Unreachable`, the order goes back and the tabs reload;
- create: cannot be told exactly; the handler searches `reporter = currentUser() AND created >= -N` minutes (N: minutes since the submit, rounded up, at least 1; `-10m` when no submit time is remembered) `ORDER BY created DESC` for the same summary and project and offers what it finds; if nothing is found it says `May or may not have been created` and reloads the tab. It never creates again by itself;
- comment add: re-read the comments for the same author and body;
- applied: `WriteVerified(Applied)` finishes as a success; not applied: it finishes as a definite failure (rollback, `It was not applied`); the verification itself fails (still offline): the optimistic change is rolled back, the rows are marked stale and reloaded when the link is back, and the status line says the outcome is unknown. The truth always arrives through a reload; the app never guesses `done`.

### Confirm flow

The existing `ConfirmRequested(ConfirmRequest)` is reused with its behaviour unchanged (`y`, `n`, `Esc`; `Enter` never confirms, `docs/ux.md`). `ConfirmRequest` today carries an action id string; for writes it gains an optional `Command? OnConfirm`, which the reducer returns on `y` (the string action stays for the profile removal). The confirmed command is a `WriteRequested` (a request with a `WriteRequest.AskText` asks first unless the command is marked `Confirmed`, #159), so mutual exclusion is checked again at that moment, not when the dialog opened. Built with delete (#165): `ConfirmRequest.OnConfirm` holds the command and `y` reduces it. `issue.delete` first counts the sub-tasks (`CountSubtasksEffect`, one search `parent = KEY AND issuetype in subTaskIssueTypes()`, at most 50, `PendingDelete` in `SiteSession` matched by request id), because the answer decides the text and `deleteSubtasks`; only then does Confirm open. A failed count opens nothing. The delete is not optimistic: on success `WriteRemoval` takes the rows and open details of the key out of every tab, the caches are dropped and the origin tab reloads; a lost reply is verified by reading the issue (404 = done, readable = not applied, anything else unknown). The question is one status-bar line, so the key, sub-tasks and "Jira cannot undo this" come first and the (shortened) title last.

| Write | Confirms | Text names |
|---|---|---|
| Delete issue | always | the key and summary, and the number of sub-tasks that go with it (`deleteSubtasks`, `docs/jira-layer.md`, "Hierarchy") |
| Delete comment | always | the issue key and the first words of the comment |
| Bulk edit, bulk transition, assignee or sprint change for several issues | always | the count and the first three keys, the field and the new value |
| Single transition to a status of the `done` category, or to a plain transition whose workflow shows a screen with nothing to fill in (#159) | always | `Move GCM-3 to Done? Jira cannot undo this; the workflow may do more than change the status`. Jira does not expose post functions, so these two are the only hints of a side effect (`TransitionChoice.AsksFirst`). A transition whose form the user filled and submitted is not asked again. |
| Any other single transition, rank, assign, edit, comment add, create | never | Reversible by another write, or invisible to others until saved. |

The rule for the text: it says what changes (key, field, old to new, or the count), that Jira cannot undo it, and for several issues what happens on partial failure. A bulk operation is one `Operation` with all keys, run one issue at a time; the failure text says how many were done and lists the keys that were not: `3 of 5 changed; not changed: GCM-4, GCM-7`. Plural forms are handled in the text builder.

### Where form state lives

Built in #158 (`Core/Forms`, `FormReducer` routed from `AppReducer` like `ViewReducer`, `FormMetadataHandler` and `FieldUpdates` in App, `FormOverlay` in Tui). All form state is in the state layer, in `TabState.Form` (null when none; one form per tab, so a form never belongs to the renderer). The form takes the keys while the mode is Insert and the active tab has one (`FormReducer.IsOpen`); the profile form and the source picker keep their own fields on `AppState` and are never open together with it.

- `FormState(FormTarget Target, IReadOnlyList<FormField> Fields, int Focus, bool IsLoading, long RequestId, string? TopError, long? OperationId, bool DiscardPending, string? BrowserUrl, SuggestionState? Suggest)`. A `FormTarget` says what the form is for: which metadata it loads and which `WriteRequest` its changed fields become (`Request(changes)`). `EditFormTarget`, `CreateFormTarget` (#162), `TransitionPickTarget` and `TransitionFormTarget` (#159) are built; so the form itself never learns about them. A target may adapt to the loaded metadata (`Loaded(fields)`: a create drops the parent when the type has no `parent` field) and refuse the form (`Blocked(fields)`: a type that requires a parent opened without one). A target may also refine itself from the metadata reply (`FormMetadataLoaded.Target`: the picker gets the transitions Jira offers), name a follow-up form instead of a write (`Following`: the picked transition asks for fields), submit at once without showing (`Automatic`: one transition leads to the column), close as soon as the write starts (`ClosesOnSend`: the result goes to the status line) and allow an empty submit (`AllowsNoChanges`: optional transition fields). (The first design had a `FormKind` enum and a key; the target replaces both.)
- `FormField` holds the field id, label, `FormFieldKind` (decided from the Jira schema by `FormFieldMapper`: text, paragraph, number, date, date-time, select, multi-select, labels, user, parent, unsupported), `Required`, the options, the `Value` and the `Initial` value (only fields that differ are written), the typing buffer, and the field's `Error`. Components and versions are choices; user and parent are picked through the suggestion popup (below). `FormFieldMapper` maps `EditField` (editmeta), `CreateField` and transition `FieldMeta` alike and orders editable fields (required first) before read-only ones.
- Metadata is loaded when the form opens by a request id like a load: `OpenFormRequested` sets `Form` with `IsLoading` and emits `LoadFormMetadataEffect`; `FormMetadataLoaded` / `FormMetadataFailed` are applied only while the form waits for that request id. The editmeta carries no values, so the opener passes the current ones it already has (`EditFormTarget.Known`, from the row or the detail).
- Editing is a pure `(field, input) -> field` (`FormEditor`), testable without a terminal; text is bounded to 32 767 characters per field.
- Submit (`FormReducer.Submit`) commits a label being typed, validates (`FormValidation`: required editable fields, number and date text) and, when valid, builds the target's `WriteRequest` from the changed fields and runs it through `WriteReducer` (so the busy refusal, the optimistic row patch and the lost-reply path are the ones of the write pipeline). A refused start (busy) keeps the form with the reason on its top line; a started one sets `OperationId` and the form shows `Saving…` and ignores edits.
- `WriteReducer` calls `FormReducer.Settled` after `WriteSucceeded`, `WriteFailed` and `WriteVerified`: when the operation behind a form has ended, success closes the form; a definite failure unlocks it with `WriteError.FieldErrors` mapped to the fields by id and the failure text on the top line (not when every message found its field); a still-running verification changes nothing.
- `Esc` on a form with changes asks `y`/`n` inline (`DiscardPending`); closing while saving detaches the form, the operation goes on and its result reaches the status line. Closing a tab drops its form (a draft). A form whose issue is deleted elsewhere shows `GCM-3 not found or no access` on submit (the write answers `NotFound`).
- `AssignFormTarget(Key, Current)` is the people picker (#164): a form with one `User` field (the assignee), opened at once with no metadata load (the form is built in the reducer). It has no search path of its own: typing opens the suggestion popup, whose `SearchSuggestionsEffect` (kind `AssignableUsers`) and `SuggestionHandler` are the only lookup of the form (#214). `Backspace` on an empty buffer clears the value (unassigned). The target's `Request` builds `AssignRequest` from the label that `FieldChange.Display` carries. `<space>im` skips the form (`FormOpener.AssignMe`).
- `EditRequest(Key, Changes)` is the edit write: `OperationKind.EditFields`, optimistic for the fields a row shows (summary, labels, priority: `EditRowChange`; the priority is patched by the name in `FieldChange.Display`), and Jira applies all of it or none, so one shown field proves a lost write. The handler turns the changes into typed `FieldUpdate`s (`FieldUpdates`); labels and multiple choices are written as adds and removes against the value the form was opened with (`FieldChange.Initial`), so a label someone else added meanwhile is not removed by a replace; a value that does not read there is a definite validation failure, never a lost reply.
- Create (#162, `CreateFormTarget`, `CreateFormReducer`, `CreateRequest`): `<space>ic` / `<space>iC` / `:create [subtask]` take the project from the issue shown or selected (the form has no project of its own; with nothing selected the status line says so). A selected epic (hierarchy level above 0) becomes the parent of a new non-sub-task, `iC` makes the selected issue the required parent of a sub-task and refuses a sub-task or an epic. The form opens on the type picker (`FormState.TypeChoices`: the project's create issue types, sub-task types only for `iC` and none for `ic`; the first load asks for types, `Enter` loads the fields of the chosen one). The fields are the create metadata (`FormFieldMapper.FromCreate`), the parent field starts with the key and is changed through the suggestion popup (#214, the only search path); a type that requires a parent without one is refused with a hint. `CreateRequest` has no key and is not optimistic: `WriteReducer` finishes it in `CompleteCreation` (caches dropped, origin tab reloaded, the parent's detail reloaded, the new issue opened when `OpenAfter` is on) from `WriteSucceeded.CreatedKey`. The description goes through the Markdown-like writer (#161) as ADF. A lost reply is verified by one search (`reporter = currentUser() AND created >= -Nm` in the project, same type and summary; N is the minutes since the submit rounded up, so an identical twin created in the same minute can still match): found is a success, not found stays undecided and says it may or may not have been created, never repeating the create.

**Comment editor (built, #167).** The first form kind, built narrower than the general design above: the editor is modal (Insert mode takes the whole keyboard), so its state is one `AppState.Editor` (`CommentEditor`: tab, key, comment id, `TextBuffer`, original text, warning, error, operation id), not a per-tab form; a draft is not kept across tabs. The text is a `TextBuffer` (`Core/Editing`: text, cursor at a grapheme start, edits as pure methods; `EditorLayout` wraps rows by character and maps cursor and rows, shared by the reducer and the renderer). The Markdown-like text becomes ADF in the reducer (`AdfMarkdownParser.Parse` is pure); the discard question and the delete question reuse the string-action `ConfirmRequest` (`comment.discard`, `comment.delete-confirmed` with the comment id as target). The three requests (`Core/Writes/Comments`) derive from `CommentRequest`: `ChangesRows` is false, so `WriteReducer` skips the row patch, the stale mark, the cache invalidation and the issue reload, and `WriteHandler` neither reads the search nor patches rows; it sends the write through `CommentWriter` (App) and posts `WriteSucceeded.Comment` (the stored comment), which `CommentEditing.Settled` applies to the editor and to the comment list of every tab showing the issue. A lost reply is verified by `CommentWriter.VerifyAsync` reading the comment pages (direct read, up to 1 000 comments; an incomplete read proves nothing) and answers `WriteVerified` with the comment found. `Settled` runs after every write command; it changes nothing for other writes.

### Suggestion popup

Built in #214 (`Core/Suggestions`, `FormReducer.Suggestions.cs`, `SuggestionHandler` in App, the popup rows in `FormOverlay`). One state, `SuggestionState`, hangs on `FormState.Suggest` (null when closed) and belongs to the focused field; the editor of the next issue (`@`/`#` in text) reuses `SuggestionPopup`, `SuggestionRanker` and the handler with another host state.

- Opens when a typed or pasted character leaves text in the typing buffer (`FormField.Entry`) of a labels, user or parent field with a source: labels (`SuggestionKind.Labels`, known labels from the tab's rows), the assignee field (assignable users of the issue), any other user field (people who can see the issue), the parent (issue picker). In a create form there is no issue, so the sources are scoped to the project (#342): the assignee searches `AssignableUsers`, other user fields `ProjectUsers`, a components or versions field (`FormField.Lookup`, `SuggestionKind.Components`/`Versions`) the project's list once a filter is typed (an empty filter lists its allowed values locally). Closes on `Esc` (on a choice field `Esc` clears the typed filter and the local list returns), on accepting a row, when the buffer empties or the focus leaves the field.
- Each query change is a pure step (`SuggestionPopup.Queried`): the rows are matched at once by `SuggestionRanker` (fuzzy, local, over the pool of everything loaded for the field) and the step emits `SearchSuggestionsEffect` with a fresh request id (`AppState.Sequence`). Replies (`SuggestionsLoaded`, `SuggestionsSlow`, `SuggestionsFailed`) are applied only to the popup that waits for that request id and still has the focus (stale-reply rule of the write pipeline). People and issues keep Jira's order; labels are re-ranked locally with the site's labels merged into the pool.
- The debounce is not read by the reducer: `SuggestionHandler` waits `SearchSuggestionsEffect.Debounce` (250 ms) on an injected `TimeProvider`, then runs the lookup under the tab's scope; a newer effect or `CancelSuggestionsEffect` cancels it, also while it waits. If the call lasts 150 ms the handler reports `SuggestionsSlow` before the answer. Reads only; the site label list (up to five pages) is kept for 2 minutes per connection generation in `SiteLabelCache` and shared by an in-flight read, so typing a label reads the site once (#292).
- Accepting a row goes through `FormEditor.Choose`: a label joins the chosen labels, a person or issue becomes the single value (id) and its display text is kept as a `FieldOption` so the form shows a name. The write conversion for `User` and `Parent` already existed in `FieldUpdates`.

### Other tabs showing the same issue

A write on GCM-3 in tab A changes tab B (a JQL list holding GCM-3), tab C (a hidden board holding it) and any issue detail of GCM-3 on any stack:

1. At start (optimistic kinds): every tab's row for the key is patched, hidden tabs too (a reference swap; hidden tabs do no network). No two tabs disagree.
2. At success: the row is replaced by key in every tab from the server rows. A list or filter tab whose JQL no longer matches the issue (status changed out of `status = "To Do"`) keeps the row until its next reload, marked stale; it is not removed locally, because the app does not evaluate JQL. All tabs holding the key get `IsStale`, cleared by their next reload; the active tab is reloaded at once only for rank, create and delete.
3. Detail: a `DetailState` for the key in any tab's stack is marked `IssueStale` and reloaded when it is the shown one (immediately if its tab is active, on activation otherwise); comments are reloaded after a comment write.
4. Cache: `InvalidateCacheEffect` drops `GetIssue(key)` and, as `docs/jira-layer.md` ("Cache keys") says, every view entry of the profile (the app cannot tell which cached first pages contain the issue). The disk files go with the next debounced write.
5. Failure: the rollback runs over the same set of tabs.
6. Writes made by others (Jira's web, a colleague) arrive only through the normal refresh; nothing here polls for them.

### Big data and the row bound

The 10 000 rows per tab and 50 000 across tabs stay. The lesson of Gitunia is to keep large things (diffs) out of state; rows here are small immutable summaries (about 500 bytes) shared by reference, and the pipeline adds nothing large: operations hold keys, a `RowChange` list and a request; forms hold bounded text; ADF documents of comments and descriptions stay in `DetailState` as today. Writes never need the whole row list: they find rows by key (O(n) per tab; if the first implementing issue measures it as a problem, `TabState` gains a key-to-index map built lazily).

Scrum's backlog (M5) changes nothing for M2. A backlog is a board source walked to the end, so it counts against the same cap; a backlog above 10 000 issues is `Truncated` like any tab. If M5 measures real backlogs beyond that, the answer is loading the backlog per sprint section on demand, outside `TabState` in a host-owned store like `SiteCache`, not raising the cap. Roadmap open question 5 records this.

### Worked example: move a card to another column

Board tab A (GCM, Kanban) is active; tab B is a JQL list `project = GCM` with GCM-3 in it; tab C is a hidden board of the same project. GCM-3 is `To Do`; the user moves it to `In Progress`.

1. `Alt-l` (#159) -> `KeyPressed` -> `TransitionForms.MoveCard` finds the next column in `BoardConfiguration` (`In Progress`, its status ids) and opens an invisible `TransitionPickTarget` form; `LoadFormMetadataEffect` reads `GET /issue/GCM-3/transitions?expand=transitions.fields`; the reply refines the target, and when exactly one transition ends in the column and it needs no fields, `FormReducer` sends `WriteRequested(A, TransitionRequest("GCM-3", choice, no fields))` at once (the card therefore moves after one read, not at the key press; the read is what finds the transition id).
2. `WriteReducer`: no operation holds `GCM-3`, so it draws `OperationId` 41 from `Sequence`, appends `Operation(41, Transition, A, [GCM-3], Resolving, Undo: [Status To Do -> In Progress])` and patches the row in tabs A, B and C. Returns `ExecuteWriteEffect(41, request)`. First paint: the card is already in the new column with a `…` marker, status line `Moving GCM-3 to In Progress`. A second move of GCM-3 now is refused (`GCM-3 is busy`). A `Tick` at this moment starts no refresh anywhere.
3. `WriteHandler` (App, site scope) posts `POST .../transitions {"transition":{"id":"31"}}` on the user lane with the id chosen in step 1 (ids are per project, never stored; `docs/jira-layer.md`, "Transitions"). The transitions were read before the write, so a transition that needs fields never starts an operation: the picker shows (or opens the fields form) instead, and when none leads to the column the picker lists them all with a label that says so.
4. 204. The handler reads `key in (GCM-3)` (one call) and posts `WriteSucceeded(41, At, rows)`. The reducer replaces GCM-3 in A, B and C with the server row (status, and anything a post function changed, such as the assignee), removes operation 41, marks B and C `IsStale`, drops the `…` marker, emits `InvalidateCacheEffect(GCM-3)` and sets `Moved GCM-3 to In Progress`. If `Operations` is now empty and a refresh was queued, A reloads now; B and C refresh on their schedule (C on activation).
5. Failure instead. (a) 403 -> `WriteFailed(41, NoPermission)` -> the card returns to `To Do` in A, B and C (each `RowChange` undone because the field still equals `In Progress`), status line `No permission to transition GCM-3: <Jira text>`. (b) Timeout after the POST -> `Verifying`, `VerifyWriteEffect` re-reads GCM-3: `In Progress` -> the success path; `To Do` -> rollback with `It was not applied`; the read also fails -> rollback, rows stale, `Not sure the move worked; reload to check`.
6. If the user closed tab A during step 4, nothing is lost: operation 41 finishes, B and C are updated, the active tab shows the status line.

## Input routing

Every way into the app ends in one action: a key resolves against the keymap to an action id, a mouse gesture comes as an `ActionRequested` (or `PointerPlaced` with the action that came with it), and a palette entry runs the same action id. All of them end in `AppReducer.Apply` (`Cancel` goes back through the `Esc` key path, which is the same handler), so the same action runs the same handler whatever the input. Only keys need an ordering, because a key can mean different things depending on what is open. `InputRouting` (`Core/State`) holds that order; `AppReducer.ReduceKey` switches on its answer (`KeyRouteKind`). The first layer that takes the key wins:

1. Suggestion popup of the comment editor (move, accept, close), only for the keys it uses.
2. An open field form (create, edit, link, profile add): it takes every key.
2a. Reserved key: `Ctrl-c` (not in Insert mode, where it cancels the edit) is `app.quit` whatever the keymap says (`ReservedKeys`), so a user file cannot lock the user in.
2b. Help filter line: while the help overlay's `/` filter is being typed it takes every key (the reserved `Ctrl-c` and any other key that resolves to `app.quit` are never text).
3. Count digit (`1`-`9`, then `0`), Normal mode with no half-typed chord only.
4. Chord prefix (`g`, `<space>`): the key is held in `PendingKeys`, nothing runs.
5. Back out: `Esc` in Normal mode with no chord or count typed and no notice pops the issue stack.
6. Dismiss: `Esc` in Normal mode with a notice showing ends the notice (nothing is popped in the same press).
7. Action: the key completes a binding of the current mode (overlays have their own modes, so an open overlay or prompt owns its keys and nothing falls through to the body).
8. Text: no binding. Insert and Command mode type it (so text never fires chords or `q`); other modes ignore it.

`InputRoutingTests` has a test per rule (the back-out and field-form cases sit in `IssueDetailReducerTests` and `FormOpenerTests`, where those states are built). A new overlay or editor is a mode (or a layer above) in this list, never a check added inside a body action.

## Cross-platform

Linux is built and tested first, then Windows, macOS last. Rules:

- Platform-specific code lives only in `Geeratya.Platform`; each such feature has a branch for every supported OS or an explicit unsupported path.
- Directories: Linux and macOS follow XDG (`XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, falling back to `~/.config`, `~/.local/state`, `~/.cache`; a relative XDG value is ignored; with no absolute XDG value and no absolute home, e.g. `HOME` unset, `ApplicationDirectories` throws `InvalidOperationException` naming `HOME` rather than yield relative paths), each with a `geeratya` folder. Windows uses `%APPDATA%\Geeratya` for configuration and `%LOCALAPPDATA%\Geeratya\State` and `\Cache` for the rest. `ApplicationDirectories` computes them from an `OperatingSystemKind`, an `EnvironmentReader` and `PlatformFolders`, so tests cover all three systems on any host.
- Console capabilities (`ConsoleCapabilities.Detect(environment, inputRedirected, outputRedirected, operatingSystem)`, tested with an injected environment on every `OperatingSystemKind`): colour tier from `NO_COLOR`, `TERM` and `COLORTERM` (Windows Terminal, which sets `WT_SESSION` but not `COLORTERM`, counts as 24-bit); glyph set from `TERM=dumb`, the locale and the classic-console rule; redirected input or output means non-interactive. Classic consoles get the ASCII glyph set and at most 16 colours. Linux: `TERM=linux`, `ansi`, `cons25`. On every system `TERM=vt52`/`vt100`/`vt220` (`vt` plus a digit, never `vte*`) means ASCII and no colour. Windows: the console host, recognised by none of `WT_SESSION`, `TERM`, `TERM_PROGRAM`, `COLORTERM`, `ConEmuANSI`, `ANSICON` being set (so VS Code, mintty, ConEmu and Git Bash are not classic). macOS: no classic console exists, so only the locale rule applies. Windows is covered by unit tests only, not run on a real console host.
- Terminal background (#375): `TerminalBackgroundDetector(environment, isInteractive, operatingSystem, query)` answers light, dark or unknown for the `auto` theme: OSC 11 through `ITerminalBackgroundQuery` (real one: `ConsoleBackgroundQuery`, reads with `TerminalAnswerReader`; skip rules and the Windows "unsupported" branch are in `docs/ux.md`), then `COLORFGBG`. `ShellHost` calls it before `Application.Init`, whatever theme is saved.
- Environment access goes through `EnvironmentReader` with an injected lookup; no direct `Environment.GetEnvironmentVariable` elsewhere.
- Secrets (`Platform/Secrets`): `ISecretStore` per system, picked by `SecretStores.Create`. Linux runs `secret-tool` (libsecret) with the token on standard input, Windows calls Credential Manager (advapi32 `LibraryImport`), macOS runs `security -i` (Keychain: the `add-generic-password` command with the token goes on standard input, reads use `find-generic-password -w`; written without a Mac to test on, accepted by the owner who checks it on a Mac: `delete-generic-password` removes, exit 44 means not found; `SetAsync` reads the value back because `security -i` may exit 0 after a failed command; the quoting, `"` and `\\` escaped and control characters refused, is assumed from the `security` man page, #29, #202), `UnsupportedSecretStore` remains for unknown systems; on Linux without `secret-tool` (or macOS without `security`), the store flips `IsAvailable` to false at first use; `TokenProvider` then falls back to `GEERATYA_TOKEN`. Profiles (site, email, no token) are `profiles.json` in the config directory, owned by `Core/Profiles`; the token is looked up by `Profile.CredentialKey`; `GEERATYA_TOKEN` is one value, used only while exactly one profile exists. Core never sees a token or the store.
- Board kinds (`Core/BoardKinds`, #319): the Scrum/Kanban probe answers of a `simple` board, per profile, in `<state dir>/<hash of the credential key>/board-kinds.json` (board id to `scrum`/`kanban`; same folder, permissions and atomic write as the history). `SiteConnections` builds one `BoardKindResolver` per connection, seeds it from the file and saves each newly probed answer; `JiraServices.BoardKinds` hands it out. A failed probe is never stored; a write failure is ignored (one more probe next run). Removing a profile deletes the file (and a stray `.tmp`); saves for a removed profile are ignored until its connection loads the store again, and a failed write removes its temp file. Answers are never expired: if a board changes kind, delete the file.
- History (`Core/History`, #193): the last 50 JQL strings and 50 issue keys per profile, newest first, de-duplicated (queries as typed, keys upper-cased), in `<state dir>/<hash of the credential key>/history.json` (same hash as the cache folder, user-only permissions, written through a temp file). It holds only what the user typed or opened, never a token. Loaded lazily when the picker opens (`LoadHistoryEffect`), kept in `SourceLists.History` of the session (dropped with it on a profile switch), recorded by `RecordHistoryEffect` when a JQL view or an issue detail opens; the host updates the file under one lock and answers with the stored value. Removing a profile deletes its history. Recent issue keys are stored for the quick jump (M4); nothing offers them yet.
- Saved views (`Core/SavedViews`, #191): the user's named source-plus-layout pairs per profile, in `<state dir>/<hash of the credential key>/saved-views.json` (same folder, user-only permissions and atomic write as the history; no token, site or rows). `SavedViewStore` reads lazily through `LoadSavedViewsEffect` when the picker opens; replies carry a `SavedViewsVersion` so a late one is dropped; an unreadable file is never overwritten (the update fails with a status message) and a corrupt one is kept as `saved-views.json.bad`; the file is removed with the profile.
- Open in browser (`Platform/Browser`): `IBrowserLauncher` via `BrowserLaunchers.Create`, `ProcessBrowserLauncher` runs `xdg-open` (Linux), `open` (macOS) or `rundll32 url.dll,FileProtocolHandler` (Windows, chosen over `cmd /c start` because cmd parses `&` in URLs) through `IProcessRunner` with the URL as one list argument; a missing opener gives "no browser opener found: copy the URL". Core checks links first (`BrowserUrlCheck`: https only, no control characters, no user info, active site host unless a remote link) and the reducer emits `OpenUrlEffect`; the launcher refuses non-http(s) again. `BrowserEffectHandler` in Tui answers with `UrlOpenFinished`.
- Paths use `Path` APIs only: no hardcoded separators, `/dev/null` or `/tmp`.

## Terminal.Gui

`Geeratya.Tui` references Terminal.Gui 2.5.0 (stable v2, pinned in `Directory.Packages.props`). The native AOT publish has no `IL*` warnings with it and no suppressions are needed.

Layout in `Geeratya.Tui`: `Input/` (`KeyTranslator`: Terminal.Gui `Key` to the renderer-agnostic spelling of `KeyNotation`; `MouseFlagTranslator`: toolkit mouse flags to a `MouseGesture`), `Rendering/` (pure: `FrameBuilder`, `IBodyRenderer` screens, `StatusBar`, `PaletteTable` (roles from a theme's colours), `Palette`, `TextWidth`, and `Themes/`: `Theme`, `ThemeFileParser`, `BuiltInThemes` (JSON files embedded in the binary, read without reflection) and `ThemeCatalog` (user files in the `themes` folder); no Terminal.Gui), `Views/` (`ShellScreen`, the only code that builds views, and `StyledBodyView`, which draws the frame's styled lines span by span in palette colours and redraws it on resize), `ShellHost` (loop, keys to `AppReducer`, state to `ShellScreen.Render`). Core knows no Terminal.Gui types and no themes: `:theme` is an `ApplyThemeEffect` that `ShellHost` answers with `ThemeApplied` (and Core then saves the name in the settings). The mouse is the same path as keys: `Geeratya.Core.Mouse` (`MouseHitTester`, `DefaultMouseMap`, `MouseResolver`) turns a cell and gesture into an `ActionRequested` command that the reducer runs like the key's action (`docs/ux-mouse.md`). Screens draw their body as one frame (`ux-look.md`, section 2): `FrameGrid` (pane rectangles to border glyphs with plain junctions and rounded outer corners, edge chips), `PaneFrame` (the one-column screens) and the issue detail's shared panel edges (`Core/Detail/Panel`); a body below 20 columns or 5 rows is drawn without a frame. `FrameBuilder` composes a header region (one row, always the tab bar, blank without tabs), a body from the first `IBodyRenderer` whose `AppliesTo(state)` is true (screens register without editing each other; start and help are built in) and the status bar; `--print-frame` prints the same lines with styles dropped. The bars are styled lines on the bar background (`ux-look.md`, section 5): `TabBar` (Core) builds the tab row from `TextRole.TabActive`, `TabDim`, `BarText` and `BarMuted` chips, and `StatusBar.RenderStyled` builds the status bar (badge chip, message in its `Bar*` severity role, hint chips); both are drawn by `StyledBodyView` like the body, so the shell has no plain-text label for the status. Key hints are `HintChip`s (key from the keymap, short label) drawn by `HintBar` (key `TextRole.BarKey`, label `BarMuted`, two spaces between); a hint row does not build those segments by hand. The ASCII glyph set turns the padding cells of chip roles into brackets in `FrameBuilder`, so widths and mouse cells do not change.

Settings and pitfalls:

- Use the instance API: `Application.Create()`, `application.Init()`, `application.Run(window)`; no static `Application.Init`.
- Keys are read from `application.Keyboard.KeyDown` and marked `Handled`, so no view or default binding sees them. The default app key bindings (`Esc` quits) are cleared at start, otherwise `Esc` would quit; quitting is the keymap's decision.
- Letters arrive as upper-case key codes; without `Shift` they are lower-case characters. `KeyTranslator` handles this (tested). A terminal sends `Esc` immediately followed by a key as `Alt-<key>`, as in any terminal program.
- Non-interactive stdin or stdout (pipes, `TERM=dumb`) never starts Terminal.Gui: the binary prints a one-line explanation and exits 1. `--help`/`-h` (usage, exit 0), `--version` and `--print-keymap-doc` work everywhere; an unknown argument prints its name and the usage on stderr and exits 2. `ApplicationRunner.Usage` is the single usage text; docs list options by quoting it, not by restating it.

`settings.json` (config directory, `Core/Settings`, `SettingsStore`) holds the user's switches. `SettingsRegistry` is the one list of them (name, file key, type, default, help); the reader (`SettingsStore.Read`), the writer, `:set` and the table in `docs/settings.md` all use it. The file is JSON with comments and trailing commas; `SaveSettingsEffect` makes `SettingsStore.Write` replace only the changed value (`SettingsText`), so comments and unknown keys stay, and a file that does not parse or changed on disk since it was read is not written (`docs/settings.md`). A missing or unparsable file means the defaults; an invalid value reads as its default with a warning in the Messages history (and on the status line).

## Design details (moved from `decisions.md`)

- **Write pipeline (#151, #154).** Running operations live in `SiteSession.Operations` (site level, origin tab stamped), so exclusion sees every tab and a tab close does not forget a sent write. A busy issue refuses a second write; row-visible changes are optimistic with per-field rollback; writes are never retried and a lost reply is verified by re-reading. Writes run through `NetworkRunner.StartDetached` (no scope dictionary): operation ids never repeat, so keyed scopes would pile up, and a tab close must not cancel a write. Read-back rows are used only if they show the change (`WriteRequest.IsShownBy`), because the search index can lag and a stale row would undo the optimistic one. Gitunia's M7 retrofit of the same rules is the source.
- **`JiraTransport`.** One per `JiraConnection`; clients take only the transport and no call takes a connection argument, so the token and `HttpClient` live in one place and a profile switch replaces the transport. It requires https (http only for loopback) and never follows redirects, so credentials cannot leak to another host.
- **`BrowserUrlCheck` (#118).** The single gate in Core before anything reaches the system browser: https only (stricter than http/https), no control characters, no user info; remote links may point at any host and `RemoteLinkMapper` keeps any scheme so the gate decides. UI and ADF link callers must go through `OpenUrlRequested`; only the issue-key path is wired so far.
