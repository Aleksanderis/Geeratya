# UX: workflows

The flows of Milestone 1 (read your board), step by step. Screens and their states are in [ux-screens.md](ux-screens.md), keys in [keymap.md](keymap.md). Keys are spelled as in `ux-keymap.md`. All flows are read-only; writes arrive with M2. Every network step is asynchronous: the frame is drawn first and the result fills in later.

## 0. Start, connection check, first view

1. The shell draws its first frame before any network reply: tab bar, empty body with the hint line, status bar.
2. With an active profile the status line shows `Checking <host>…` and the body stays as it is (cached views are shown with the `STALE` banner once the cache issue stores them). Without a profile the profile manager is the first screen.
3. The check is `GET /myself`. Success: `Connected as <name>` on the start and profile screens (the status line stays silent, #646). 401: the banner explains the token was rejected (screens, "Errors"). Network failure: `OFFLINE`, cached views stay usable.
4. After the first frame the shell reads the active profile's remembered tabs (`tabs.json`, definitions only). Remembered tabs reopen as they were (source, layout, name, quick filters, swimlane and lane, the active tab); only the active one loads at once, the others when first shown, each from the disk cache with the `STALE` banner until the refresh arrives. A tab whose board or filter is gone (404) is dropped with a status note. With nothing remembered (first start, or all tabs closed) the board picker opens once the connection check succeeds, or the board itself when the site has exactly one; the empty start screen only shows without a profile, while offline, or when the picker was dismissed. `:set startup.restore off` skips the file and always starts on the board picker. Switching profile reads that profile's tabs.
5. A start target on the command line (`geeratya GEN-123`, `--board <name>`, `--backlog <name>`, `--jql <query>`, `--filter <name>`; one at most, `--profile <name>` picks the saved profile for this run for this run only (editing profiles in the manager in the same run may save it as active)) opens one tab with the same commands as the palette (`:board`, `:jql` and so on; an issue key opens `key = KEY` with the issue on top) once the remembered tabs are read and on top of them, or alone (no board picker) when nothing is remembered or `startup.restore` is off. It starts after the first frame, so no network reply is awaited. A board or filter name that matches nothing (or several) leaves the picker open with that notice. An unknown `--profile` shows a warning in the status line and opens nothing.

## 1. Open a view

By picker: `<space>t` (or `Ctrl-t`, or `:tab new`), type to filter, `Up`/`Down`, `Ctrl-p`/`Ctrl-n` or `Ctrl-j`/`Ctrl-k` to choose, `Enter` opens it in a new tab, `Esc` closes. The picker also lists the latest 10 recent JQL queries of the profile (group `Recent`, filtered by the typed text) before the typed query row. By palette: `:jql <query>`, `:filter [name]`, `:board [name]`, `:backlog [name]`, which open a new tab too. A new tab becomes active at once and shows `Loading…` (or its cache); a failure shows the error body in that tab only, other tabs are untouched.

A board opens in Columns, everything else in List. `<space>l` switches a board between Columns and List.

## 2. Browse a list

`j`/`k` move, `Ctrl-d`/`Ctrl-u` half pages, `g g`/`G` top and bottom. Reaching the end of the loaded rows loads the next page. `Enter` opens the issue (workflow 4). `<space>o` opens the selected issue in the browser. `<space>r` refreshes: rows stay, the selection is kept by key.

## 3. Browse a board

`h`/`l` change column, `0`/`$` jump to the first and last, `j`/`k` move between cards. Columns that do not fit scroll horizontally with the selection. `Enter` opens the selected card. `Alt-l` / `Alt-h` move the selected card to the next or previous column (workflow 10); `<space>l` shows the same issues as a list.

## 4. Open an issue, follow links, go back

1. `Enter` on a row or card pushes the issue onto the tab's stack. The cached copy shows at once, the fresh one replaces it.
2. `j`/`k` move the cursor (`>`) line by line through the document, skipping the panel edges, and the window follows it; `] ]` and `[ [` jump to the start of the next section, or of the current one and then the previous (nothing moves at either end).
3. `Enter` on a sub-task, epic child or linked issue pushes that issue (so a chain of issues is a deeper stack); on a remote link or attachment it opens the browser (the issue page for an attachment, the link's URL for a remote link; only `https` URLs, anything else is refused with a note in the status line).
4. `<space>p` pushes the parent (a status note when there is none); `<space>o` opens the cursor row in the browser (remote link, attachment or related issue) and the shown issue from any other line.
5. `Esc` pops one level. After the last pop the view is back with its selection and scroll as they were. `Esc` at the view does nothing (`q` quits, as everywhere).
6. Switching tab keeps each tab's stack; closing a tab drops its stack.

## 5. Tabs

`Tab`/`Shift-Tab` (or `g t`/`g T`) next and previous, wrapping around; `Alt-1` to `Alt-9` go to a tab by number (a missing number does nothing); `<space>c` closes (the right neighbour becomes active); `<space>t` opens a new one. State (view, layout, selection, scroll, issue stack) is per tab. The tabs of the active profile are saved as they change (see workflow 0).

## 6. Refresh, offline, rate limits

- `<space>r` reloads the active tab (or the open issue). Background refresh uses the same path and shows `STALE` only when it fails or the data is older than the refresh interval.
- Offline: the cached data stays, the banner shows the age of the data and the next retry (exponential back-off, 60 s doubling to 300 s, `architecture.md`); `<space>r` retries at once. A reply ends the state. An offline start shows the cached rows marked stale, or without a cache the error body.
- Rate limited: the banner counts the `Retry-After` seconds down; requests wait, nothing is dropped, and the keys keep working on the data already shown.
- A reply that is a 401 stops all automatic retries for the profile until the token is replaced (a repeating wrong token would lock the account); the banner stays.

## 7. Switch profile with views open

`:profile switch <name>` replaces the connection; every tab, stack and cache of the old profile is dropped (`ux.md` "Profiles"). The new profile starts with no tabs, and the check line runs again. A reply that arrives for the old profile is ignored.

Add, edit and remove profiles: the profile list (`:profile list`, or `:profile` with a profile saved) is the manager. `Ctrl-a` adds, `Ctrl-e` edits the highlighted profile, `Ctrl-x` removes it after a confirm that names what is deleted (the profile entry and its stored token; Jira data is untouched and Jira cannot undo anything here). The form tests the connection on demand (`Alt-t`) and an edit never asks for the token again unless it should change (`ux.md`, "Profiles"). First run: with no profile the manager screen opens at start (empty list, `Ctrl-a` adds one); `:profile` with no profile opens it too, and `:profile add` opens the form directly. The manager stays open under the form and under the remove question and shows the new list after a save.

## 8. Write something (M2)

Design in `architecture.md`, "Write pipeline". What the user sees:

- A change that a row shows (move a card, rank, assignee, a field) appears at once with a `…` marker and a status line saying what is being done; it settles when Jira answers. On failure the row goes back and the status line says why and what was not done (no permission, not found, rate limited with the wait, Jira's own text for a refused transition).
- Rank (#169, `Alt-j`/`Alt-k`, `<space>kt`/`kb`/`kk`): works in a board or backlog view (a JQL or filter list is ordered by its query, not by rank, and refuses). The issue under the cursor moves next to a neighbour the view shows: the next row, or in the columns layout the next card of its column (a card with sub-tasks shown under it moves with them). The row moves at once and carries the `…` marker until Jira answers; `Alt-j` on the last row says `already at the bottom`. In the columns layout, cards of other columns that lie between the two in the board order are named in the status line (`Ranking GCM-1 below GCM-4 (2 cards of other columns lie between)`). Rank cannot be read back from one issue, so a lost reply is not resolved to done or not done: the order goes back, the status line says to reload, and the view reloads. After a rank the view reloads (the server order is the truth). `<space>kk` picks up the issue, then drops it where the cursor stands. With marks or a Visual range `Alt-j`/`Alt-k` move the whole set as one block (#428, `docs/ux-keymap.md`, "Which writes accept a set").
- Creating, deleting and commenting wait for the reply; the form shows `Saving…` and stays open on an error, with each field's message at the field. Comments (built, #167): `<space>m a` opens the editor in the issue detail, `Ctrl-s` sends, `Esc` asks before throwing text away; `<space>m e` edits and `<space>m d` deletes (after a `y`/`n` that says Jira cannot undo it) the comment under the cursor; the comment list changes from the reply (`ux-screens.md`, "Comment editor").
- A second write on an issue that is still being written is refused (`GCM-3 is busy`), not queued. Other issues are free. Refresh waits until the writes end; `<space>r` is remembered and runs after.
- If the answer is lost (timeout, network), the app says it is checking, re-reads the issue and then shows the true state; it never repeats a write by itself.
- Delete, bulk changes and assignee or sprint changes for several issues ask first (`y`/`n`/`Esc`): the text names what changes and says Jira cannot undo it.
- Delete (#165, #316): the confirm counts the visible sub-tasks and, when there are any, adds `(and any hidden from you)`, because the delete is sent with `deleteSubtasks=true`, which removes sub-tasks the user cannot browse too, and Jira gives no count of them. An issue with no visible sub-tasks is sent with `deleteSubtasks=false` and Jira refuses it if hidden ones exist. Jira answers `404` alike for a deleted issue and for one the user cannot see, so when the delete reply is lost and the check reads `404`, the status line says `probably deleted, or hidden from you` and the row goes.
- The same issue in other tabs changes too; a list tab whose query no longer matches keeps the row, marked stale, until its next reload.
- Closing a tab does not stop a write that was sent; quitting or switching profile with writes running asks first.

## 9. Edit with the field form

The edit form (`<space>ie`, or `:edit`, `:priority`, `:labels` for one field) and the people picker (`<space>ia`); transition and create open the same form (`ux-screens.md`, "Field form overlay").

1. `<space>ie` (or `:labels`) on a selected row (or the shown issue) opens the form at once with `Loading fields…`; the metadata (`editmeta`) is fetched, never at startup. A failure shows on the top line and `Esc` closes the form.
   After editmeta the form reads the issue once with exactly the ids of the other editable fields (due date, components, versions, custom fields such as a number estimate) so each starts with its current value: date text, the chosen options or the rich text. A user or parent field is not offered yet; if the read fails only the fields the view already holds are offered.
2. The labels field starts with the issue's current labels. Type a label and press `Space` to add it as typed, or `Enter` to take the highlighted suggestion (an exact match ranks first); `Backspace` on an empty buffer removes the last one. `Ctrl-s` saves (also from any field). With several editable fields the form opens in the navigate state (`j`/`k`/`Tab` move field to field, `Enter`, `i` or a click edits, `Enter` or `Esc` stops editing; #650), where `Enter` never saves; a form with one editable field is always editing and `Enter` on the empty buffer saves.
3. The row shows the new labels at once. If Jira refuses, the row goes back and the form stays open with the message at the field. If the answer is lost, the form stays locked while the issue is checked, as in workflow 8.
4. Typing in a labels, person or parent field opens the suggestion list under it (`ux-screens.md`, "Field form overlay"): `Down`/`Up` or `Ctrl-n`/`Ctrl-p` choose, `Tab` or `Enter` accept the highlighted row (the label is added, the person or issue becomes the value), `Esc` closes the list only. `Space` adds the typed label as it is; so does `Enter` on the `(new)` row. The comment editor has the same list for `@` and `#` (`ux-screens.md`, "Comment editor").
5. While editing, `Esc` goes back to navigating; `Esc` there (or in a one-field form) with changes asks `y`/`n`, without changes it closes. Closing while the save runs leaves the write running and its result goes to the status line.
6. Summary, labels and priority change the row at once (priority by its name, as the allowed value is called); the other fields are verified when the issue is read again. Jira has no optimistic locking on edits (last write wins, a concurrent change is not reported), so a summary edit from a stale row overwrites the newer text; the row is read again after every write, which shows the true state. Only if Jira does answer a conflict, the row goes back, the form says so and the issue is read again.

Estimate (#183, `:estimate`): the same form limited to the one number field the issue's own edit metadata offers: the estimation field of the board the tab shows (the form does not open when the issue's screen lacks it), or on a tab without a board (JQL, filter) the first editable estimate field of the site and of the boards seen (#443; story points: the board's estimation field, e.g. `customfield_10047` on the company-managed and `customfield_10016` on the team-managed Scrum sample). An empty value clears the estimate, text that is not a number is refused at the field, and the row and detail show the new value at once and go back if Jira refuses. When no estimate field is editable on the issue (a Kanban board, estimation by time tracking, an issue type whose screen lacks it) the form does not open and the top line says why. A board read from Jira without estimation (none or time tracking) also removes `:estimate` from the palette and the command says "the board has no story point estimation"; a board shown from the cache keeps no estimation, so nothing is hidden until its configuration loads. It works on the selected row of any list, board or backlog, and on the shown issue. Issue detail labels the value with the board's estimation field name ("Story Points") when the tab has a board configuration, otherwise "Estimate" (#439).

Assign: `<space>ia` opens the people picker (`ux-screens.md`), type a name, `Enter` takes the highlighted person and `Enter` again assigns (the row shows the person at once, `Backspace` on an empty field clears it). `<space>im` (or `:assign-me`) assigns the shown or selected issue to your own account without a picker; neither asks to confirm, a single assignment can be repeated.

## 10. Change status (M2)

Built in #159. Works from the list, the columns layout and the issue detail on the selected or shown issue.

1. `<space>is` (or `:status`) opens a picker with the transitions Jira offers for this issue now (`Loading fields…` while they are read; nothing is cached or stored, transition ids differ per project). Each entry is the target status, with the transition name when it differs (`Start progress → In Progress`). Typing filters, `Up`/`Down` choose, `Enter` picks, `Esc` closes.
2. A transition without fields is sent at once: the picker closes, the card shows the new status with the `…` marker and the status line says `Moving GCM-3 to In Progress`. A transition that asks for fields (a required field without a default, or a screen with fields) opens a second form with those fields, required ones first (taken from the same transitions read as the picker, so a move reads them once); `Ctrl-s` (or `Enter` on the last field) sends the transition with them, and Jira's message for a refused field shows at the field.
3. Columns layout: `Alt-l` / `Alt-h` (or `:status next` / `:status prev`, for terminals that send no Alt; plain `:status` is the picker) look up the transitions that end in the next or previous column. Exactly one: the card moves at once, no form shows, and the selection follows the card into its new column (the cursor is kept: only its column and card change, every column keeps its scroll; a rollback moves it back). Two or more: the picker lists only those. None: the picker lists every transition and its label says so. First or last column, a card in no board column, and the list layout answer with a status line note and send nothing. A column move is not offered from the issue detail.
4. A move that may fire workflow side effects asks first (`y`/`n`/`Esc`, text `Move GCM-3 to Done? Jira cannot undo this; the workflow may do more than change the status`): a transition to a status in the done category, or a screen with nothing to fill in. A transition with fields is not asked again: submitting its form is the confirmation. Declining sends nothing.
5. If Jira refuses (permission, a validator, a field) the card goes back and the status line says why; a lost reply is checked by reading the issue, as in workflow 8.

## 11. Link two issues, remove a link

Built in #190; both work on the selected row or the shown issue and the same way in company-managed and team-managed projects.

1. `<space>il` opens the field form (workflow 9) titled `Link GCM-3`, with `Loading fields…` while the link types are fetched (`GET /issueLinkType`, never at startup). The first field, `Link type`, lists each side of each type as its own choice (`blocks`, `is blocked by`, `clones`, ...; a type that reads the same both ways, `relates to`, is one choice), so type and direction are one pick, and the choice reads as "this issue <choice> the other". `Enter` picks and moves on; typing filters the list (the suggestion popup of selects, `ux-screens.md`).
2. The second field, `Issue`, finds the other issue as you type, by a word of its summary or by key (the suggestion popup, `Enter` or `Tab` takes the highlighted row; the issue itself is never offered). A full key typed by hand (`gcm-5`, lower case is accepted) is taken as it stands on `Enter` (`Tab` takes the highlighted row instead) or `Ctrl-s`; the search is Jira's issue picker. `Ctrl-s` saves. Text that is neither a picked row nor a full key is refused at the field (`Pick one from the list`), as is the issue itself; an issue Jira does not find or may not link comes back as the status line text and the form stays open.
3. The write is not optimistic (no row shows links). When Jira confirms, the form closes, the status line says `Linked GCM-3 blocks GCM-5`, and the open detail of either issue reloads. A lost reply is checked by reading the issue, as in workflow 8.
4. In the issue detail, put the cursor on a row of `Linked issues` and press `<space>iu`: Confirm mode asks `Remove the link GCM-3 blocks GCM-5? Jira cannot undo this.` and only `y` removes it (`n` or `Esc` leaves it). Anywhere else the key says `The cursor is not on a linked issue.`
5. Only one write per issue at a time (`GCM-5 is busy (assigning)`): a link touches both issues, so both must be free.

## 12. Create an issue

1. Select an issue (or open one): the project comes from it. `<space>ic` (or `:create`) creates an issue; if the selection is an epic it becomes the parent of the new issue. `<space>iC` (or `:create subtask`) creates a sub-task of the selected issue. With nothing selected the status line says where the project comes from; a sub-task or an epic cannot be the parent of a sub-task.
2. The box opens at once with `Loading fields…`, then lists the issue types the project allows (sub-task types only for `<space>iC`). `Down`/`Up` and `Enter` choose; `Esc` closes. The types come from the project, so company-managed and team-managed projects offer their own.
3. The form lists the fields of that type, required ones first (`*`); the summary is required. The description is Markdown-like text, `Enter` adds a line. Fields the form cannot edit are listed read-only with the project link; the parent starts as the selected issue and is changed through the suggestion popup, and the assignee uses it too (no Me/Unassigned rows there); with no issue yet the popup searches by the project key (people who can be assigned in it, issues of it). `Ctrl-g` turns "open after" on, then the new issue opens in the detail when it is created.
4. `Ctrl-s` (or `Enter` on the last field) creates. A missing required field is marked at the field and nothing is sent; a refusal by Jira (a parent that does not fit the type, a required custom field) stays open with the message at that field. `Esc` with changes asks `y`/`n`; nothing is created by cancelling.
5. On success the view reloads, the status line says `Created GCM-12` and the form closes. If the reply is lost the app searches for the issue and says whether it was created; if that cannot be told it says so and never creates it a second time. The form stays open and unlocked, so check the view before saving again.

## Design details (moved from `decisions.md`)

Detail behind short entries in `decisions.md`; the decision and its reason stay there.

- **Create (#162).** Project and parent come from the issue shown or selected, because a view has no project of its own. A selected epic is offered as the parent and dropped when the chosen type has no `parent` field. The type picker is part of the form (types first, then the fields of the chosen type), so cancel, loading and errors are the form's own. "Open after" is `Ctrl-g` in the form (off by default).
- **Assignee and edit form.** `<space>ia` is the field form with one person field; its search is the suggestion popup's. The edit form offers only fields whose current value the view holds (summary, labels, priority, an opened issue's description); a description that does not round-trip through the Markdown-like text is read-only with the browser link. Other editable fields (due date, components, versions, custom fields) get their value from one issue read with only those field ids, made when the form loads, right after editmeta (#283); it is not stored in the detail or its cache. If that read fails the form keeps the fields it already knows.
- **Comment writes (#167).** Add and edit wait for the reply (no optimistic text), the editor stays open on an error. They change no row, so the pipeline skips the row patch, the search read, the stale mark and the issue reload (`WriteRequest.ChangesRows`). Editing another author's comment is not refused up front (overrides `ux-keymap.md`): project administrators may edit all comments, so the editor warns and Jira's 403 decides. A lost reply is verified by reading the comments directly. `Ctrl-s` is the shared `form.submit` action, `Alt-Enter` a fallback where a terminal swallows `Ctrl-s`. The comment editor is `AppState.Editor`, separate from the per-tab `TabState.Form` (#158); it is modal and needs no metadata.
- **Write keys.** One `<space>` group per noun (`i` issue, `m` comment, `s` sprint, `k` rank, `v` view options), never a prefix of an M1 leaf; `Alt-h/j/k/l` move a card or row, `v` Visual, `Alt-m` marks; no bare letters. Only sprint moves and rank steps take a set; a count never selects.
- **Change status (#159).** A single transition confirms when its target is in the `done` category or its workflow shows a screen with no fields; every other single transition sends at once, and a transition with fields is confirmed by submitting its form. A column move reads the issue's transitions first (an invisible picker form), because only then are the transition id and the "exactly one leads there" test known; the card moves after that read.
- **Rank (`<space>kk`, #169).** First press remembers the issue (`TabState.RankPickup`), the second drops it at the card under the cursor: above it when the cursor is above the picked-up issue, else below. The right-click menu of a list row has the same entry (pick up, right-click the target, pick it again). In a Scrum backlog the drop target may be in another section: the issue then also takes that section's sprint (#182, `docs/ux-screens.md`). Rank keys carry no status bar hints until the write hints are designed together.
- **Link form (`<space>il`, #190).** Link type and side are one choice (`blocks`, `is blocked by`, ...; the field id carries type id, side and wording); the other issue is found by the suggestion popup (the `Issues` source, #305) or taken as a typed full key. Removing a link (`<space>iu`) works from the issue detail cursor only, because that is where a link id is known; a row whose other key is malformed is not selectable. One pick states the sentence and avoids a wrong-direction link.
- **Sprint form (`<space>sn`, `<space>se`, #185).** The field form with `Name *`, `Goal`, `Start` and `End` (dates `yyyy-MM-dd HH:mm`, local time, optional), opened at once with nothing fetched, on a Scrum backlog or a Sprint view (any other view says why in the status line). Create makes a future sprint on the board of the tab; edit changes the sprint of the Sprint view, or the sprint of the section under the cursor in the backlog; a closed sprint is read only. The write waits for the reply and is not optimistic; the field ids are Jira's member names, so a refusal (`endDate`, `name`) lands at its field. A change of one date sends the other as it stands so the order is checked (the end must be after the start) before anything goes out. A date cannot be cleared once set (Jira's partial update has no way to), so an emptied date field counts as unchanged. When Jira confirmed, the form closes and every Scrum backlog and Sprint tab of the board reloads. A lost reply of an edit is checked by reading the sprint; a lost reply of a create cannot be checked (no id yet), so the status line says to look at the backlog before creating it again.
- **Start and complete a sprint (`<space>ss`, `<space>sc`, #186).** Both find the sprint like edit does (the Sprint view's sprint, or the sprint of the backlog section under the cursor) and count its loaded issues; the answers are `y`, `n` and `Esc` only. Start accepts a future sprint (parallel active sprints are allowed by Jira, so there is no "another sprint is active" refusal) and asks for Start and End in a form only when the sprint lacks either. Complete accepts an active sprint only (Jira refuses completing a future one) and refuses while the tab has more pages to load, because the list of open issues must be whole before it is moved. Open means the status is not in the done category. "Asks where open issues go" is a one-field form (`Backlog` default, or `Next sprint: <name>`, the future sprint with the lowest id) shown only when there are open issues and the tab knows a future sprint (the Scrum backlog and the Sprint view both load the board's open and future sprints, #504). Complete is two Jira calls (complete, then move, with the move client of #180); a failed or partly failed move leaves the sprint completed, reloads the board and says in a warning how many issues were not moved and that they stay in the closed sprint. A lost reply of the first call is checked by reading the sprint (closed means applied; the status then says the issues were not moved, because the second call never ran). Any sprint write on a board is refused while another one on that board runs, and a complete holds the keys of its open issues, so a write on one of them is refused too (#154).
- **Suggestion popup (#214, #293).** Drives labels, user and parent fields; selects and multiple choices use it too, their allowed values are the pool, ranked locally with no Jira call. Debounce (250 ms) and the "searching" notice (150 ms) run in `SuggestionHandler` on an injected `TimeProvider`, not in the reducer (the app tick is one second and the reducer reads no clock). Enter and Tab accept the highlighted row (first by default, fzf style); `Space` adds a typed label verbatim. An issue never appears as its own parent or link target.
- **Palette (#368).** Fuzzy list of every action with its keys, opened by `:` or `Ctrl-p` (an accepted exception to the vim rule, as in Gitunia). Typed commands with arguments (`jql <query>`, `tab ...`, `profile ...`) stay a command line when the first word is a command name followed by a space. Gitunia's actions take no arguments; a Jira view command is naturally typed with its query.
- **Comments order (#84).** The issue detail lists comments oldest first and loads further pages at the end (`Load more comments`, `Enter`), because the client pages oldest first with offsets; reversing needs a second client mode for no reader benefit yet.
- **Columns grouping (#192, PR #143).** Children group under their parent card (any issue with a `parent`) and the parent is named in the top border of a child whose parent is in another column. A parent and its children in one column share one outer frame, children indented by two cells, at the card pitch of five rows, so the viewport maths is unchanged. Swimlanes are one lane at a time (`ux-screens.md`, "Columns layout"), so the grouping above works inside the lane.
