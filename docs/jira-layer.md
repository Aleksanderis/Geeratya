# Jira layer

Findings about how Jira Cloud behaves, from the survey on the dev site (2026-11-01). Every statement names the fixture it rests on; fixtures live under `tests/Geeratya.Jira.Tests/Fixtures/` (paths below are relative to it) and are recorded with `scripts/record-fixture.sh` and scrubbed by `scripts/scrub-fixture.py`.

Part 1 of the survey covers identity, projects, search, filters and errors; part 2 (#14, section "Survey part 2") covers boards, backlog, ranking, hierarchy, create/edit metadata, transitions, ADF and links. The layer contract, paging models, cache keys and refresh rules are below (M1 design, #64); the sections of each client are written with its issue.

Dev site facts that shape the fixtures: two sandbox projects, `GCM` (company-managed, `style: classic`) and `GTM` (team-managed, `style: next-gen`). The API token's account is a site admin but has no "delete issues" permission in `GCM` (see Errors).

## Authentication and rate-limit headers

- Basic auth, `email:api-token`, on `https://<site>.atlassian.net/rest/api/3/...`. `Accept: application/json` is enough for reads.
- Every response carries rate-limit headers, also on 200: `ratelimit-policy: "jira-burst-based";q=100;w=1`, `ratelimit: "jira-burst-based";r=<remaining>;t=<reset seconds>`, `x-ratelimit-limit: 350`, `x-ratelimit-remaining`. Source: `myself/myself.meta.txt` (status line and these headers). The transport reads them on every response (see Transport).

## Transport (`src/Geeratya.Jira/Transport`)

- `JiraTransport` is created per connection (`JiraConnection`: site URL plus account email) with a `JiraApiToken` and owns one `HttpClient`, the auth header, `Accept`, the user agent, the per-attempt timeout (30 s default) and a per-site concurrency cap (4). Clients such as `JiraUserClient` take the transport; all view state stays in the tab, so one transport serves every tab of the active site.
- The site URL must be https (http only for loopback, used by the fake Jira) and the transport never follows redirects, so a 3xx surfaces as an error and the credential cannot reach another host.
- Calls return `JiraResult<T>` (value or `JiraError` with `JiraErrorKind`): 400 `BadRequest`, 401 `Unauthorized`, 403 `Forbidden`, 404/410 `NotFound`, 409 `Conflict`, 429 `RateLimited`, 5xx `ServerError`, `PageExpired` (a search continued with a bad or expired token), plus `Timeout`, `Network`, `HostRefused`, `InvalidResponse`. Caller cancellation is the one exception that surfaces as `OperationCanceledException`.
- Retries (up to 3) only for idempotent requests (`JiraRequest.Get`, `PostSearch`) on 429, 5xx except 501, and network failure; never on a timeout and never for `JiraRequest.Write`, except a write that gets a 429 with `Retry-After` (not processed, see Writes). The wait is `Retry-After` (seconds or HTTP date) or exponential backoff with jitter, capped at 60 s (a `Retry-After` beyond the cap is not waited for: the call returns `RateLimited` with `RetryAfter` at once). The 429 path is backed by a recorded real 429 (`errors/search-429-rate-limited.*`, #18).
- The token is held only in the transport. `JiraApiToken.ToString()` is `[redacted]`, error messages are scrubbed of the token and the Basic credential, and a network failure message carries only the `HttpRequestError` code.
- `GEERATYA_LIVE_HOSTS` is parsed by `JiraHostAllowList`; a transport given `AllowedHosts` refuses any other host before sending (`HostRefused`).
- Scheduling (#22): `JiraRequest.Priority` is `User` (default) or `Background` (`request.AsBackground()`). The per-site cap (4) has two lanes: user requests may use every slot and are granted first; background requests use at most `cap - ReservedForUser` slots (1 reserved, never below one slot), so a key press never queues behind a refresh. Cancelling a queued call removes it from its lane.
- Proactive throttle (#22): after each response the transport keeps the last budget from `ratelimit: ...;r=<remaining>;t=<reset seconds>` (with several policies the smallest `r` wins) or, failing that, `x-ratelimit-remaining` with a one-second window. A background request waits for the window to end when `r <= BackgroundThrottleRemaining` (10); a user request waits only when `r == 0`. The wait is capped by `MaxWait` and is not spent holding a slot. A 429 is not recorded as a budget (its `Retry-After` wait applies instead, so there is no double wait). Both waits (this throttle and a `Retry-After` retry, not 5xx backoff) are published for the UI (#49): `JiraTransport.RateLimitedUntil` is the latest end of any active wait (null when none) and the `RateLimitWaitChanged` event fires, on a non-UI thread, when one starts or ends. Unreadable headers mean no throttling. The header format rests on the survey (`myself/myself.meta.txt`) and Atlassian's docs; a real 429 carries no `ratelimit`/`x-ratelimit-*` headers (so it never feeds the budget), see Errors.
- Scoped tokens (`api.atlassian.com/ex/jira/<cloudId>`): the transport appends paths to a base path (tested); cloudId discovery and profile support belong to profiles (#5).

## Layer contract (M1 design, #64)

- A client is a small class over one `JiraTransport` (`JiraSearchClient`, `BoardClient`, filter, issue and comment clients, one folder and one `JsonSerializerContext` each). It owns no state, no cache and no cancellation policy: the caller passes a `CancellationToken` and, for refresh, builds the request with `AsBackground()`. It never references Core or the UI.
- Every method returns `JiraResult<T>` with typed models; mappers never throw on missing or unknown fields. Models are the ones core state holds (`IssueSummary`, `BoardConfiguration`, issue detail): Core does not wrap them in duplicate DTOs. The only copy is the disk cache's own DTOs (see "Cache keys").
- The clients know nothing of tabs, views or request ids; those belong to the state layer (`docs/architecture.md`, "Views and tabs", "Loading").

## Paging models

Both paging styles hide behind one cursor so the state layer pages the same way for every source (types from #66; #69 and #70 reuse them):

| Type | Shape | Used by |
|---|---|---|
| `PageCursor` | Either a `Token(string)` (opaque `nextPageToken`) or an `Offset(int)` (`startAt`) | request side of every paged call |
| `IssuePage` | `Items` (`IReadOnlyList<IssueSummary>`), `Next` (`PageCursor?`, null on the last page), `Total` (int?, null for search; set from `total` for the agile API) | `/search/jql`, board issues, backlog |
| `OffsetPage<T>` | `Items`, `StartAt`, `Total`, computed `IsLast` | boards list, filters, projects, comments |

Rules: the agile API has no `isLast`, so the client sets `Next` to `Offset(startAt + count)` unless `startAt + count >= total` (an empty page also ends the walk, guarding against a `total` that shrinks). Search has no total; its last page has no token. The cursor of a search page is only valid with the same `jql`, `fields` and `maxResults`, so the client takes the whole query again with the cursor; it expires, and a 400 on a request that carried a token means "page expired", handled by the state layer by restarting at the first page (`docs/architecture.md`, "Loading"). Default page size 100 for both styles (the search cap is probed in #66, the agile caps in #69).

## Cache keys

The disk and memory cache (`docs/architecture.md`, "Cache and refresh") keys what a client returned, never raw HTTP:

- Views: `(ViewSourceKind, SourceValue)` inside the profile's folder. Source value is the JQL text, the filter id or the board id. The profile (site plus account) is the folder, so the same JQL on two sites never collides. A board key caches the board's configuration with its first page.
- Issue details: the issue key inside the profile's folder. An entry is removed when the issue load answers 404 or 403 (the issue is gone or hidden).
- Not cached: comments, remote links, filter lists and board lists (cheap and rarely the first thing seen), anything from `/myself`, anything with credentials. Writes (M2) invalidate the issue detail entry and the first-page entries of every view that could contain the issue (simple rule: drop all view entries of the profile; `InvalidateCacheEffect` runs `SiteCache.RemoveIssue` per key and `SiteCache.RemoveViews`, #154; `docs/architecture.md`, "Write pipeline").
- Custom field ids are per site, which is one more reason the cache folder is per profile. Cached rows carry only the fields the mapper reads; a change to that field list bumps the cache schema version.

## Writes (`src/Geeratya.Jira/Writes`, #155)

Shared base of every write client. A write is built with `JiraRequest.Write` and sent with the `SendWriteAsync` extension on `JiraTransport` (namespace `Writes`; typed reply, or no reply body for 204); the result is `WriteResult<T>` (value or `WriteError`). `SendWriteAsync` refuses a read request. Each write is its own client method named for what it does and is only called from a confirmed command.

| Status / failure | `WriteErrorKind` | Outcome |
|---|---|---|
| 400 | `Validation`: `FieldErrors` (field id and message, from `errors`) plus `Messages` (`errorMessages`); a transition refused by a workflow validator also lands here | not applied |
| 401 | `Unauthorized` | not applied |
| 403 | `Permission` | not applied |
| 404, 410 | `NotFound` (hidden and missing look the same) | not applied |
| 409 | `Conflict` (changed meanwhile, workflow rule) | not applied |
| 429 | `RateLimited`, `RetryAfter` set when sent | not applied |
| Timeout | `Timeout` | unknown |
| Network failure, 5xx, unreadable 2xx body, unexpected status (3xx) | `UnknownOutcome` | unknown |
| Host not allowed | `NotSent` | nothing sent |

- Never retried automatically, with one exception: a 429 that carries `Retry-After` is waited out and sent again (up to `MaxRetries`; a `Retry-After` beyond `MaxWait` is returned as `RateLimited` at once), because Jira did not process it. A 429 without `Retry-After`, and every timeout, network failure or 5xx, is returned as is: repeating a create or comment could duplicate it. The wait shows in `RateLimitedUntil` like a read's.
- `WriteError.IsOutcomeUnknown` is true for `Timeout` and `UnknownOutcome`. The UI says "may or may not have been applied" and offers a reload; it never re-sends silently. Caller cancellation throws `OperationCanceledException` and is likewise unknown.
- `ReadAfterWrite.ReloadIfUnknownAsync(write, reload, ct)` runs the caller's read only after an unknown outcome and returns null otherwise; the caller compares the reloaded issue with the intended change.
- Error bodies: the three shapes under Errors; `errors` values and `errorMessages` entries are kept as Jira wrote them (truncated at 200 characters), HTML never reaches the message, the token is redacted. Fixtures: `errors/create-400-*.json`, `errors/issue-delete-403-no-permission.json`, `errors/issue-404.json`, `errors/search-429-rate-limited.json`; `errors/transition-409-conflict.json` is synthetic (a 409 was not recorded live).
- A 2xx whose body cannot be read is reported as `UnknownOutcome` although the write was applied; the reload settles it. Rule for the first write client: invalidate the cache (Cache keys) after a success and after an unknown outcome, since the issue may have changed.

## Refresh rules (Jira side)

The schedule is in `docs/architecture.md`, "Cache and refresh"; what the Jira layer guarantees for it:

- Automatic refresh uses `AsBackground()` on the same transport: at most `cap - ReservedForUser` slots, throttled earlier than user work when the budget is low, so a refresh never delays a key press. Manual refresh, open, next page and retry are user requests.
- Refresh traffic is bounded: one tab at a time, one load in flight per tab, pages walked sequentially. A list tab costs one search call per refresh (one a minute at the default interval); a board or backlog tab costs one call per page of its issues (100 per call, so a 1 000-issue board is 10 background calls a minute, a full 10 000-row board 100, the worst case).
- While `JiraTransport.RateLimitedUntil` is set the state layer starts no automatic refresh; the transport itself already waits `Retry-After` on retries. A `Retry-After` beyond `MaxWait` is not slept, so it does not set `RateLimitedUntil`; the caller reads `RetryAfter` from the error.

## Errors to UI states

Map once, in the pure message table in Core (`LoadErrorText`, #77; the reducer builds the text), used by loads, refresh and banners:

| `JiraErrorKind` | State | Refresh behaviour |
|---|---|---|
| `Network`, `Timeout`, `HostRefused` | offline (last data stays, marked stale) | backoff probe |
| `RateLimited` | rate limited; the load error text names the wait ("Try again in N s") when `Retry-After` is known; the banner counts the wait down from `RateLimitedUntil` | paused until the wait ends |
| `Unauthorized` | error "token rejected" with a `:profile` hint | refresh stops until the connection check succeeds |
| `Forbidden`, `NotFound` | error "not found or no access" (the two cannot be told apart, see Errors) | backoff |
| `BadRequest` | Jira's own message (JQL syntax); on a request that carried a page token, "page expired": reload from the first page | none for JQL errors; reload once for an expired token |
| `ServerError`, `InvalidResponse`, `Unexpected` | error with Jira's or the client's own message (the refresh key retries, see "Refresh rules") | backoff |

### Writes (M2 design, #151)

State-layer rules are in `docs/architecture.md`, "Write pipeline"; what the Jira layer owes it:

- Write clients return `JiraResult<T>` with the mapped `JiraError`; `JiraError` gains `FieldErrors` (the `errors` object of a 400, empty otherwise), so a form can show a message at its field. The body shapes in "Errors" apply; 401 has no JSON.
- Never retried: every write is `JiraRequest.Write` (no retry on 429, 5xx, network or timeout), because a create or an added comment is not idempotent and a retry the user did not choose may repeat a side effect. The reads that verify a write (re-reading the issue, `key in (...)`) retry as usual.
- Definite or not: `HostRefused` (nothing sent), 4xx and 429 are definite; `Timeout`, `Network`, 5xx and `InvalidResponse` are not. The state layer's table (`WriteFailure.Of`) uses this and the status, nothing else.
- Cancelling the caller's token after a write was sent does not undo it; it only drops the reply, which the app treats as an unknown outcome.
- After a write that changes an issue the handler reads the changed issues by key (one search, row fields), so the UI gets the server's truth including post-function changes; rank and create reload the view instead.

## Current user: `GET /rest/api/3/myself`

Fixture: `myself/myself.json`.

- Returns `accountId`, `accountType` (`atlassian`), `active`, `displayName`, `emailAddress`, `locale`, `timeZone`, `avatarUrls`, `self`. `expand=groups,applicationRoles` is advertised but the lists come back empty with only a `size`; do not rely on them.
- Use it as the credential check when a profile is added or switched: 200 means email and token are good, 401 means not (see Errors). The shell runs it as a `CheckConnectionEffect` (user lane) at start, after `:profile add` and a switch, and on `:profile check`; the failure kind (401, 403, network, timeout, host refused, 429) picks the hint in `ConnectionText`. Nothing from `/myself` is cached.
- `emailAddress` can be hidden by the account's privacy settings; treat it as optional.

## Projects: `GET /rest/api/3/project/search`

Fixture: `projects/project-search.json`.

- Paged with `startAt`/`maxResults` and `isLast`/`total` (the classic offset paging, unlike search). The requested `maxResults` was echoed (50); the cap was not probed.
- Project kind is told by `style` (`classic` = company-managed, `next-gen` = team-managed) and the boolean `simplified` (`false` / `true`); both are present on every project in the list, no `expand` needed. `projectTypeKey` is `software` for both here; business and service-desk projects use other values.
- `projectCategory` is present only when the project has one (GTM has `Dev`, GCM none): optional.
- `entityId` and `uuid` are the same GUID. `avatarUrls`, `properties` and `description` may be empty.
- Both kinds have the same issue-type names (Epic, Story, Task, Bug, Sub-task/Subtask) but different ids; team-managed issue types additionally carry `entityId` in issue payloads (`search/search-page2.json`, GTM issues; absent on GCM issues).
- Quirk: a team-managed project's statuses have their own ids, and a status name need not match its category (GTM's `To Do` has category `In Progress` in `search/search-page2.json`); never infer the category from the name.

## JQL search: `GET|POST /rest/api/3/search/jql`

Fixtures: `search/search-page1.json`, `search-page2.json`, `search-page3-last.json` (three pages of seven issues across both kinds with `maxResults=3`), `search-post.json`, others as named below.

- Paging is by opaque token. A page has `issues`, `isLast` and, unless last, `nextPageToken`; the last page has no token (`search-page3-last.json`). Pass the token back as `nextPageToken` with the same `jql`, `fields` and `maxResults`. The token is long (about 120 characters) and embeds the query; it expires (a bad or expired one is 400, `errors/search-400-bad-token.json`). There is no `total` and no `startAt`.
- Count: `POST /rest/api/3/search/approximate-count` with `{"jql": ...}` returns `{"count": n}` (`search/approximate-count.json`). Approximate in general; use it only for a "about N" label.
- POST takes the same parameters as a JSON body (`jql`, `maxResults`, `fields` as an array, `nextPageToken`) and pages the same way (`search/search-post.json`). Use it when the JQL is too long for a URL.
- `fields` matters: with none, each issue is `{"id": "..."}` only, not even the key (`search/search-default-fields.json`). With `fields=summary` an issue is `id`, `key`, `self`, `expand` and the field (`search/search-maxresults-5000.json`). `fields=*navigable` returns 76 fields on this site, mostly `customfield_*` ids (`search/search-fields-navigable.json`); never send it, ask for what is shown. Custom field ids are per site (rule in `.claude/rules/jira-layer.md`).
- `expand` on each issue is a string listing what can be expanded, not data; ignore it.
- A requested but empty `assignee` is `null` (`search/search-page1.json`); `parent` is absent, not `null`, when the issue has none (`search/search-page2.json`, `search/search-fields-navigable.json`).
- Without `ORDER BY` the order is not creation order (`search/search-maxresults-5000.json` lists newest first for one project); always send an explicit `ORDER BY`. Ordering across both project kinds works (`ORDER BY created ASC`, `search/search-page1.json`; `DESC` in `search/search-order-desc.json`).
- `key in (A-1, B-2, A-9999)` returns the issues that exist and silently skips the missing key, no error (`search/search-key-in.json`). Good for batch fetches; detect missing keys by diffing.
- JQL must be bounded: an empty `jql` or one with only `ORDER BY` is 400 `Unbounded JQL queries are not allowed here. Please add a search restriction to your query.` (`search/search-unbounded-jql.json`, `search/search-order-only.json`). The app must add a restriction (for example a project) before sending.
- JQL builder: `JqlBuilder` (`src/Geeratya.Jira/Jql/`, static, pure) is the only way the app builds JQL. It quotes and escapes every value (`\\`, `"`, control characters, U+2028/9), writes valid issue keys bare (`parent = GCM-5`, `key in (A-1, B-2)`) and quotes anything else, writes numeric filter ids bare (`filter = 10001`), and always quotes project keys, issue types and status categories. `IsBounded(jql)` skips quoted text when looking for `ORDER BY`; `EnsureBounded(jql, restriction)` is for app-built queries only. JQL typed by the user is never passed through it. Probed on the dev site (2026-11-02; fixtures `search/search-key-reserved-word.json`, `search/search-parent-reserved-word.json`, `search/search-statuscategory-{todo,inprogress,done}-*`, `errors/search-400-reserved-word-value.json`; the response bodies do not carry the JQL, the queries are in the commit message of #107): `key in (OR-1, IN-5, AND-3, ORDER-2)` and `parent = OR-1` parse (200, no such issues exist), so the builder keeps such keys bare; only a bare reserved word as a value (`key = OR`) is a 400 asking for quotes. `statusCategory` accepts the names (`"To Do"`, `"In Progress"`, `"Done"`) and the keys (`new`, `indeterminate`, `done`) with the same issues. The names are localized per site language and untested on a non-English site (owner check, #219), so the builder sends the keys, which are assumed not to be localized (also untested on a non-English site). A filter whose name is all digits is read as an id. `parent = KEY` returns direct children only, so sub-tasks of children need a second query (`ParentIn`).
- Unknown project or field in valid JQL is not an error here: `200` with no issues, re-checked live with `jql=project = NOPE`, `jql=nosuchfield = 1` and `jql=project = GCM AND nosuchfield = 1` (all with `fields=summary`) (`search/search-unknown-project.json`, `search/search-unknown-field.json`). Only a syntax error is a 400 (below). So "no results" cannot be told from a typo in a project key; the UI should not claim the project exists.
- The old `GET /rest/api/3/search` is gone: 410 with a message pointing to `/search/jql` (`search/search-legacy-removed.json`). Do not use or fall back to it.
- `maxResults`: the cap is 5000. `5000` is accepted (`search/search-maxresults-5000.json`); `5001` and `100000` are 400 `The max results parameter has to be between 1 and 5,000.` (`errors/search-400-maxresults-cap.json`, probed with `fields=summary`; with more fields Jira may return fewer than asked, so never assume a full page equals `maxResults`). The app uses tens per page and the client clamps to 1..5000.
- There is no jump to row N: tokens only go forward, so a deep scroll pages through every earlier page.

### Search client (`src/Geeratya.Jira/Search`)

- `JiraSearchClient` takes a `JiraTransport`. `SearchAsync(IssueSearchQuery, PageCursor?, ct)` returns an `IssuePage` (`Items`, `Next` cursor or none, `Total` always null for search); `ApproximateCountAsync` posts to `/search/approximate-count`. `IssueSearchQuery.AsBackground()` marks refresh and prefetch as background work. The client never adds `ORDER BY`.
- GET while the request path is at most 2000 characters, POST with the same parameters as a JSON body beyond that (`search/search-post.json`). The field list is the constant `IssueFields.ListRow` (summary, status, issuetype, priority, assignee, labels, parent, updated, project), never `*navigable`. Fixtures with exactly those fields: `search/search-rows-gcm.json` (24 issues, company-managed: epics, a parent-less and a parented story, sub-tasks, all three status categories) and `search/search-rows-gtm.json` (16 issues, team-managed, `Subtask`, status `To Do` in category `indeterminate`, `Backlog` in `new`). All dev-site issues are unassigned, so the assignee object shape is covered by an inline JSON test, not a recorded fixture.
- `IssueSummary` is the list row: ids, key, summary, `IssueStatus` (category key from Jira), `IssueTypeSummary` (hierarchy level and sub-task flag), priority name (null when the project has none), assignee (null when unassigned), labels, `IssueParent` stub (null when the `parent` field is absent), `updated` (Jira writes the offset as `+0200` without a colon; an unreadable value maps to null) and project key. The mapper never throws: a missing status becomes category `undefined`, missing strings become empty, unknown properties are ignored. Repeated names are shared within a page.
- `OffsetPage<T>` (`Paging/`) is the shared shape for the offset-paged agile and filter endpoints; `NextStartAt` is null on the last page.
- Errors: a bad JQL is `BadRequest` with Jira's message; a 400 while continuing with a cursor is `PageExpired` ("The page expired, reload the results." followed by Jira's own message, so a wrong JQL stays visible); 401, 403, 404/410, 429 (retried by the transport, then `RateLimited`) and 5xx map as in Errors below. 410 is `NotFound`.
- Issue detail: `IssueClient.GetIssueAsync(key, ct)` (`src/Geeratya.Jira/Issues/`, own JSON context) reads `GET /rest/api/3/issue/{key}?fields=` with `IssueFields.Detail` (the list-row fields plus reporter, created, description, subtasks, issuelinks, attachment). A string that is not an issue key (`IssueUrls.IsValidKey`) is answered as NotFound without a request. `IssueDetail` holds the `IssueSummary` fields plus reporter, `Created`, `Description` (`AdfDocument`, null when the field is null or the document has no content), `Parent` and `Subtasks` as `IssueStub` (key, summary, status, type), `IssueLink` and `IssueAttachment`. A link has no direction field: `outwardIssue` present means the opened issue reads the type's `outward` text ("blocks"), `inwardIssue` present means the `inward` text ("is blocked by"); an entry with neither is dropped. Attachments are metadata only (`ContentUrl` is kept, never fetched). Fixtures per kind, recorded on 2026-11-02 with the detail field list: `issues/issue-gtm11.json` (team-managed story with parent, two sub-tasks, a link each way, an attachment), `issue-gtm20.json` (sub-task), `issue-gtm9.json` (epic, no parent), `issue-gcm10.json` (company-managed story with the same relations), `issue-gcm6.json` (sub-task, null description), `issue-gcm2.json` (null description, no relations), `issue-gcm24.json` (media description, image attachment). `FakeJiraRouter` serves them by key; other keys answer the recorded 404. Fixtures for "issue-gtm5-*" in the survey are partial and stay as survey records.
- `IssueUrls.Browse(connection, key)` is the only builder of `https://<site>/browse/KEY` (scheme and host of the site URL only, so a scoped-token gateway URL `api.atlassian.com/ex/jira/<cloudId>` would need its own site URL; null for an invalid key such as `GCM-1/../x`, `GCM-1?x` or a trailing newline). No API call.
- Mapping cost: 10 000 issues of the `GCM` fixture (18 MB, one 5000-style page) take about 80 ms median, 120 ms p95 on a JIT Release build over the fake handler, including reading the body as a string and deserializing (see `docs/performance.md`).

## Suggestions

`src/Geeratya.Jira/Suggestions` (#213): `SuggestionClient` over one transport. Read-only, cancellable (cancel throws `OperationCanceledException`), typed `JiraResult<IReadOnlyList<Suggestion>>` with at most 20 entries. `Suggestion` is `Id` (account id, label text, issue key, component or version id), `Label`, `Detail` (issue key for issues) and `IsInactive` (deactivated user, archived version). An empty or blank query sends no request and returns nothing (a picker never lists a whole site); the one exception is issues, where Jira's picker answers recents. For locally filtered sources (labels, components, versions, allowed values) prefix matches rank before contains-matches (`SuggestionFilter`, pure); user and issue order is Jira's. Nothing is cached by the client; the picker owns debouncing and cancelling the previous call (`SuggestionHandler` in App, #214: 250 ms pause, one lookup per tab); the site label list is read by `GetSiteLabelsAsync` (up to 5 sequential pages, unfiltered) and kept for 2 minutes by the app (`SiteLabelCache` in `SuggestionHandler`, one per connection generation, so a profile switch drops it; failures are not kept), so typing a label reads the site once and later queries filter locally (#292). Mentions use `viewissue/search`; `/user/search` was not needed. Live check (#340, `LiveEditorTokensTests`, `GCM` and `GTM`): a comment written from editor text with a mention of a real account and a link mark to the browse URL is stored and read back with the mention id and the link href intact, an `inlineCard` for the same issue is stored as an inline card (the link mark is not converted), and both bodies pass `AdfRoundTrip`. `GCM` refuses deletes (#19), so each run leaves one `geeratya-test-<run id>` issue there.

Fixtures under `errors/`. Statuses were all recorded live unless marked.

| Case | Status | Body | Fixture |

| Invalid query parameter | 400 | Problem-details shape: `{"detail", "instance", "status", "title", "type"}`, no `errorMessages` | `errors/search-400-bad-maxresults.json` |

| No permission | 403 | `errorMessages` ("You do not have permission to delete issues in this project.") | `errors/issue-delete-403-no-permission.json` |

| Concurrency rate limit | 429 | `errorMessages` ("The request has been rate-limited. Please try again later."); headers `Retry-After` (seconds), `ratelimit-reason` | `errors/search-429-rate-limited.json`, `.meta.txt` |
| Removed endpoint | 410 | `errorMessages` | `search/search-legacy-removed.json` |
| Server failure | 500 | HTML page ("Something went wrong"), not JSON | `errors/500-html-error-page.html` |

Consequences for the mapper:

- Three body shapes exist: `{errorMessages, errors}`, problem-details JSON, and non-JSON text or HTML. The error mapper must try JSON and fall back to a trimmed text snippet (never the raw HTML in the UI). Status decides the typed error, the body only supplies the message.
- 404 and 403 cannot be told apart for hidden things: an issue you may not see is 404, with the same message as a missing one. Say "not found or no access".
- 401 has no JSON body; do not parse it. A wrong email and a wrong token look the same.
- `403` on delete was recorded as a side effect: the dev account cannot delete issues in `GCM` while it can in `GTM` (permission schemes differ between the kinds). Tests that clean up must handle a 403 on delete.
- **429 recorded (#18).** A read-only burst of parallel `search/jql` calls on the dev site (30, 80 and 150 parallel: all 200; 300 parallel: 245 x 200, 55 x 429) hit the concurrency limit, not the per-second budget. The 429 carries `Retry-After` in whole seconds (25 to 35 s in that burst, jittered, so honour it rather than assume a value), `ratelimit-reason: jira-max-concurrent-threads-across-all-instances-per-tenant-per-user`, and the JSON body `{"errorMessages":["The request has been rate-limited. Please try again later."],"errors":{},"status":429}`. It has no `ratelimit`, `ratelimit-policy` or `x-ratelimit-*` headers and no `beta-retry-after`; the proactive throttle must not expect them. Fixture: `errors/search-429-rate-limited.json` (body) and `.meta.txt` (status and headers). `Retry-After` is still parsed as seconds or an HTTP date, since only the seconds form was observed.

### Ranking

- Rank is the Lexorank string in the Rank field, e.g. `0|i0000e:` (`boards/rank-gcm-backlog-before.json`). Request it with `fields=customfield_10019` (resolved id). Board, backlog and `ORDER BY Rank ASC` (`boards/jql-order-by-rank-gcm.json`) are meant to order by it, but see the disagreement below. JQL `ORDER BY Rank` was recorded for `GCM` only.
- Rank write: `PUT /rest/agile/1.0/issue/rank` with `{"issues": ["GCM-3"], "rankBeforeIssue": "GCM-6"}` or `rankAfterIssue`; one or several issues; 204 with no body. A missing reference issue is 400 with the usual `errorMessages` (`boards/rank-400-missing-issue.json`; the text is the "does not exist or no permission" message, not a rank-specific one). Ranking relative to an issue of another project was also answered 204 (GCM-3 before GTM-4; no body, no fixture), so the app must pick the reference from the same view.
- A rank write changes the values of the moved issue and possibly others (`boards/rank-gcm-backlog-before.json` against `boards/rank-gcm-backlog-after-after-op.json`; the requests in between were two rank writes, 3 before 6 and 6 after 4, and the intermediate state is `boards/rank-gcm-backlog-after-before-op.json`). The listed order and the field values disagree: already in `boards/rank-gcm-backlog-before.json` GCM-6 (`0|i0002e:`) comes before GCM-2 (`0|i00002:`), and `boards/jql-order-by-rank-gcm.json` still had GCM-6 before GCM-4 although 6 has the larger value, a minute after the last write. The cause is unknown (not a lag that closed within a minute; GCM-6 is a sub-task and GCM-3 was once ranked next to a GTM issue, which may matter). Treat the server order as the truth, re-fetch after a rank write instead of re-sorting locally, and do not compare rank strings in the app.
- Rank across sprint sections (#182): rank changes rank only (see the sprint survey), so landing next to an issue of another section is two calls in this order: move the issues (`POST sprint/{id}/issue` for a sprint, `POST backlog/issue` for the backlog), then `PUT issue/rank`. Not atomic; a failed second call leaves the issues moved and is reported as such.
- Move to backlog: `POST /rest/agile/1.0/backlog/issue` with `{"issues": [...]}` (204). On the Kanban board it did not change the status of GCM-1 (still `To Do`, `boards/gcm-board-after-backlog-move.json`) and on the team-managed board GTM-5 stayed `In Progress` (`boards/gtm-board-after-backlog-move.json`): it appears to be a Scrum operation (take an issue out of a sprint); unverified. For Kanban, "send to backlog" is a transition to the backlog status.
- Rank client (`src/Geeratya.Jira/Rank`, #168): `RankClient` over one transport. `RankBeforeAsync` / `RankAfterAsync(keys, referenceKey, rankFieldId, token)` write `PUT issue/rank`, `MoveToBacklogAsync(keys, token)` writes `POST backlog/issue`; both return `WriteResult<RankOutcome>` with one `RankItemResult` (key, `IsRanked`, Jira's messages) per requested issue in request order. `rankFieldId` is the board's `customfield_NNNNN` (`BoardConfiguration.RankFieldId`) sent as the numeric `rankCustomFieldId`; null lets Jira pick. 204 (empty body) means all moved (an empty 207 body is read the same way); 207 `{"entries": [{issueKey, status, errors}]}` is a successful call with per-issue results (a partial failure is not a `WriteError`: check `AllRanked`), and an issue missing from a 207 counts as not moved. The 207 shape follows Atlassian's API description; it was not reproduced on the dev site (`writes/synthetic-rank-207-partial.json` is synthetic). Input that cannot be valid (no keys, more than 50, a bad or repeated key, the reference among the moved issues, a malformed rank field id) is refused as `Validation` with no request; a reference that no longer exists is 400 `Validation` with Jira's "does not exist or no permission" message, so rank relative to an issue the view still shows and reload on that error. Writes are never retried (a 429 with `Retry-After` excepted); a lost reply is an unknown outcome. The caller reloads the view after success or unknown outcome (server order is the truth, see above) and invalidates its cache (Cache keys). The transport accepts an empty 2xx body for a typed write only when the request says so (`JiraRequest.AllowsEmptyBody`).

The kind comes from the field schema: string (rich text for `description`, `environment` and custom textareas), option and priority (single choice), arrays of option/component/version (multi choice) or string (labels), user, date and datetime, number, `parent`, project and issuetype (fixed, set from the selection). Any other schema, or none, is `Unsupported`: it stays in the list (read-only in the UI with a browser link), never dropped. Entries without an id and non-object allowed values are skipped. No issue type name is special-cased: the hierarchy level and sub-task flag are Jira's, so a custom level 2 type works (`create/synthetic-issuetypes-custom.json`, `create/synthetic-fields-custom.json`, which also hold a renamed sub-task type, a required custom select and an unknown field type).
- Parent rule (`CreateFormRules.ParentRule`): the `parent` field on the type's create screen decides. Missing means not allowed (epics), `required: true` means required (sub-tasks of both kinds), otherwise optional. Both project kinds write `parent: {key}`; Epic Link is never written. Jira's own checks (a parent of a wrong level) stay Jira's: the answer is 400 with `errors.parent` (`create/synthetic-create-400-invalid-parent.json`, synthetic: the real message was not recorded). `CreateFormRules.MissingRequired` lists required fields the form still lacks, skipping project, issue type and fields with a default (the team-managed reporter, which Jira fills with the creator); a missing field Jira finds itself is 400 with the field id (`writes/create-400-no-summary.json`, `create/synthetic-create-400-required-custom.json`).
- Limits: a required field of kind `Unsupported` is listed by `MissingRequired` but cannot be filled (no raw value form); the form shows "create in the browser" for such a type. A site whose create screen offers only the legacy Epic Link and no `parent` gets parent rule NotAllowed and Epic Link as Unsupported (deliberate: the parent model is the one written). The type walk stops at 1000 entries.
- `CreateIssueAsync(NewIssue)` is the write (`POST /issue`, 201 `{id, key, self}`): project by key, issue type by id, summary, an optional plain-text description written as ADF (one paragraph per line, an empty line is an empty paragraph), optional parent key and further fields as typed `CreateFieldValue` (text, rich text, choice id, choice ids, labels, account id, number), written in the shape Jira wants. Input that cannot be valid (blank summary, malformed project key, type id or parent key, a field the call sets itself in the extras) is refused as `Validation` with no request. Errors follow the Writes table; a 2xx without a key is an unknown outcome. Never repeat a create after an unknown outcome without searching first. The caller invalidates the cache after success or unknown outcome (Cache keys).
- Edit metadata: `GET /rest/api/3/issue/{key}/editmeta` (`metadata/editmeta-gcm-26.json`, which has components and versions) gives the same field shape for the fields that can be edited now; it varies by issue (status and type), so fetch it when the editor opens, not at startup.
- Write bodies: `PUT /rest/api/3/issue/{key}` takes `fields` (replace) and `update` (`labels: [{add}]`, `comment: [{add}]`); 204 on success. An unknown or screen-less field is 400 `errors: {"nosuchfield": "Field 'x' cannot be set. It is not on the appropriate screen, or unknown."}` (`adf/edit-400-unknown-field.json`). Description and comment bodies are ADF in v3 (below).

Since #110 table cells and headers also carry `RowSpan` (1 when absent, below 1 or unreadable) and `ColumnWidths` (empty unless `colwidth` is a list of whole numbers), and `AdfNestedExpand`, `AdfDecisionList`/`AdfDecisionItem` (`State`), `AdfCaption` and `AdfMediaInline` exist (`AdfMediaInline` derives from `AdfMedia`, so a renderer that shows media shows it too). `background` is not kept (colour is ignored in the terminal). The cache stores the row span and widths in the string slots of the flat node shape (`AdfCacheMapper`), so files written earlier read back with span 1. It reads `JsonElement` by hand, so it needs no serializer context. It never throws: `null`, wrong types, missing `content` and malformed JSON give an empty document (malformed sets `IsTruncated`), and nodes nested deeper than `AdfParser.MaxDepth` (64) are dropped with `IsTruncated` set, so recursion is bounded. `media` nodes are kept as nodes with their attributes and never resolved. Rendering is `Core/Adf/AdfRenderer.Render(document, width)` (#80): pure, returns `AdfRendering` (styled lines plus `LineCount`, cacheable per document and width). Blocks are separated by one blank line (tight inside list items and table cells): headings take the `Heading` role, lists use `- `, `N. ` (from `attrs.order`, numbers padded to align) and `[x] `/`[ ] `, code blocks are fenced with the language after the opening fence (role `Code`, no highlighting, cut at the width), blockquotes and panels get a `| ` bar (a panel starts with `[type]`), `expand` shows `v Title` with its content indented, tables are `| a | b |` grids with a `|---|` rule under an all-header first row (columns sized from content, widest columns narrowed down to 8 columns and their cells wrapped, and when that still does not fit, one block per row as `Header: value`, with a long header on its own line above the value; a `rowspan` cell is drawn in its first row and leaves blank space below it, cells in the rows below take the next free column, a span past the last row or into a taken column is clamped, and a span cell taller than its rows makes the last covered row taller; in the one-block-per-row form it appears once, in its first row). `nestedExpand` looks like `expand` (`v Title`, default `Expand`), a `decisionItem` gets a `[decided]` marker (the lowercase state, `[decision]` when none), a `caption` is a line under the media marker and `mediaInline` is the inline `[file]` marker (#117). Media shows as `[image]` (`mediaSingle`) or `[file]` (`media`, `mediaGroup`), with the alt text when present. Marks map to one role each (`Code` over `Link` over `Strong` over `Emphasis`; underline uses `Emphasis`, strike uses `Muted`, as `TextRole` has no such roles; colour is ignored); a link whose text differs from its address is followed by `<address>`; sub and superscript get `_` and `^`. A keycap emoji (ASCII character plus variation selector and enclosing keycap) is one cell of two columns and is never split when wrapping. Mention is `@Name`, emoji the glyph or `:shortName:`, date `yyyy-MM-dd` (UTC), status `[TEXT]` (role by colour: green done, blue in progress, red error, else to do), inline card its URL. Unknown nodes and marks print `[unsupported: type]` followed by their text; nesting deeper than 100 levels (hand-built trees only) ends in `[unsupported: nesting too deep]`.
- Writer (#161, `src/Geeratya.Jira/Adf/`): ADF is edited as Markdown-like text (roadmap question 1, default taken). `AdfMarkdownWriter.ToText(document)` writes it, `AdfMarkdownParser.Parse(text)` reads it back into an `AdfDocument`, `AdfJsonWriter.ToJson(document)` writes the ADF JSON body for a description or comment write, and `AdfRoundTrip.RoundTrips(document)` says whether ADF to text to ADF gives the same document, so the UI can warn before saving one that does not. All are pure and never throw. Syntax (`AdfMarkdownSyntax`): paragraphs split by blank lines (a single newline is a `hardBreak`), `#` to `######` headings, `**bold**`, `*italic*`, `~~strike~~`, `++underline++`, `` `code` ``, `[text](url)`, bullet (`- `), ordered (`1. `, the first number is kept) and task lists (`- [ ]`, `- [x]`, only when every item is a task of one paragraph) nested by indentation under the marker, fenced code blocks with a language, `>` quotes, `---` rules, `@[Name](mention:accountId)` for a mention (kept as an opaque token, the account id is preserved) and `<https://...>` for an inline card. A backslash makes the next punctuation character literal; the writer escapes what the parser would read as syntax. A link address may hold balanced parentheses. So that the ADF is one Jira accepts, the parser drops empty list items and quotes, turns a heading inside a quote or list item into a paragraph, drops a rule there, flattens a quote inside a quote or item, and puts an empty paragraph before a list that opens an item (confirmed live on the dev site, #266: Jira accepted the writer output as an issue description and as a comment in two bodies, one with nested bullet and ordered lists, a task list, a quote, a quote inside an item, a heading, a code block, a rule, a mention and an inline card, one with the cases above after the parser had dropped or flattened them, and stored both unchanged except for an empty `accessLevel` and the mention `text`; whether Jira would reject the unflattened forms was not tried; fixtures `adf/writer-roundtrip-gtm30.json` and `adf/writer-edge-gtm31.json`, compared with the writer output in `AdfRoundTripTests`) Styles toggle and may overlap, an unpaired delimiter stays text, and a link, quote or list never nests deeper than `AdfMarkdownSyntax.MaxNesting` (the rest stays text). A lone UTF-16 surrogate in the text makes `RoundTrips` return false (JSON turns it into U+FFFD on both sides, so the comparison cannot see it). Not expressible: tables, panels, expands, media, decisions, text colour, sub and superscript, dates, statuses and unknown nodes are written as their plain text and `RoundTrips` returns false for them (and for a truncated document). `RoundTrips` compares the writer's JSON of both documents, which joins neighbouring text with the same marks, orders marks, drops empty text and numbers `localId`s in document order, so a split run, a different mark order, an empty paragraph or an emoji node with its glyph (it becomes the plain character) do not count as a difference. Known limits: a paragraph that starts or ends with a line break, `~~~`-style runs of three or more delimiter characters and link addresses with line breaks do not always survive; `RoundTrips` reports them (the 4000-round property test in `AdfRoundTripTests` and an ad hoc 600k-round run found only these). Media cannot be written: Jira rejects media ids it does not know (above), so a document with media must not be sent as text.

### Writes

- Create: `POST /rest/agile/1.0/sprint` `{name, originBoardId, goal?}` (201, `write-sprint-create.json`, state `future`). Move issues in: `POST /sprint/{id}/issue` `{issues: [...]}` (204); an issue in another open sprint is moved (one open sprint per issue); a closed target is 400 `You must specify a sprint which has not been completed.` (`error-sprint-move-into-closed-400.json`). Move to backlog: `POST /backlog/issue` (204) clears the Sprint field. Rank relative to an issue of another sprint (`PUT /issue/rank`) is 204 and changes rank only, not the sprint.
- Update: `PUT /sprint/{id}` replaces, so an omitted `goal` is dropped (`write-sprint-start-parallel-active.json` has no goal where the created sprint had one); `POST /sprint/{id}` is the partial update (`write-sprint-partial-update.json`). Start: `PUT` with `state: active`, `startDate`, `endDate` (200). Without dates it is 400 `You must specify a start date for the sprint.` (`error-sprint-complete-future-no-start-400.json`, from a close attempt without dates). Complete: `PUT` with `state: closed` and the dates (200 with `completeDate`, `write-sprint-complete.json`); closing a future sprint is 400 `Transitioning from FUTURE state to CLOSED state is not supported` (`error-sprint-future-to-closed-400.json`); reopening a closed sprint is 400 `Transitioning from CLOSED state to ACTIVE state is not supported` (`error-sprint-reopen-closed-400.json`); completing a closed sprint again is 200 and changes nothing. A closed sprint can still be renamed (`write-sprint-edit-closed-rename.json`, 200). Clearing a date (checked on the dev site, #493): the partial update ignores `startDate: null` (200, date stays) and rejects `""` (400 `Invalid date format: ''`); `PUT` with the dates left out, or sent as `null`, removes them (200). `SprintWriteClient.ReplaceAsync(current, edit)` therefore sends the whole sprint (`state`, `name`, `goal`, the kept dates) with `PUT` for an edit with `ClearStartDate` or `ClearEndDate`; `UpdateAsync` refuses such an edit. Both probes were observed live and have no fixture. The `PUT` sends `state`, `name` and `goal` as last loaded, so a change made in Jira since then (a rename, a new goal, a started sprint) is overwritten by it, and a stale `state` can come back as a 400 that the status line shows; clearing a date of an active sprint is left to Jira to refuse.
- Complete does not move issues: `moveIssuesTo` (integer or string) is rejected with 400 `Invalid request payload` (`error-sprint-complete-moveissuesto-400.json`). Unfinished issues stay in the completed sprint and show up in the backlog. The Jira UI's "move open issues to sprint X" is therefore two calls: complete, then `POST /sprint/{X}/issue` with the unfinished keys (not atomic: the confirm says so and a partial failure says what was not moved; open question 8).
- Sprint write client (`src/Geeratya.Jira/Sprints`, #184): `SprintWriteClient` over one transport; `CreateAsync(name, originBoardId, goal, start, end, token)`, `UpdateAsync(id, SprintEdit, token)`, `StartAsync(id, start, end, token)`, `CompleteAsync(id, token)`, each returning `WriteResult<WrittenSprint>` (the sprint Jira answers with). All but create use `POST /sprint/{id}`, the partial update, also for the state change: recorded on the dev site, `POST {"state":"active","startDate","endDate"}` keeps the goal (`write-sprint-post-start-keeps-goal.json`) and `POST {"state":"closed"}` needs no dates (`write-sprint-post-complete-no-dates.json`), so `PUT` (which drops an omitted goal) is never used. An empty goal clears it (live round trip). Dates are sent as UTC ISO with milliseconds. The client refuses without a request: blank name, board or sprint id below 1, nothing to change, end not after start. `SprintWriteErrors.Classify(WriteError)` names the cases the UI shows in its own words (`SprintWriteProblem`: start date missing, completing a sprint that is not active, starting a closed one, from the English sentences recorded in the fixtures; end before start and blank name are the client's own checks), so any other Jira error, an end-date or name error included, is `Other` and the UI shows the message. There is no "another sprint is active" error because Jira allows parallel active sprints. Completing a future sprint without dates answers `StartDateMissing` (Jira checks the date first); with dates it answers `NotActive`. Complete does not move unfinished issues: the move into another sprint or the backlog is a separate call (the move client, #180) after a successful complete, and the UI says it is two calls (#186). Start and complete are workflow-affecting: the client only exposes the call, the confirmation is the UI's. Live round trip on boards 5 and 6: `LiveSprintWriteTests`.
- Sprint move client (`src/Geeratya.Jira/Sprints/SprintMoveClient.cs`, #180): `MoveToSprintAsync(sprintId, keys)` (`POST /sprint/{id}/issue`) and `MoveToBacklogAsync(keys)` (`POST /backlog/issue`), both writes for a confirmed command only. Jira takes at most 50 keys per call, so longer lists go out as sequential chunks of 50 and the run is not atomic. The `SprintMoveOutcome` puts every key in one list: `Moved`, `Rejected` (a per-key failure of a 207, or a whole chunk Jira refused, with its message), `Unknown` (timeout or lost reply: reload before retrying) or `NotAttempted` (chunks after a whole-call error; per-key 207 failures do not stop the run). `Error` is the whole-call error that stopped it (closed target sprint is 400 `You must specify a sprint which has not been completed.`, 403, 429). Only an invalid sprint id or key list is refused without a request. The single-call `RankClient.MoveToBacklogAsync` stays for the rank flows. The rank-with variants (move and rank in one call) were not in the survey and are not offered. Tests: `SprintMoveClientTests`; the fake Jira server (`tools/FakeJira`) already serves both endpoints. Moving between sprints of different boards was not recorded (the dev site has no second Scrum board with shared issues); `LiveSprintMoveTests` (opt-in, #424) runs the 204 path live on GCS and GTS (issue to a throwaway sprint, to the backlog, re-read); the 207 per-key path is covered by the fixtures only. The UI side (#181): `SprintMoveRequest` goes through the write pipeline (`WriteHandler`); the pipeline settles a write as a whole, so a move that did not take every issue fails with `N of M moved; KEY not moved: <reason>`, the optimistic rows are undone and the tabs reload to show what really moved; `WriteError.FailedKeys` carries the keys not moved so the reducer unmarks only the moved ones; after a lost chunk (unknown outcome) all marks stay, as nothing is known; it is reported as "could not check, reload" (a read of the issues cannot prove a sprint move, so none is made).
- Delete: `DELETE /sprint/{id}` is 204 for future, closed and also active sprints (an active sprint with issues was deleted without a complaint, so the app confirms and names the issue count); the issues have no Sprint value afterwards.
