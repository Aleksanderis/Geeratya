# Jira layer

Findings about how Jira Cloud behaves, from the survey on the dev site (2026-11-01). Every statement names the fixture it rests on; fixtures live under `tests/Geeratya.Jira.Tests/Fixtures/` (paths below are relative to it) and are recorded with `scripts/record-fixture.sh` and scrubbed by `scripts/scrub-fixture.py`.

Part 1 of the survey covers identity, projects, search, filters and errors; part 2 (#14, section "Survey part 2") covers boards, backlog, ranking, hierarchy, create/edit metadata, transitions, ADF and links. The layer contract, models and refresh design are written when the Jira layer is built.

Dev site facts that shape the fixtures: two sandbox projects, `GCM` (company-managed, `style: classic`) and `GTM` (team-managed, `style: next-gen`). The API token's account is a site admin but has no "delete issues" permission in `GCM` (see Errors).

## Authentication and rate-limit headers

- Basic auth, `email:api-token`, on `https://<site>.atlassian.net/rest/api/3/...`. `Accept: application/json` is enough for reads.
- Every response carries rate-limit headers, also on 200: `ratelimit-policy: "jira-burst-based";q=100;w=1`, `ratelimit: "jira-burst-based";r=<remaining>;t=<reset seconds>`, `x-ratelimit-limit: 350`, `x-ratelimit-remaining`. Source: `myself/myself.meta.txt` (status line and these headers). The transport reads them on every response (see Transport).

## Transport (`src/Geeratya.Jira/Transport`)

- `JiraTransport` is created per connection (`JiraConnection`: site URL plus account email) with a `JiraApiToken` and owns one `HttpClient`, the auth header, `Accept`, the user agent, the per-attempt timeout (30 s default) and a per-site concurrency cap (4). Clients such as `JiraUserClient` take the transport; all view state stays in the tab, so one transport serves every tab of the active site.
- The site URL must be https (http only for loopback, used by the fake Jira) and the transport never follows redirects, so a 3xx surfaces as an error and the credential cannot reach another host.
- Calls return `JiraResult<T>` (value or `JiraError` with `JiraErrorKind`): 400 `BadRequest`, 401 `Unauthorized`, 403 `Forbidden`, 404/410 `NotFound`, 429 `RateLimited`, 5xx `ServerError`, plus `Timeout`, `Network`, `HostRefused`, `InvalidResponse`. Caller cancellation is the one exception that surfaces as `OperationCanceledException`.
- Retries (up to 3) only for idempotent requests (`JiraRequest.Get`, `PostSearch`) on 429, 5xx except 501, and network failure; never on a timeout and never for `JiraRequest.Write`. The wait is `Retry-After` (seconds or HTTP date) or exponential backoff with jitter, capped at 60 s. The 429 path is backed by a recorded real 429 (`errors/search-429-rate-limited.*`, #18).
- The token is held only in the transport. `JiraApiToken.ToString()` is `[redacted]`, error messages are scrubbed of the token and the Basic credential, and a network failure message carries only the `HttpRequestError` code.
- `GEERATYA_LIVE_HOSTS` is parsed by `JiraHostAllowList`; a transport given `AllowedHosts` refuses any other host before sending (`HostRefused`).
- Scheduling (#22): `JiraRequest.Priority` is `User` (default) or `Background` (`request.AsBackground()`). The per-site cap (4) has two lanes: user requests may use every slot and are granted first; background requests use at most `cap - ReservedForUser` slots (1 reserved, never below one slot), so a key press never queues behind a refresh. Cancelling a queued call removes it from its lane.
- Proactive throttle (#22): after each response the transport keeps the last budget from `ratelimit: ...;r=<remaining>;t=<reset seconds>` (with several policies the smallest `r` wins) or, failing that, `x-ratelimit-remaining` with a one-second window. A background request waits for the window to end when `r <= BackgroundThrottleRemaining` (10); a user request waits only when `r == 0`. The wait is capped by `MaxWait` and is not spent holding a slot. A 429 is not recorded as a budget (its `Retry-After` wait applies instead, so there is no double wait). Both waits (this throttle and a `Retry-After` retry, not 5xx backoff) are published for the UI (#49): `JiraTransport.RateLimitedUntil` is the latest end of any active wait (null when none) and the `RateLimitWaitChanged` event fires, on a non-UI thread, when one starts or ends. Unreadable headers mean no throttling. The header format rests on the survey (`myself/myself.meta.txt`) and Atlassian's docs; a real 429 carries no `ratelimit`/`x-ratelimit-*` headers (so it never feeds the budget), see Errors.
- Scoped tokens (`api.atlassian.com/ex/jira/<cloudId>`): the transport appends paths to a base path (tested); cloudId discovery and profile support belong to profiles (#5).

## Current user: `GET /rest/api/3/myself`

Fixture: `myself/myself.json`.

- Returns `accountId`, `accountType` (`atlassian`), `active`, `displayName`, `emailAddress`, `locale`, `timeZone`, `avatarUrls`, `self`. `expand=groups,applicationRoles` is advertised but the lists come back empty with only a `size`; do not rely on them.
- Use it as the credential check when a profile is added or switched: 200 means email and token are good, 401 means not (see Errors).
- `emailAddress` can be hidden by the account's privacy settings; treat it as optional.

## Projects: `GET /rest/api/3/project/search`

Fixture: `projects/project-search.json`.

- Paged with `startAt`/`maxResults` and `isLast`/`total` (the classic offset paging, unlike search). The requested `maxResults` was echoed (50); the cap was not probed.
- Project kind is told by `style` (`classic` = company-managed, `next-gen` = team-managed) and the boolean `simplified` (`false` / `true`); both are present on every project in the list, no `expand` needed. `projectTypeKey` is `software` for both here; business and service-desk projects use other values.
- `projectCategory` is present only when the project has one (GTM has `Dev`, GCM none): optional.
- `entityId` and `uuid` are the same GUID. `avatarUrls`, `properties` and `description` may be empty.
- Both kinds have the same issue-type names (Epic, Story, Task, Bug, Sub-task/Subtask) but different ids; team-managed issue types additionally carry `entityId` in issue payloads (`search/search-page2.json`, GTM issues; absent on GCM issues).
- Quirk: a team-managed project's statuses have their own ids, and a status name need not match its category (GTM's `To Do` has category `In Progress` in `search/search-page2.json`); never infer the category from the name.

## JQL search: `GET|POST /rest/api/3/search/jql`

Fixtures: `search/search-page1.json`, `search-page2.json`, `search-page3-last.json` (three pages of seven issues across both kinds with `maxResults=3`), `search-post.json`, others as named below.

- Paging is by opaque token. A page has `issues`, `isLast` and, unless last, `nextPageToken`; the last page has no token (`search-page3-last.json`). Pass the token back as `nextPageToken` with the same `jql`, `fields` and `maxResults`. The token is long (about 120 characters) and embeds the query; it expires (a bad or expired one is 400, `errors/search-400-bad-token.json`). There is no `total` and no `startAt`.
- Count: `POST /rest/api/3/search/approximate-count` with `{"jql": ...}` returns `{"count": n}` (`search/approximate-count.json`). Approximate in general; use it only for a "about N" label.
- POST takes the same parameters as a JSON body (`jql`, `maxResults`, `fields` as an array, `nextPageToken`) and pages the same way (`search/search-post.json`). Use it when the JQL is too long for a URL.
- `fields` matters: with none, each issue is `{"id": "..."}` only, not even the key (`search/search-default-fields.json`). With `fields=summary` an issue is `id`, `key`, `self`, `expand` and the field (`search/search-maxresults-5000.json`). `fields=*navigable` returns 76 fields on this site, mostly `customfield_*` ids (`search/search-fields-navigable.json`); never send it, ask for what is shown. Custom field ids are per site (rule in `.claude/rules/jira-layer.md`).
- `expand` on each issue is a string listing what can be expanded, not data; ignore it.
- A requested but empty `assignee` is `null` (`search/search-page1.json`); `parent` is absent, not `null`, when the issue has none (`search/search-page2.json`, `search/search-fields-navigable.json`).
- Without `ORDER BY` the order is not creation order (`search/search-maxresults-5000.json` lists newest first for one project); always send an explicit `ORDER BY`. Ordering across both project kinds works (`ORDER BY created ASC`, `search/search-page1.json`; `DESC` in `search/search-order-desc.json`).
- `key in (A-1, B-2, A-9999)` returns the issues that exist and silently skips the missing key, no error (`search/search-key-in.json`). Good for batch fetches; detect missing keys by diffing.
- JQL must be bounded: an empty `jql` or one with only `ORDER BY` is 400 `Unbounded JQL queries are not allowed here. Please add a search restriction to your query.` (`search/search-unbounded-jql.json`, `search/search-order-only.json`). The app must add a restriction (for example a project) before sending.
- Unknown project or field in valid JQL is not an error here: `200` with no issues, re-checked live with `jql=project = NOPE`, `jql=nosuchfield = 1` and `jql=project = GCM AND nosuchfield = 1` (all with `fields=summary`) (`search/search-unknown-project.json`, `search/search-unknown-field.json`). Only a syntax error is a 400 (below). So "no results" cannot be told from a typo in a project key; the UI should not claim the project exists.
- The old `GET /rest/api/3/search` is gone: 410 with a message pointing to `/search/jql` (`search/search-legacy-removed.json`). Do not use or fall back to it.
- `maxResults`: the survey data (seven issues) cannot show the cap; `5000` was accepted without error (`search/search-maxresults-5000.json`). The documented maximum is not verified; page sizes the app uses (tens) are far below any cap.
- There is no jump to row N: tokens only go forward, so a deep scroll pages through every earlier page.

## Saved filters

Fixtures: `filters/filter-search.json`, `filters/filter-my.json`, `filters/filter-get.json`, `filters/filter-favourite-empty.json`, `filters/filter-get-missing.json`, `search/search-by-filter.json`.

- `GET /rest/api/3/filter/search?expand=jql,description,owner` is offset-paged like projects (`startAt`, `maxResults`, `total`, `isLast`, `values`). `expand=jql` is needed to get the JQL; `owner` to get the owner.
- `GET /rest/api/3/filter/my?expand=jql` returns a bare array of the caller's filters, with `favourite`, `isWritable`, `sharePermissions`, `sharedUsers`, `searchUrl`, `viewUrl`, `approximateLastUsed`. `GET /rest/api/3/filter/favourite` returns a bare array (empty here).
- The two filters on the dev site are the ones Jira created for the boards ("Filter for GCM board" with JQL `project = "GCM" ORDER BY Rank ASC`); a board's filter is an ordinary filter and shows up in these lists.
- Running a filter is plain JQL: `filter = 10001 ORDER BY created ASC` through `/search/jql` (`search/search-by-filter.json`).
- A filter you cannot see or that does not exist is 404 with `The selected filter is not available to you, perhaps it has been deleted or had its permissions changed.` (`filters/filter-get-missing.json`).
- The survey did not create filters (writing filters is outside the sandbox rule); creating, sharing and editing filters is out of scope for the app anyway.

## Errors

Fixtures under `errors/`. Statuses were all recorded live unless marked.

| Case | Status | Body | Fixture |
|---|---|---|---|
| JQL syntax error | 400 | `{"errorMessages": ["Error in the JQL Query: ... (line 1, character 11)"], "errors": {}}` | `errors/search-400-bad-jql.json` |
| Invalid query parameter | 400 | Problem-details shape: `{"detail", "instance", "status", "title", "type"}`, no `errorMessages` | `errors/search-400-bad-maxresults.json` |
| Bad or expired `nextPageToken` | 400 | `errorMessages` | `errors/search-400-bad-token.json` |
| Field validation on write | 400 | `{"errorMessages": [], "errors": {"<field>": "<message>"}}` | `errors/create-400-bad-issuetype.json`, `errors/create-400-unknown-field.json` |
| Missing request body fields | 400 | `errorMessages` ("one of 'fields' or 'update' required") | `errors/create-400-missing-summary.json` |
| Bad token or unknown email | 401 | Plain text `Client must be authenticated to access this resource.` (not JSON); header `www-authenticate: OAuth realm="https%3A%2F%2F<site>"` | `errors/myself-401-bad-token.json`, `errors/myself-401-bad-email.json` |
| No permission | 403 | `errorMessages` ("You do not have permission to delete issues in this project.") | `errors/issue-delete-403-no-permission.json` |
| Missing XSRF header on attachment upload | 404 (not 403) | Plain text `XSRF check failed` | `errors/attachment-xsrf-404.json` |
| Issue missing or hidden | 404 | `errorMessages` ("Issue does not exist or you do not have permission to see it.") | `errors/issue-404.json`, `errors/issue-404-unknown-project.json` |
| Concurrency rate limit | 429 | `errorMessages` ("The request has been rate-limited. Please try again later."); headers `Retry-After` (seconds), `ratelimit-reason` | `errors/search-429-rate-limited.json`, `.meta.txt` |
| Removed endpoint | 410 | `errorMessages` | `search/search-legacy-removed.json` |
| Server failure | 500 | HTML page ("Something went wrong"), not JSON | `errors/500-html-error-page.html` |

Consequences for the mapper:

- Three body shapes exist: `{errorMessages, errors}`, problem-details JSON, and non-JSON text or HTML. The error mapper must try JSON and fall back to a trimmed text snippet (never the raw HTML in the UI). Status decides the typed error, the body only supplies the message.
- 404 and 403 cannot be told apart for hidden things: an issue you may not see is 404, with the same message as a missing one. Say "not found or no access".
- 401 has no JSON body; do not parse it. A wrong email and a wrong token look the same.
- `403` on delete was recorded as a side effect: the dev account cannot delete issues in `GCM` while it can in `GTM` (permission schemes differ between the kinds). Tests that clean up must handle a 403 on delete.
- **429 recorded (#18).** A read-only burst of parallel `search/jql` calls on the dev site (30, 80 and 150 parallel: all 200; 300 parallel: 245 x 200, 55 x 429) hit the concurrency limit, not the per-second budget. The 429 carries `Retry-After` in whole seconds (25 to 35 s in that burst, jittered, so honour it rather than assume a value), `ratelimit-reason: jira-max-concurrent-threads-across-all-instances-per-tenant-per-user`, and the JSON body `{"errorMessages":["The request has been rate-limited. Please try again later."],"errors":{},"status":429}`. It has no `ratelimit`, `ratelimit-policy` or `x-ratelimit-*` headers and no `beta-retry-after`; the proactive throttle must not expect them. Fixture: `errors/search-429-rate-limited.json` (body) and `.meta.txt` (status and headers). `Retry-After` is still parsed as seconds or an HTTP date, since only the seconds form was observed.

## Survey part 2 (#14)

Recorded on the dev site on 2026-11-01 with `scripts/record-fixture.sh`. Fixture paths are relative to `tests/Geeratya.Jira.Tests/Fixtures/`. Writes happened only in `GCM` and `GTM`; the issues were labelled `geeratya-test-survey4`. `GTM-4..8` were deleted again; `GCM-5..7` could not be (403, `hierarchy/delete-gcm-403.json`, #19). Writes that answer 204 or an empty 201 have no body, so they have no fixture; the status is given in the text. The agile API lives under `/rest/agile/1.0/`, a separate base from `/rest/api/3/`, with the same Basic auth.

Dev site facts: `GCM` is board 4 (`type: kanban`), `GTM` is board 3 (`type: simple`, the team-managed board). Rank is `customfield_10019` on both (`boards/board-gcm-config.json`, `boards/board-gtm-config.json`: `ranking.rankCustomFieldId`); field ids are per site, resolve them from `GET /rest/api/3/field` (`metadata/field-list.json`, 90 fields; names such as `Rank`, `Epic Link` (10014), `Epic Name` (10011), `Sprint`, `Story point estimate`, `Parent Link`, with `schema.custom` telling the kind).

### Boards

- List: `GET /rest/agile/1.0/board` (`boards/board-list.json`), offset paged (`startAt`, `maxResults`, `isLast`, `total`, `values`). Filters `projectKeyOrId`, `type` (`boards/board-list-filtered.json`). Each board has `id`, `name`, `type` and `location` (`projectKey`, `projectId`, `projectTypeKey`; `avatarURI` is a URL to scrub). Team-managed boards say `type: simple`, company-managed Kanban say `kanban` (a Scrum board would say `scrum`; none on the dev site). One call per board also exists (`boards/board-gcm.json`, `boards/board-gtm.json`).
- Configuration: `GET /rest/agile/1.0/board/{id}/configuration` (`boards/board-gcm-config.json`, `boards/board-gtm-config.json`). `columnConfig.columns[]` is `{name, statuses: [{id, self}]}`, so columns map to status ids only (names come from the project statuses, `metadata/project-statuses-gcm.json`). Both boards have four columns (`Backlog`, `To Do`, `In Progress`, `Done`) with one status each, but the order differs: the team-managed board lists `Backlog` third, after `In Progress`, so never assume the first column is the backlog. Also `filter.id` (the board's saved filter, ordinary filter, see Saved filters), `ranking.rankCustomFieldId`, `type`, and on the company-managed board `subQuery.query` (an extra JQL clause; absent on the team-managed board) and `columnConfig.constraintType` (`issueCount` vs `none`). The JQL the board shows is the filter's JQL plus `subQuery`.
- Kanban board issues: `GET /rest/agile/1.0/board/{id}/issue?fields=...&maxResults=` (`boards/board-gcm-issues.json`, `hierarchy/agile-board-gcm-issues-epic-fields.json`). Offset paged (`startAt`, `maxResults`, `total`), unlike `/search/jql`; there is no `isLast`, compute it from `total`. `fields` works the same as in search. It returns every issue the board's filter matches, in all columns, including sub-tasks and epics (all four statuses are mapped to columns on both boards, so the case of an unmapped status was not observed). A `jql` parameter exists to narrow it; not probed. Issue `self` links point at `/rest/agile/1.0/issue/{id}`, not `/rest/api/3`. The page size cap was not probed.
- Kanban backlog: `GET /rest/agile/1.0/board/{id}/backlog` (`boards/board-gcm-backlog.json`). On a Kanban board with the backlog enabled, "backlog" means the issues whose status is in the Backlog column: moving GCM-1 to `To Do` removed it from the backlog list but not from the board list (`boards/gcm-board-backlog-after-todo.json` against `boards/gcm-board-issues-after-todo.json`). The team-managed board behaved differently: its backlog listed `To Do` and `In Progress` issues and left out only `Done` (`boards/gtm-board-backlog-after-transition.json` against `boards/gtm-board-issues-after-transition.json`). So the backlog is whatever the endpoint returns per board kind; do not compute it from column names.
- Sprints: `GET /rest/agile/1.0/board/{id}/sprint` on a Kanban board is 400 `The board does not support sprints` (`boards/board-gcm-sprints-kanban.json`). Only call it for `scrum` boards (not surveyed: no Scrum board on the dev site, the app is Kanban first).
- Other: `GET board/{id}/epic` lists epics (`done`, `id`, `key`, `name` (empty), `summary`, `color`; `hierarchy/agile-board-epics-gtm.json`; `boards/board-gcm-epics.json` is the empty case), `GET board/{id}/project` the projects, `GET board/{id}/properties` the board property keys (`boards/board-gcm-projects.json`, `boards/board-gcm-properties.json`).

### Ranking

- Rank is the Lexorank string in the Rank field, e.g. `0|i0000e:` (`boards/rank-gcm-backlog-before.json`). Request it with `fields=customfield_10019` (resolved id). Board, backlog and `ORDER BY Rank ASC` (`boards/jql-order-by-rank-gcm.json`) are meant to order by it, but see the disagreement below. JQL `ORDER BY Rank` was recorded for `GCM` only.
- Rank write: `PUT /rest/agile/1.0/issue/rank` with `{"issues": ["GCM-3"], "rankBeforeIssue": "GCM-6"}` or `rankAfterIssue`; one or several issues; 204 with no body. A missing reference issue is 400 with the usual `errorMessages` (`boards/rank-400-missing-issue.json`; the text is the "does not exist or no permission" message, not a rank-specific one). Ranking relative to an issue of another project was also answered 204 (GCM-3 before GTM-4; no body, no fixture), so the app must pick the reference from the same view.
- A rank write changes the values of the moved issue and possibly others (`boards/rank-gcm-backlog-before.json` against `boards/rank-gcm-backlog-after-after-op.json`; the requests in between were two rank writes, 3 before 6 and 6 after 4, and the intermediate state is `boards/rank-gcm-backlog-after-before-op.json`). The listed order and the field values disagree: already in `boards/rank-gcm-backlog-before.json` GCM-6 (`0|i0002e:`) comes before GCM-2 (`0|i00002:`), and `boards/jql-order-by-rank-gcm.json` still had GCM-6 before GCM-4 although 6 has the larger value, a minute after the last write. The cause is unknown (not a lag that closed within a minute; GCM-6 is a sub-task and GCM-3 was once ranked next to a GTM issue, which may matter). Treat the server order as the truth, re-fetch after a rank write instead of re-sorting locally, and do not compare rank strings in the app.
- Move to backlog: `POST /rest/agile/1.0/backlog/issue` with `{"issues": [...]}` (204). On the Kanban board it did not change the status of GCM-1 (still `To Do`, `boards/gcm-board-after-backlog-move.json`) and on the team-managed board GTM-5 stayed `In Progress` (`boards/gtm-board-after-backlog-move.json`): it appears to be a Scrum operation (take an issue out of a sprint); unverified. For Kanban, "send to backlog" is a transition to the backlog status.

### Hierarchy

- Issue types carry `hierarchyLevel` (`metadata/issuetype-list.json`, `metadata/createmeta-issuetypes-gcm.json`): Epic `1`, Story/Task/Bug `0`, Sub-task `-1`; a `subtask: true` flag too. Both kinds use the same levels; team-managed issue types carry `scope: {type: PROJECT}`; the `entityId` shows on the `issuetype` values of `metadata/createmeta-fields-gtm-*.json`. Names differ: `Sub-task` (company-managed) vs `Subtask` (team-managed); match on `subtask`/level, not on the name.
- Parent link is the `parent` field in both kinds: `{"fields": {"parent": {"key": "GTM-4"}}}` when creating (`hierarchy/create-gtm-story-with-parent.json`) and when editing (204, no body); clear it with `"parent": null` (204). In company-managed projects the old `Epic Link` field (`customfield_10014`) still exists and JQL `"Epic Link" = GCM-5` still finds the child (`hierarchy/search-epic-link-legacy-gcm.json`), but write and read `parent`.
- Reading the parent: `parent` in the issue fields is `{id, key, self, fields: {summary, status, priority, issuetype}}` (`hierarchy/search-hierarchy-fields.json`). It is absent when there is none (as in part 1). Sub-tasks are listed in the parent's `subtasks` field as small issue stubs (`hierarchy/search-hierarchy-fields.json`: GTM-6 lists GTM-8).
- Children of an epic: JQL `parent = GCM-5` returns direct children of any level, the same in both kinds (`hierarchy/search-epic-children-gcm.json`, `hierarchy/search-epic-children-gtm.json`). The agile `epic/{key}/issue` and `epic/none/issue` follow the legacy Epic Link model and do not match the `parent` model: `hierarchy/agile-epic-issues-gcm.json` returns only GCM-1 where JQL also returns the sub-task GCM-7, and `hierarchy/agile-epic-none.json` spans both projects and lists issues that do have a parent epic (`hierarchy/agile-board-epics-gtm.json` and `hierarchy/agile-board-epics-gcm.json` list epics per board). Do not use the agile epic endpoints for children; use JQL `parent =` and `issuetype = Epic` (`hierarchy/search-epics-only.json`). A grandchild (sub-task of a child) is not returned by `parent = <epic>`; walk one level at a time.
- Quirk: a sub-task can be created directly under an epic in a company-managed project (201, `hierarchy/create-gcm-subtask-under-epic.json`), and a task can be made a child of an epic and still have sub-tasks. Do not assume only three levels are consistent.
- Create requires `parent` for sub-types (`required: true` in `metadata/createmeta-fields-gcm-subtask.json`, `metadata/createmeta-fields-gtm-subtask.json`), `parent` is optional for Task/Story (`metadata/createmeta-fields-gcm-task.json`) and absent for Epic.
- Deleting a parent with sub-tasks is 400 `The issue 'GTM-6' has subtasks. You must specify the 'deleteSubtasks' parameter` (`hierarchy/delete-400-has-subtasks.json`); the confirm dialog must say that sub-tasks go too.

### Create and edit metadata

- `GET /rest/api/3/issue/createmeta/{project}/issuetypes` lists issue types of a project (`metadata/createmeta-issuetypes-gcm.json`, `metadata/createmeta-issuetypes-gtm.json`; offset paged with `startAt`, `maxResults`, `total`; `isLast` was `null`). `GET .../issuetypes/{id}` lists the fields (`metadata/createmeta-fields-gcm-task.json` and the epic, sub-task, GTM variants). The old `createmeta?expand=projects.issuetypes.fields` form was not used.
- Each field has `fieldId`, `name`, `required`, `schema` (`type`, `system` or `custom`), `operations` (`set`, `add`, `remove`), `hasDefaultValue` and `allowedValues` for select-like fields (priority: Highest..Lowest, five values; issue type and project: the one value). `allowedValues` is absent for free text and users (use the user search for assignee).
- Required on both kinds: `summary`, `issuetype`, `project`. Team-managed additionally requires `reporter` (`metadata/createmeta-fields-gtm-task.json`); company-managed hides it (the creator is the reporter). Sub-types require `parent`. Everything else (assignee, labels, priority, description, due date, components and fix versions on company-managed) is optional. Custom fields on screens differ by kind: team-managed offers `customfield_10021` (Flagged), `customfield_10019` (Rank) and `customfield_10000` (Development) on create, company-managed does not; all offer `customfield_10001` (Team); Start date (`customfield_10015`) is on Task, Story and Epic, not on team-managed sub-tasks. Each field also has `key`, `name` and, for pickers, `autoCompleteUrl`.
- Edit metadata: `GET /rest/api/3/issue/{key}/editmeta` (`metadata/editmeta-gcm-1.json`) gives the same field shape for the fields that can be edited now; it varies by issue (status and type), so fetch it when the editor opens, not at startup.
- Write bodies: `PUT /rest/api/3/issue/{key}` takes `fields` (replace) and `update` (`labels: [{add}]`, `comment: [{add}]`); 204 on success. An unknown or screen-less field is 400 `errors: {"nosuchfield": "Field 'x' cannot be set. It is not on the appropriate screen, or unknown."}` (`adf/edit-400-unknown-field.json`). Description and comment bodies are ADF in v3 (below).

### Transitions

- `GET /rest/api/3/issue/{key}/transitions?expand=transitions.fields` (`transitions/transitions-gcm-1.json`, `transitions/transitions-gtm-5.json`, `transitions/transitions-gtm-8-subtask.json`). Each transition has `id`, `name`, `to` (the target status with category), `hasScreen`, `isGlobal`, `isInitial`, `isAvailable`, `isConditional`, and with the expand a `fields` object (same shape as create metadata) for the fields the transition screen asks for.
- Transition ids are per project, not global: `To Do` is `21` in GCM and `11` in GTM, `Backlog` is `11` in GCM and `31` in GTM. Resolve by the target status, never by a stored id.
- Both dev projects use a simple "all to all" workflow: four global transitions, `hasScreen: false`, empty `fields`. There is no transition with required fields on the dev site and the workflow cannot be changed (outside the sandbox rule), so a required-field transition is not recorded (#31). The shape is the create-metadata field shape; sending a field the screen does not have is 400 (`errors: {"resolution": "Field 'resolution' cannot be set. It is not on the appropriate screen, or unknown."}`, `transitions/transition-with-resolution-field.json`). The UI must gather `fields` where `required` is true before it posts.
- Do a transition: `POST /rest/api/3/issue/{key}/transitions` with `{"transition": {"id": "21"}}`, optional `fields` and `update` (a comment can ride along, not recorded). 204 with no body. Posting the transition to the status the issue is already in was also answered 204 (no body, no fixture). A wrong id is 400 `Transition id '999' is not valid for this issue.` (`transitions/transition-400-bad-id.json`). Unknown issue is 404 (`transitions/transitions-404.json`).
- The status must be reloaded after: the response has no issue. On a Kanban board a transition moves the card between columns; the board does not need a separate call.

### ADF in real data

Fixtures: `adf/issue-gtm5-rich-description.json` (description and two comments), `adf/comments-gtm5.json`, `adf/issue-gtm5-rendered.json` (the same description with `expand=renderedFields`, HTML), `adf/comment-post-rich-gtm5.json`, `adf/comment-post-mention-gtm5.json`. The description was written through the API from a hand-built document and read back.

- The description was built by hand (the request body was not kept) and read back; these node types came back with the shape listed: `heading` (levels 1 and 3), `paragraph`, `hardBreak`, `bulletList` with a nested list, `orderedList` (`attrs.order: 3` kept), `taskList`/`taskItem` (`state: DONE|TODO`, `localId`), `codeBlock` (`attrs.language`), `blockquote`, `panel` (`panelType`), `rule`, `table` with `tableRow`, `tableHeader`, `tableCell` (`attrs` can be `{}` or hold `colspan`), `expand` (`attrs.title`), `inlineCard` (`attrs.url`), `emoji` (`shortName` plus the glyph in `text`), `date` (`attrs.timestamp`, a string of epoch milliseconds), `status` (`text`, `color`), `mention` (`attrs.id` is an account id, `attrs.text` the visible `@Name`, in a comment).
- Marks seen: `strong`, `em`, `strike`, `code`, `underline`, `link` (`attrs.href`), `textColor` (`attrs.color`), `subsup` (`attrs.type`: `sub`). Plain text keeps unicode and emoji (`żółć 日本語 🚀`).
- Media nodes cannot be created from ADF: the `id` is a media-service id that attachments do not expose, and a made-up id is rejected with 400 `ATTACHMENT_VALIDATION_ERROR` (`adf/edit-400-media-node-unknown-id.json`). They can be created through the v2 API: attach a file (`POST /rest/api/3/issue/{key}/attachments`), then `PUT /rest/api/2/issue/{key}` with wiki markup `!pixel.png!` in `description`; Jira converts it. The write was made once with direct `curl` against the dev site (GCM-24, in the sandbox; `record-fixture.sh` refuses the v2 path), the read was recorded with the script: `adf/issue-gcm-media-description.json`. This node comes from the wiki-markup conversion; an image pasted in the web UI may differ (a real `collection`, `alt`, `occurrenceKey`).
- What the renderer sees of that node: The v3 read returns `mediaSingle` (`attrs.layout: "center"`) holding one `media` with `attrs`: `type: "file"`, `id` (a UUID, unrelated to the attachment id `10004`), `collection: ""` (empty), `width`, `height` (183x200 for a 1x1 PNG, so not the real pixel size). There is no `alt` and no filename in the node: name, type and size come from matching the issue's `fields.attachment`, which cannot be done by id (the media UUID is not the attachment id). The renderer cannot resolve a media node to its attachment by id; show a `[image]` marker with the issue's attachment list or a browser link to the issue. `mediaGroup` was not recorded. A comment with media was not recorded.
- Descriptions are `null` when empty, an ADF object otherwise; `fields.description` came back as a full `{version: 1, type: "doc", content: [...]}`. Comments: `GET /rest/api/3/issue/{key}/comment` is offset-paged (`startAt`, `maxResults: 100`, `total`, `comments[]`; `adf/comments-gtm5.json`). A comment has `id`, `author`, `body` (ADF), `created`, `updated`, `updateAuthor`, `jsdPublic`. The issue's `comment` field (`fields=comment`) holds the same, first page only. Posting a comment returns the created comment (201).
- Mention ids and the visible mention text are personal data; the scrubber rewrites both (`scripts/scrub-fixture.py`).
- `renderedFields` HTML exists but is not used (the app renders ADF itself).

### Issue links, remote links, attachments

- Link types: `GET /rest/api/3/issueLinkType` (`links/issuelink-types.json`, wrapper object `issueLinkTypes[]` with `id`, `name`, `inward`, `outward`): Blocks, Cloners, Duplicate, Problem/Incident, Relates.
- Create: `POST /rest/api/3/issueLink` with `{"type": {"name": "Blocks"}, "inwardIssue": {"key"}, "outwardIssue": {"key"}}`: 201 with an empty body (so the new link id is only discoverable by re-reading the issue). Delete: `DELETE /rest/api/3/issueLink/{id}` (204).
- Read: the `issuelinks` field. Each entry is `{id, type, outwardIssue|inwardIssue}`; only the side that is the *other* issue appears, so the direction is told by which key is present (`outwardIssue` present means "this issue <outward text> other", e.g. GTM-5 `blocks` GTM-6; `links/issue-gtm5-links.json`, `links/issue-gcm2-links.json`). The linked issue stub carries `key`, `fields.summary`, `status`, `priority`, `issuetype`. `issuelinks` is also searchable with `fields=issuelinks` (`links/search-issuelinks.json`) and JQL `issueLinkType = Blocks`.
- Remote links: `POST /rest/api/3/issue/{key}/remotelink` with `{"object": {"url", "title", "summary"}}` (201, `{id, self}`; `links/remotelink-post-gtm5.json`), `GET` returns a bare array of `{id, self, application, object}` (`links/remotelink-list-gtm5.json`). They are not part of the issue fields.
- Attachments: the `attachment` field lists `{id, filename, mimeType, size, created, author, content, self}` (`links/issue-gtm5-attachments.json`; `thumbnail` appears for some images, not seen on these two files). `content` is the download URL (needs the Authorization header, so the app opens the browser URL of the issue instead of downloading). Upload is `POST /rest/api/3/issue/{key}/attachments`, multipart field `file`, header `X-Atlassian-Token: no-check`, answer 200 with an array (`links/attachment-post-gtm5.json`; two files in one request, one with a non-ASCII name). A single metadata call is `GET /rest/api/3/attachment/{id}` (`links/attachment-meta.json`), and the limits are in `GET /rest/api/3/attachment/meta` (`links/attachment-settings.json`: `enabled`, `uploadLimit` 1 GiB). Attachments are never rendered in the terminal (project rule): name, type, size and the issue link only.

## Fixture inventory and scrubbing

- Scrubbing: host becomes `example.atlassian.net`, account ids `fake-account-N` (also inside URLs, encoded or not), emails `userN@example.com`, display names `Test User N`, `avatarUrls` emptied, time zones `UTC`. Fixtures are recorded with sorted keys and 2-space indentation so diffs stay small.
- Rate-limit headers and the status line are not part of the fixture files; `RECORD_META=<file>` of the script writes them (stored once: `myself/myself.meta.txt`). The status of an error fixture is in the Errors table; the `search/search-*` fixtures with no status in their name are 200 unless the table says otherwise (`search-unbounded-jql` and `search-order-only` 400, `search-legacy-removed` 410).
- Recording guards: writes are refused outside issues of `GCM`/`GTM`; output that still contains another `*.atlassian.net` host, the token or the email is not written.
- Fixtures were recorded without keeping the request; the requests are given in prose above. Keys are sorted by the scrubber, so property order is not Jira's.
- `search/search-fields-navigable.json` is large on purpose (it is the only fixture showing the full field set of one issue, including the per-site `customfield_*` ids); trim it if a test needs less.
