## Shell

The shell is one full-screen window with a body, a one-line status line at the bottom and overlays on top. The first frame is drawn before any network reply. Until views exist (M1) the body is empty apart from a hint line; the M1 views (tab bar, list, columns, issue detail, source picker, network banner) are specified in [ux-screens.md](ux-screens.md).

## Modes

The input mode decides which keys act. It lives in `AppState.Mode`, except Visual: it is a state of the tab (`TabState.VisualAnchor`) over Normal mode, so every Normal key still works and the badge reads `VISUAL`; Help and Command show their prompt in the status bar; Insert shows the `:profile add` steps as a centred box (title with the step `[n/4]`, what the answer is for, `> text_` with the token masked, the keys) and keeps only `[n/4] label` in the status bar, falling back to the whole prompt there when the screen is too small (`ProfileFormOverlay`); Confirm shows a centred dialog and only the short `Confirm  (y/n)` in the status bar.

| Mode | Entered with | Keys | Left with |
|---|---|---|---|
| Normal | start, or leaving any other mode | the Normal table in `keymap.md` | (home mode) |
| Visual | `v` in a list or backlog view (or a drag over rows; on a Scrum backlog a drag that ends in another section asks to move the rows instead, see `ux-mouse.md`) | the Normal motions (`j k Ctrl-d Ctrl-u g g G`, the wheel) extend the range; the write keys act on it as a set (`Alt-m` marks the range); read-only itself, it writes nothing | `v`, `Esc` (a second `Esc` then clears the marks) |
| Help | `?` | `j`/`k` or `Down`/`Up` and `Tab`/`Shift-Tab` move between sections; `J`/`K` scroll a line, `D`/`U` or `Ctrl-d`/`Ctrl-u` half a page (8 lines); `/` filters (printable keys are text until `Enter` or `Esc`); `?`, `q` and `Esc` close (with a filter set the first `Esc` or `q` clears it) | `?`, `q`, `Esc` |
| Command | `:` | printable keys and `Space` are text; `Enter` runs, `Backspace` deletes, `Esc` cancels | `Enter`, `Esc`, `Backspace` on empty text |
| Confirm | a destructive action asks | only `y`, `n`, `Esc` and `Ctrl-c` (quit) act; every other key is swallowed, `Enter` never confirms; the two rows and the backdrop are clickable | `y` (runs the action), `n`, `Esc`, a click outside the box (cancel), `Ctrl-c` (quits; asks first while writes run) |
| Insert | `:profile add` (the first editable form), the jump-to-issue prompt (`<space>g`, same choose keys as the picker), the source picker (`<space>t`, adds `Up`/`Down`/`Ctrl-p`/`Ctrl-n`/`Ctrl-j`/`Ctrl-k` to choose, `Ctrl-l` accepts like `Enter`, so in a paragraph field or the comment editor it adds a line; `Ctrl-j` arrives from Terminal.Gui as Ctrl+Enter and is mapped back), the comment editor (`<space>m a`/`m e`; `Enter` is a new line, `Ctrl-s` saves, arrows move; `Esc` asks first when the text changed), the link form (`<space>il`) and the field form (`<space>ie`, `<space>ia`, `:edit`, `:priority`, `:labels`, `:assign`; adds `Tab`/`Shift-Tab` for fields and `Ctrl-s` to save, see [ux-screens.md](ux-screens.md), "Field form overlay") | printable keys and `Space` are text; `Enter` accepts the field, `Backspace` deletes, `Esc` and `Ctrl-c` cancel (never quit) | last `Enter`, `Esc`, `Ctrl-c` |

In Insert mode printable keys are text and only `Esc`, `Enter`, `Ctrl-` and `Alt-` combinations act.

**Single-line prompts have a caret.** The command palette, the source and sprint pickers, the jump prompt, the help filter, the profile form (`:profile add` and edit) and the text of every field form (the filter or label buffer of a choice or label field, the value of a text, number, date or paragraph field) share one editor (`PromptText` in Core). Typed and pasted text goes in at the caret. `Left`/`Right` move by a character (a wide character, emoji or combining sequence is one step), `Home`/`End` to the start or end (in the palette also `Ctrl-a`/`Ctrl-e`; in a paragraph field the caret's line), `Ctrl-Left`/`Ctrl-Right`, `Alt-Left`/`Alt-Right` and `Alt-b`/`Alt-f` by a word; `Backspace`/`Delete` remove a character, `Ctrl-w`, `Ctrl-Backspace` and `Alt-Backspace` the word before the caret, `Alt-d` and `Ctrl-Delete` the word after it, `Ctrl-u` everything before it (on the caret's line). The caret is drawn `_` after the last character and `|` between two characters; a text longer than the box is cut around the caret with `…` at the cut sides. Differences from Gitunia: `Ctrl-k` (delete to end) is not bound, because `Ctrl-j`/`Ctrl-k` choose rows in Insert and Command mode here; `Ctrl-a`/`Ctrl-e` are not Home/End in Insert mode because they are `profile.add`/`profile.edit` in the profile list; the comment editor shares the word and line deletes (`Ctrl-w`, `Alt-d`, `Ctrl-u`). In the profile form the token field takes the same keys but shows one `*` per letter with the caret mark in place (`|` or `_`), never the text; moving to another field puts the caret at its end.

Paste (terminal paste, e.g. `Ctrl-Shift-V`) fills the active Insert field, and the Command palette, in every form step. Terminal.Gui delivers a bracketed paste as one `Application.Paste` event (not as keys), which the shell turns into a `TextPasted` command; terminals without bracketed paste send plain key events and already work as typing. In a single-line field only the first non-empty line is used and control characters are dropped, so a trailing newline never submits a step; the comment editor keeps all lines. The token stays masked and is never printed or logged.

## Hints

Two helps, each set with `:set hints.statusBar full|minimal|off` and `:set hints.whichKey on|off` (`:set` alone opens the Messages overlay with every setting, one line each with value, default and help; `:set <name>` shows its value, default and accepted values on the status line, kept under 80 columns). The choice is saved in `settings.json` in the configuration directory (only the changed value is written; comments are kept, see [settings.md](settings.md)) and hints default to `full` and the popup to on.

- **Status bar hints** (right side of the status line): the main keys of the active screen (list, columns, issue detail, source picker, field form) plus the global ones (`? help`, `: commands`, `q quit`). Each hint names an `ActionId` and a short label; the key shown comes from the keymap, and a hint whose action is unbound is left out. A hint whose actions are all above the command level (`everyday` by default) is left out (`ux-keymap.md`, rule 4). `minimal` shows only `? help  : commands  q quit` in Normal mode (the prompts of other modes keep their hints, they are the way out); `off` hides the whole right side.
- **Which-key popup**: while a multi-key binding is half typed in Normal mode (`g`, `<space>`, `<space> i`), a box at the bottom right of the body (flush right, the body stays visible to its left, as in Gitunia) lists the keys that continue it: the key, and the action title from `ActionCatalog`, or `+group (n)` for a longer chain. It opens 250 ms after the pending prefix (an injected tick, no timer thread), so a fast chord never flashes it; it lists plain actions first in clusters of related actions (shared id prefix, blank line between clusters), then the `+more` groups named by noun (`i` issue, `m` comment, `k` rank, `s` sprint, `v` view), each part alphabetical; the blank lines go when it does not fit. It disappears when the sequence completes or breaks, and is generated from the keymap, never written by hand. Actions above the command level are left out, and a group with no action left disappears with them (`<space>k` shows only at the advanced level).

## Focus model and key style

- Keys are spelled out everywhere: `Ctrl-d`, `Alt-1`, `Shift-Tab`, `<space>o`; never `^d` or `c-d`.
- Exactly one place has focus: the overlay when one is open, otherwise the body. An overlay takes every key; nothing falls through to the body.
- `Esc` backs out one level: it clears a half-typed sequence or ends the status message (`<space>x` does too), closes an overlay or cancels Command and Confirm mode. In a tab at the view root it first leaves Visual mode, then clears the marks (`docs/ux-keymap.md`, "Selection and counts"); then it pops the issue stack (issue detail back to the view it was opened from; the stack pops before any mark is cleared). In Normal mode with nothing to back out of, `Esc` does nothing; it never quits.
- `Ctrl-c` quits from Normal, Help, Command and Confirm mode. In a text form (Insert mode) it cancels and never quits. A quit cancels the running read loads at once; running writes are not cancelled (see below).
- `q` quits only in Normal mode. In Help it closes the overlay first (a second `q` quits); in Command mode it is text; in Confirm mode it does nothing (the question is answered with `y`, `n` or `Esc`).
- Every quit (`q`, `Ctrl-c`, `:q`) asks first while writes are running (`1 write is still running; its result will not be shown. Quit anyway?`, `y`/`n`/`Esc`); after the `y` the app waits up to 5 s for them to finish before it exits; so do `:profile switch` and removing the active profile.
- Multi-key bindings (`g g`) show the typed prefix in the status line; any key that does not continue the binding drops it.
- A key that no mode binds is ignored silently.

## Confirm mode

Destructive or hard-to-undo actions (delete, bulk edits, transitions that may fire workflow side effects (a move to a done status, or a screen with nothing to fill in; other single transitions do not ask; see `architecture.md`, "Write pipeline", Confirm flow), changing assignee or sprint for many issues) ask first. The dialog says exactly what will change and that Jira cannot undo it, and answers only to `y`, `n` and `Esc`; `Enter` never confirms. The reducer receives a `ConfirmRequested` command with the question and the action to run on `y`.

The dialog (`ConfirmOverlay`, sized by `ConfirmDialog` in Core) is a box centred over the body: the title (`Confirm`, or the action and its target such as `Move GCM-8`), the question wrapped to the box (it names issue keys and counts), a blank row and the warning (the sentences that say nothing can be undone, in the warning colour, bold in the no-colour tier), a blank row, then `y  <name of the action>` and `n  Cancel`. The wording of each question is the one the request carries (`ConfirmRequest`); the label of the `y` row is its `Label` (`Delete issue`, `Remove link`, ...). The box shrinks to its longest line (at least 30, at most 62 columns) and needs 4 columns of margin. Deletes, transitions, completing a sprint and moving several issues to a sprint use the bad frame colour.

- Only `y` runs the action, after the dialog has closed; `n` and `Esc` cancel; `Ctrl-c` quits (it asks first while writes run); every other key is swallowed and nothing behind the dialog moves.
- Mouse: the `y` and `n` rows are clickable (same as the keys); a click anywhere outside the box, the status line included, cancels like `n`; a click inside the box but off the rows does nothing (`ux-mouse.md`).
- What the action does is fixed when the dialog opens (the request carries the write), not when `y` is pressed. The input mode before the dialog is restored when it closes (the comment editor gets its text back).
- If the dialog does not fit the terminal (under 28 columns, or fewer rows between the tab bar and banner and the status line than the wrapped text needs, 8 for a short question) it is not shown and the action does not start: the status line says `Terminal too small to confirm. Nothing was done; enlarge it and try again.` An answer nobody can read is no confirmation. A dialog that stops fitting after a resize is closed unanswered, with a warning in the status line, and nothing runs. Until the first size is reported (the first frame) the check is skipped and the status line keeps the whole question.

## Profiles

A profile is a Jira site plus an account (`Core/Profiles`); one is active. The palette manages them:

- `:profile add` (or `Ctrl-a` in the profile list, or the Add button) opens the Insert-mode form with all four fields at once: name, site URL (https; a bare host gets `https://`), account email, API token. `:profile edit [name]` (or `Ctrl-e` / the Edit button in the list) opens the same form filled with the profile (the active one without a name). The token is masked (`*` per character), never shown again, never printed, logged or kept in a printable value (`SecretText`); when editing, an empty token field says "kept (type to replace)" and the stored token stays. Keys: `Tab` / `Shift-Tab` (or a click) move the focus, `Enter` validates the field and moves on (on the token it saves), `Ctrl-s` validates every field, focuses the first problem and saves, `Alt-t` (or the Test connection button) asks `/myself` with the typed values (or, when the token field is empty, the stored token) and shows `Connected as <name>.` or `Failed: <reason>` in the box without saving anything (an edit that changed the site or account needs a typed token to test: the stored token is sent only to the saved site; an edit of a field ends a running test and drops its answer), `Esc` cancels. Validation runs as you type (empty name, a name used by another profile, a non-https URL, a malformed email, an empty token on add; the note is the line under the fields, or the status line when the box does not fit). Saving an add stores the token in the OS secret store under the profile's credential key and saves `profiles.json`; the first profile becomes active. Saving an edit replaces the profile in place (same position, the active mark follows a rename); when the site or account changed the kept token moves to the new credential key (a typed token is stored under it) and, when no other profile shares the old key, the old token and the old local data (cache, history, saved views, board kinds) are deleted. Editing the site or account of the active profile goes through the profile-switch path (`ProfilesChanged` with a different active profile: views and cache dropped, connection rebuilt, check run); replacing only its token rebuilds the connection the same way (`ProfilesChanged.Reconnect`). With no profile, `:profile` opens the (empty) manager; only `:profile add` opens the form directly.
- No secret store (Linux without `secret-tool`, macOS without `security`, or an unknown system): the profile is still saved and the status line says to set `GEERATYA_TOKEN`. A store that fails (locked keyring) reports the error and saves nothing.
- `GEERATYA_TOKEN` is one token for the whole process, so it is used only while exactly one profile exists. With several profiles a profile without a stored token does not connect and the status line says to store a token for it (`:profile edit` and type it; without a secret store several profiles are not usable); the variable is never sent to another profile's host. A profile already connected through the variable stays connected after a second profile is added; a switch back then needs a stored token.
- `:profile list` (or `:profile`) opens the profile manager, a full-body two-pane screen (Insert mode, the tab row shows a single `Profiles` chip): the profiles on the left with the active one marked, the details of the highlighted one on the right (name, site, account, where the token comes from: `OS secret store`, `env GEERATYA_TOKEN` or `not set`, never the token, and the connection status, which is known only for the active profile; a source still being looked up reads `looking up...`). The bare command runs at once, with no argument to type (the usage line reads `profile [list]|add|...`). With no profile saved the manager is the first screen at start (and `:profile` opens it too); `Down`/`Up` choose, `Enter` switches (the same switch as `:profile switch`), `Enter` on the active profile just closes the manager, `Ctrl-a` adds, `Ctrl-e` edits the highlighted profile, `Ctrl-x` asks to remove (the same question as `:profile remove`), `Esc` closes; the form and the remove question open over the manager and return to it when closed or saved; a click on a row switches, a right-click asks to remove, the Add and Edit buttons do what `Ctrl-a` and `Ctrl-e` do. A switch or removal is refused with "Still saving" while a profile change is being saved.
- `:profile switch <name>` makes another profile active and saves the choice. The connection is replaced: views and the memory cache belong to the active profile and are dropped with it (the disk cache of a profile is kept until the profile is removed). `AppState.Session` holds the tabs (the cache is a host object dropped by the same effect, `docs/architecture.md`, "Cache and refresh"); when `ProfilesChanged` changes the active profile (including removal of the active one) the reducer replaces it and emits `DropSiteCacheEffect` for the old profile. The host (`SiteConnections`) then closes that connection and builds the new one from the profile's site, account and token; a failure reply for a profile that is no longer active is ignored.
- Connection check: at start, after `:profile add` and a switch, and on `:profile check`, the shell asks `/myself` (off the UI thread, after the first frame). `SiteSession.Connection` is `Checking`, `Connected(display name)` or a failure with its kind and hint (no token, 401 token or email wrong, 403, cannot reach the host, timeout, host refused, 429). The start screen and, when no notice or pending keys occupy it, the status line show `Connected as <name> on <host>` or the hint; the token and the email are never repeated in them. A reply for a profile that is no longer active is ignored.
- `:profile remove <name>` asks in Confirm mode, naming the profile, site and account and saying the removal cannot be undone, then deletes the profile and its token (the token stays while another profile uses the same site and account).
- A `profiles.json` that cannot be parsed is ignored, a copy is kept as `profiles.json.corrupt`, and the status line says so at start. A start without a home directory (`HOME` unset and no absolute `XDG_*` directory) prints the reason to standard error and exits with code 1.

The start screen shows the active profile; when there is none the profile manager is shown instead (first run), and closing it leaves the start screen with `:profile`. Mouse paths for these commands are in [ux-mouse.md](ux-mouse.md) (part O, the profile list rows and the profile form buttons).

## Command palette

`:` or `Ctrl-p` opens the palette (Command mode, #368; shaped by Gitunia's palette): a box over the body that lists every action with its keys, under group subheaders, with a query line, a `shown/total` count chip in the top edge and a footer of key hints, and the typed text also on the status line. Typing filters fuzzily by title or action id (a substring of the title ranks first, then of the id, then letters in order); the highlight returns to the first row at every keystroke. `Up`/`Down`, `Ctrl-p`/`Ctrl-n`, `Ctrl-j`/`Ctrl-k` and the wheel move the highlight; `Enter`, `Ctrl-l` or a click runs the highlighted action exactly as its key would, through the same input path as keys and the mouse, after the palette has closed (so a form or a Confirm opens as usual, and destructive actions still ask); `Esc` closes. An empty filter and `Enter` run the first row. Each row shows the title and every Normal-mode binding of the action (user rebinds show). Rows sit under non-selectable subheaders from `ActionCatalog.GroupOf` (`Issue`, `Comment`, `Rank`, `View`, `Tabs`, `Navigate`, `General`; a test fails when a bound action has none); inside a group the actions of the focused view (those of the right-click menus for the cursor and the view) come first. A blank line precedes each subheader but the first and is dropped when the list does not fit. Listed: every action except the modal-only ones (Confirm answers, picker, form, editor and palette keys), the palette's own opener and `Esc`; commands without a key (`labels`, `priority`) are listed too and run as their command line; so is one row per theme (group `General`, title `Theme: <name>`, running `theme <name>`; the names come from the host in `AppState.ThemeNames`, set at start, since Core knows no themes; #387); an action bound ahead of its feature (`ActionCatalog.Unimplemented`) is greyed and says "not yet" instead of running. Command level (#196): at the `everyday` level the unfiltered list leaves the advanced actions out and ends with a muted note `N advanced commands hidden; type to find them`; the unfiltered list also leaves the theme rows out at every level (about 20 would push the notes below the fold at 80x24, #416) and ends with a second note `N themes hidden; type "Theme:" to pick one` (`theme` alone is a command line and shows usage, so the note names the row prefix); a typed filter searches every action and every theme, so an advanced one runs from the palette (a level hides, it never disables).

Typed commands stay: when the first word is a command name (`quit`/`q`, `help`/`h`, `profile ...`, `tab ...`, `history clear`, `theme [name]`, `set ...`, `keys reload`, `layout ...`, `browse KEY`, `labels`, `create [subtask]` and the view commands `jql [query]`, `filter [name]`, `board [name]`, `backlog [name]`; the list is generated in [keymap.md](keymap.md), see [ux-screens.md](ux-screens.md), "Palette commands") the text is a command line and `Enter` runs it, never a row, and the list shows that command's usage line (so a bare `tab` or `jql` shows usage, not rows; the issue text said "followed by a space", a bare name is read as a command too so `:jql`, `:board`, `:quit` keep working). Text that is no command and matches no row shows "Unknown command: ..." in the status line.

Not yet: theme entries in the list (the theme names live in the rendering layer; `:theme [name]` stays typed).

## Help

`?` opens an overlay generated from the keymap and the action catalog, in pages (below); it is never hand-written. It lists the everyday bindings and the `All actions` page ends with `(N advanced commands hidden; <space>* shows them)`; `<space>*` works inside help too and switches the command level at once (`:set commandlevel advanced` keeps it). A test checks that every non-modal action has a description, a group, a level and a key, and that the `All actions` page at the advanced level lists every bound action.

**Pages (#371, from Gitunia's help overlay; popup frame #456).** Help is a framed popup over the view of the tab (the view stays visible above and below it; up to 96 columns, centred, one row from the top and the bottom; on a very small body it fills it), `HelpOverlay`. Inside, a menu of the page names on the left with the active one marked `> ` and the shown page beside it; the filter shows in the title (`Help  / text_`). `j`/`k`, `Down`/`Up` and `Tab`/`Shift-Tab` move between sections (the first two stop at the ends, `Tab` wraps; a click on an entry shows it, `HelpPage` target in [ux-mouse.md](ux-mouse.md)), `J`/`K` and `D`/`U` scroll as above, the wheel scrolls 3 lines wherever the pointer is. The Messages overlay keeps `j`/`k` as scroll (it has no sections). Long rows wrap at spaces with a hanging indent under the title. Differences from Gitunia, with reasons: the menu is always shown (Gitunia uses a tab row below five pages; Geeratya has four or five pages, so one layout keeps the clickable names in the same place), the filter narrows the shown section only (the `All actions` page already lists every action once, so a cross-section filter would repeat it), `g g` and `G` jump to the first and the last line of the shown page (`help.top`, `help.bottom`; the last line stays at the top, as far as `J` reaches). The shown page is generated by `HelpPages` and starts at its first line. Pages in order: the active layout (`List`, `Columns`, `Backlog` or `Issue detail`; none without a tab), `Global`, `All actions`, `Commands` and, only when `keymap.json` changed something, `Custom`. Geeratya keeps the same keys in every view, so there is no per-view key table: each catalog action carries an applies-to tag (`ActionScope`, `ActionCatalog.ScopeOf`; an untagged action is global) and the layout page lists the tagged actions that have a key, `Global` the untagged ones. `All actions` lists every action that has a key once, under the `ActionCatalog.GroupOf` groups of the palette, and a last group `Dialogs` with the keys that only work inside a dialog or the help (confirm, form, editor, picker, help filter and page keys). One row per action: the main key (first Normal-mode binding) in the keys column, the other keys after the title in parentheses. The command level applies as before (`All actions` ends with the hidden count). `Commands` is the palette commands table. `Custom` lists each binding the user's file added or changed (key, title and action id, mode when not Normal) and `Unbound: <keys>` for a removed default; skipped rows are not there (the Messages overlay keeps them). `/` opens a filter line (a case-insensitive match on any key of the row, the title or the action id; the status line shows `j section  J scroll  / filter`); printable keys, including `j`, `k` and `q`, are then text, `Backspace` deletes, `Enter` keeps the filter so the keys act again, `Esc` clears it and a second `Esc` closes help (`q` and the `help.close` action behave the same). `Ctrl-c` still quits. A page and filter reset when help closes; the Messages overlay shares the mode but has no pages or filter. The completeness test (every bound action is on the `All actions` page with a title, a group and a level) stays the gate.

## Status bar

The bottom line is a bar of exactly the terminal width. It starts at column 0 with a mode badge as a filled bold chip (` NORMAL ` accent, ` VISUAL ` remote, ` INSERT ` good, ` COMMAND ` warn, ` CONFIRM ` bad, ` HELP ` and ` MESSAGES ` info; reversed-free bold in the no-colour tier, bracketed `[NORMAL]` in the ASCII glyph set), a space, then the mode's text: the pending keys or message in Normal mode, `:text` in Command mode, `Confirm  (y/n)` in Confirm mode (the question is in the dialog; the status line keeps the question only when no dialog is drawn), `[n/4] label` in Insert mode (the typed text, the token masked, only when the box does not fit). Short key hints are right-aligned chips (`HintBar`: the key bold in the key role, the label muted, two spaces between chips; a message is drawn in its severity role on the bar background): the screen hints of the active tab first, then the global `? help`, `: commands`, `q quit`. The screen hints are the main keys of the layout, from the keymap: list `j/k move`, `Enter open`, `<space>o browser` (plus `<space>l columns` on a board); columns `za sub-tasks` (first; only while the cursor is on a card with sub-tasks or on one of them), `h/l column`, `j/k card`, `Enter open`, `<space>l list`, `<space>o browser`; issue detail `j/k scroll`, `Enter open`, `Esc back`, `<space>o browser`, `<space>p parent`, `]] pane` (last of its screen hints, in the detail and the Scrum backlog). Each hint names its action id (a pair like `j/k` names two) and a test checks that the default keymap binds it; a remapped key shows up. The global hints are kept as long as they fit; the screen hints are dropped one by one from the end first (as in Gitunia). In Normal mode with no notice or pending keys the text starts with the network word of the active tab (`offline`, `rate limited 25s`, `stale`, `error`, `loading`), then the connection line. When the line is too narrow the hints are dropped first, then the text is cut (wide characters are never split).

**Status messages (#369, from Gitunia).** Every notice is a message with a severity, a lifetime counted from the injected `Tick` (or the key press that carries a time; the reducer reads no clock) and a place in the history. Info lasts 5 s, a warning 15 s, an error 30 s. Warnings and errors start with `Warning: ` or `Error: ` (never colour alone) and are drawn in the warning or error role over the bar; info is drawn in the success (good) role and, for its first 1.5 s after it is stamped, as a filled chip (bold reverse, so the no-colour tier shows it without colour; the host redraws when the chip ends, at the next one-second tick). Failed writes, a failed profile or secret-store step, an unusable keymap or cache write and refused browser opens are warnings or errors; the rest is info. A key press no longer clears a message; it ends by expiry, by `Esc` in Normal mode when nothing else claims it (no chord, count or rank pickup; it comes before the issue stack's back-out), by `<space>x` or by being replaced. The same text while it still shows is not posted again and does not renew the timer; a warning or error posted again once its lifetime has passed shows and is recorded again. The last 50 messages are kept, newest first; `<space>n` (or a click on the message) opens them in an overlay on the help screen's mode (badge `MESSAGES`; `j`/`k` scroll, `Esc`/`q` close). Reducers post by setting `AppState.Message` (and `MessageSeverity`, or `StatusMessages.Warn`/`Fail`); `AppReducer` settles the result into `AppState.Status` and the history, so a reducer that clears `Message` changes nothing. A write's "started" text (`Saving ...`) is a message too and is replaced by its result.

## Colour tiers

Colours are decided by roles (`PaletteRole`) in `PaletteTable`, from the colours of the active theme ("Themes" below); views never name a colour. Three tiers, picked from `ConsoleCapabilities`: 24-bit (`COLORTERM=truecolor` or `24bit`), 16-colour (forces Terminal.Gui's 16-colour output) and no colour (`NO_COLOR` set, `TERM=dumb`, `TERM=vt100` and relatives, redirected output); classic consoles (Linux `TERM=linux`, Windows console host) are capped at 16 colours even when `COLORTERM` claims more, and use the ASCII glyph set. In the no-colour tier meaning rests on text attributes (the status bar is reversed, error and network roles are bold or underlined), so nothing relies on colour alone. Text roles must reach contrast 4.5 against their background, the divider role 3.0, in both colour tiers, for every built-in theme (tested; the 16-colour check uses typical xterm values on a dark terminal and a table with darker normal colours on a light one). Network-state roles (error, loading, offline, rate limited, stale) tag the network banner and its badge (`TextRole.Offline`, `RateLimited`, `Stale`, `Error`); see [ux-screens.md](ux-screens.md), "Connection check and network states".

**Themes (#198, shaped by Gitunia).** A theme is a JSON file (comments and trailing commas allowed). Built-in themes are the same files, embedded in the binary: `auto` (default, see below), `catppuccin-mocha`, `catppuccin-macchiato`, `catppuccin-frappe`, `catppuccin-latte`, `high-contrast` (text at 7:1 or better at 24 bits), `tokyo-night` (and `-storm`, `-moon`, `-day`), `gruvbox-dark-hard|medium|soft` and `gruvbox-light-hard|medium|soft`, `dracula`, `nord`, `solarized-dark`, `solarized-light`, `rose-pine` (and `-moon`, `-dawn`). Published palettes (all MIT) with only the colours that must pass contrast nudged. `dark` and `light` are accepted names for `catppuccin-mocha` and `catppuccin-latte` (there is no separate generic palette); `auto` (the default) picks `catppuccin-latte` on a light terminal background and `catppuccin-mocha` otherwise (see below). The colour modes stay 24-bit, 16 colours and none; there is no 256-colour tier. `:theme [name]` switches live (no name: lists the theme families and any files that were not used, because the status line is one row; `:theme tokyo` lists the names that contain the word when it is not a theme itself) and saves the name in `settings.json` (`theme`). A saved theme that cannot be used starts as `catppuccin-mocha` with a status line notice.

`auto` (#375): before the UI starts (whatever theme is saved, so `:theme auto` works later), the terminal is asked for its background with OSC 11 (followed by a DA1 query, whose reply ends the wait early; 50 ms at most for a terminal that stays silent). No answer falls back to `COLORFGBG`, then to dark. The query is skipped when not interactive, at `NO_COLOR`, for `TERM` unset, `dumb`, `linux`, `ansi`, `cons25` or the `vt100` family, and on Windows (unsupported: only `COLORFGBG` is read there); Linux and macOS ask. The answer is kept: `:theme auto` later in the session uses it (the terminal cannot be asked once the UI owns the input) and saves `auto`. A reply still under way when the 50 ms end (or any reply over SSH) gets a second window of 250 ms, so a late reply never reaches the UI as keystrokes. Detection happens once per start, so a terminal switched between light and dark needs a restart.

Your own themes are `themes/<name>.json` in the configuration directory; the lower-case file name is the theme name and a user file wins over a built-in of the same name (`dark`, `light` and `auto` and names with a space cannot be used). The folder is read once at startup, so edits show after a restart; a file that cannot be read or is invalid is not offered and the reasons show on the status line at startup and in `:theme`. User themes are not checked for contrast.

```jsonc
{
  "version": 1,            // optional; the only format there is
  "variant": "dark",       // required: dark or light, the side of the terminal the theme is made for
  "colors": {              // all required, "#rrggbb" only
    "accent": "#89b4fa", "good": "#a6e3a1", "bad": "#f38ba8", "remote": "#cba6f7", "warn": "#f9e2af",
    "info": "#89dceb", "muted": "#979db5", "border": "#6c7086", "barBackground": "#181825",
    "selection": "#45475a", "baseForeground": "#cdd6f4", "baseBackground": "#1e1e2e",
    "overlayBackground": "#1e1e2e"   // optional: the fill of an overlay box; default baseBackground
  },
  "ansi": { "accent": "brightBlue" }   // optional 16-colour overrides, see below
}
```

`PaletteTable` builds every role from these colours (headings, links and in-progress statuses use `accent`; done, stories and code `good`; errors and bugs `bad`; epics and stale `remote`; keys, editable fields, rate limits and the `Warning` role (the Confirm dialog's warning line, bold) `warn`; loading, field labels and sub-tasks `info`; the status bar sits on `barBackground`, the selected row on `selection`; an overlay box is filled with `baseBackground` (or `overlayBackground` when the file sets it) and the view behind it is always `baseBackground` moved towards black: `high-contrast` (black page) and `rose-pine` (too dark a page to step down visibly) do, #559). The theme's background is always painted, so it looks the same on any terminal background; keeping the terminal's own background is not offered (#566). An unknown key is ignored; a missing or malformed colour, an unknown `variant` or `version` or a bad `ansi` entry refuses the file, one reason each.

**The 16-colour rule.** At 16 colours the terminal's own palette decides what the named colours look like, so a theme cannot carry its hex values there. The `variant` picks the built-in 16-colour table (dark: bright accents on black; light: normal-intensity accents on white; selection and status bar are white on blue in both) and the optional `ansi` object overrides single colours (`accent`, `good`, `bad`, `remote`, `warn`, `info`, `muted`, `border`) with one of `black blue green cyan red magenta yellow gray darkGray brightBlue brightGreen brightCyan brightRed brightMagenta brightYellow white` (case-insensitive). Selection stays reversed without colour in every theme. The built-in dark table uses bright cyan for the accent, because xterm bright blue does not reach contrast 4.5 on black; the 16-colour contrast test uses a table with darker normal colours for the light variant, because the xterm normal colours fail on white. Only built-in themes are held to the contrast tests (24-bit and 16 colours), user themes are not. Core knows no themes: `:theme` is an effect answered by `ThemeApplied`, and only an applied theme is saved; this replaced the first attempt (PR #356) and there is no generic hardcoded dark or light palette.

Screens produce styled text, not colours: Core's `TextRole` (body, muted, heading, strong, emphasis, code, link, quote, selected, key, the three status categories, the five issue-type colours, error) tags each `StyledSpan`, and `PaletteTable.For` maps it to a `PaletteRole`. Selection is reversed and bold in the no-colour tier, so it never rests on colour alone; emphasis and quotes use italics there, links underline, strong and headings bold. The colour tiers apply the same bold, italic and underline as the no-colour tier (so emphasis shows everywhere) but never reverse, since a role there has its own background.

## Not adopted from Gitunia

Gitunia's interaction design (`docs/internal/ux.md`, `ux-keymap.md`, `ux-settings.md`, `ux-look.md`, `ux-mouse.md` there; issues #368 to #373) was adopted where Geeratya had diverged without a reason. The whole-product audit #560 compared the live binary with Gitunia area by area; every gap it found is an issue, and these differences are intended:

| Gitunia | Geeratya | Why |
|---|---|---|
| Repeat mode (bare step keys after one step) | none; rank steps take counts (`3 Alt-k`) | the only steppers are rank keys; there is nothing to resize or nudge |
| Pane focus keys (`Ctrl-h/j/k/l`, `Ctrl-w`), pane resize, zoom, drag to resize | `h`/`l` between columns, `] ]` and `[ [` between sections; no resize | panes are content-driven (columns, sections), not a fixed pane set |
| In-view find (`/`, `n`, `N`) and clipboard copy (`y`, OSC 52) | not included (decision #467) | README Features does not list them; JQL and saved views narrow a list, `<space>g` jumps to a known key |
| Character selection (`Alt-v`) | none | Visual selects issues, there is no text to select |
| Per-view key rows and a `view` field in the user file | the same keys in every view; an applies-to tag on the action drives contextual help | one key set to learn |
| Three command levels | two (`everyday`, `advanced`) | two are enough until the keymap grows |
| One `config.json` with `keys` | `keymap.json` (never written by the app) and `settings.json` (app-written) | different writers; the keymap already shipped |
| `<space>m` message history, `<space>.` actions menu | `<space>n`, `<space>a` (issue) and `<space>A` (tab and view) (decisions #465, #468) | `<space>m` is the comment group; already built and taught |
| Visual as an input mode | a state of the tab over Normal mode | its keys are exactly the Normal keys |
| Graph lanes, branch label caps, diff colours, `labelCaps` | issue-type and status-category colours, no Powerline caps | Geeratya must not look like a Git client |
| Repository picker with pins, recents and discovered folders (`scanRoots`) | source picker with boards, filters, saved views and recents; profiles instead of repositories | Jira nouns; one site is active at a time |
| Fetch, pull and push chips, operation banner, dirty and ahead/behind markers, file polling | network banner and `STALE` banner, `<space>r` refresh, `!` failed and `…` loading tab markers, refresh of the active tab only | there are no remotes or working trees; a Jira view is stale by age |
| Session restore of tabs, the active tab and focus | remembered tab definitions (`tabs.json`); rows come from the cache | views reload, so a stored cursor or scroll position could point at other rows |
| No right-, middle- or Ctrl-click bindings (#479 there), a `...` marker opens the row menu | right-click menus and Ctrl-click marks (full mouse support is a README feature, `ux-mouse.md`); a `...` marker is planned (#572) | the right-click paths shipped first; the marker is for multiplexers that swallow them |
| Double-click accepts a picker row | a single click on a picker, jump or palette row runs it | Gitunia's single click only highlights, so it needs the double-click; here a single click already accepts |
| Commit message box pane, conflict editor | comment editor overlay | no commit or merge in Jira |
| Main loop at 100 iterations per second, 50 when idle | Terminal.Gui default | not needed: the default is 25 per second and the AOT build idles at 0.2 to 0.3 % of a core (`performance.md`, "Idle cost (#619)"); an idle governor is #624 |

The Settings screen Gitunia has is in too (requested by the owner, #556; see "Settings screen" in [settings.md](settings.md)). The other gaps found by the audit are open issues linked from #560: single-line prompt caret (#567), cursor position in the status bar (#569), wheel in help and messages (#570), row menu marker (#572), commands button (#573), tab rename and labels (#574), command line (#576, #577), print-frame colours (#585), error and loading bodies (#579).

## Print frame

`geeratya --print-frame` (options: see `geeratya --help`) prints the plain-text frame the shell would draw for that size (default 80x24, no colour, works without a terminal) and exits (`geeratya --help` prints the full option list). It is the basis of the snapshot tests in `tests/Geeratya.Tui.Tests/Snapshots` at 120x36, 80x24 and 40x10; the frame builder is also tested at every size from 0x0 up so a resize never throws. The `All actions` help page is longer than 36 rows, so besides `help-120x36` (the Global page, no tab open) the snapshots `help-all-scroll0|20|40-120x36` (`--help-page 1 --help-scroll N`, with `--mode help`; N is the first visible line of the page) together cover every group, `help-commands-120x36` is the Commands page, and `help-page-list|columns|detail|backlog-WxH` (a test builds the state with a tab) are the first page of each layout; a test checks that the groups are all there. When the page grows past the last scroll snapshot, add a further one. `--command-level advanced` shows the help of the advanced level (snapshots `help-advanced-scroll0|20|60-120x36`, the All actions page; the default is everyday). To refresh a snapshot after an intended change, rerun the command into the matching file and review the diff.
