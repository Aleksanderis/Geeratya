# Decisions

Short dated log of live, non-obvious settled choices that cut across docs. Add an entry only when the choice is not already evident from `ux.md` and its parts (`ux-*.md`), `architecture.md` or the code, or when it overrides an earlier decision; a behaviour change documented in `ux.md` needs none. Agents follow these without asking. Open questions live in `roadmap.md`. Superseded, closed and purely historical entries are archived word for word in `history/decisions.md` (not required reading).

Format: dated heading, entries appended at the end, each starting with a bold topic tag (**Stack**, **Jira layer**, **UI**, **Testing**, **Process**, **Code structure**), one or two lines (decision and why), a blank line between entries. Long detail lives in `docs/history/`, the area docs or the issue or PR. When a decision changes, append a new entry that supersedes the old one, and archive the old entry once the new one states the outcome.

## 2026-11-02

**UI:** Create (#162): project and parent come from the issue shown or selected, not from a project setting, because a view has no project of its own (a JQL or filter spans many); a selected epic is offered as the parent and dropped when the chosen type has no `parent` field. The type picker is part of the create form (types first, then the fields of the chosen type) instead of a separate overlay, so cancel, loading and errors are the form's own. "Open after" is `Ctrl-g` in the form (off by default) instead of an extra field. Why: least new state and keys; the create metadata decides what is allowed.

**UI:** The assignee picker (`<space>ia`) is the field form with one person field, not a separate overlay; its search is the suggestion popup's (#214), there is no second search path. The edit form offers only fields whose current value the view holds (summary, labels, priority, an opened issue's description); a description that does not round-trip through the Markdown-like text is listed read-only with the browser link. Why: one overlay and one state machine for every edit; editmeta has no values, and writing a blind value over an unseen one loses data. The other editable fields (due date, components, versions, custom fields of the kinds the form edits) get their value from one issue read with only those field ids, made when the form loads, right after editmeta (#283); it is not stored in the detail or its cache, so the value is as fresh as the form. If that read fails the form keeps the fields it already knows.

**UI:** Comment writes (#167): adding and editing a comment wait for the reply (no optimistic text) with the editor staying open on an error; the three comment writes change no row, so the pipeline skips the row patch, the search read, the stale mark and the issue reload for them (`WriteRequest.ChangesRows`). Editing another author's comment is not refused up front (overrides "others are refused with the reason" in `ux-keymap.md`): project administrators may edit all comments, so the editor warns and Jira's 403 decides. A lost reply is verified by reading the comments (a direct read, not the search index), so "not applied" is a safe conclusion. `Ctrl-s` is the shared `form.submit` action (comment editor and field forms); `Alt-Enter` is bound to it too, as a fallback where a terminal swallows `Ctrl-s`. The comment editor is `AppState.Editor`, separate from the per-tab field form (`TabState.Form`, #158): it is modal and needs no metadata, and the two never open together.

**UI:** Write keys: one `<space>` group per noun (`i` issue, `m` comment, `s` sprint, `k` rank, `v` view options), never a prefix of an M1 leaf, plus `Alt-h/j/k/l` to move a card or row (status, rank), `v` Visual and `Alt-m` marks; no bare letters; only sprint moves and rank steps take a set, every other write is single-issue; a count never selects. Why: Gitunia redesigned its keymap late for the same reasons (one noun one prefix, command levels). Plan in `ux-keymap.md` (issue #152); each issue binds its rows.

**Jira layer:** Remote link URLs keep any scheme in `RemoteLinkMapper`; the scheme check lives in `BrowserUrlCheck` (Core), the single gate before anything reaches the system browser: https only (stricter than http/https), no control characters, no user info; remote links may point at any host. Why: one gate for every open path; the UI and ADF link callers must go through `OpenUrlRequested` (only the issue-key path is wired so far). Issue #118.

**Scope:** Scrum boards and sprints are in (milestone M4, ahead of polish), in both project kinds; Scrum reports and charts are not. Why: Scrum is common and the tool is not only for the owner's team. Dev site: `GCS` (company-managed, board 6) and `GTS` (team-managed, board 5) are sandbox projects like `GCM` and `GTM`.

**Jira layer:** Project configuration is dynamic: issue types, fields (including custom ones), required fields, allowed values, transitions, statuses and link types are read per connection and project from Jira metadata, never hard-coded from the dev projects; unsupported field types degrade to read-only with a browser link. Why: every site and project differs (custom fields, custom issue types, team-managed vs company-managed). Rule in `.claude/rules/jira-layer.md`.

**UI:** Suggestions: `@` opens people, `#` plus a project key opens issues (inside text editors, Neovim-style popup); picker fields (labels, components, assignee, selects) suggest by context as you type, fzf/zoxide `zi` style. Why: owner's choice; issues #213-#215.

**Process:** Milestones after M2 follow what Gitunia had to redo, not its order: the write pipeline and a UI-free `Geeratya.App` project come first in M2 (running operations in state, rollback, mutual exclusion), the keymap gets command levels and a completeness test (M6), themes get a contrast test each (M3), and version stamping, idle CPU and macOS come before release week (M7). Why: Gitunia's M5 keymap redesign, M7 effects-as-data refactor and M6 theme and console fixes were rework.

**UI:** The columns layout groups children under their parent card (any issue with a `parent`, so stories under an epic as well as sub-tasks) and names the parent in the top border of a child whose parent is in another column; no swimlanes needed. A parent and its children in one column share one outer frame with the children indented by two cells, at the card pitch of five rows, so the viewport maths is unchanged. Overrides the earlier note that grouping belongs to swimlanes (#192). Why: owner feedback on PR #143, issue #85.

## 2026-11-01

**Stack:** Same as Gitunia: C# on .NET 10 with Native AOT, Terminal.Gui v2, xUnit, JetBrains inspectcode. Why: the owner is a .NET developer, and the agent routines, style rules and tooling carry over.

**Process:** The agent routines (CLAUDE.md, reviewer agent, rules, the work-task, work-orchestrator, work-readiness, retrospective, testing, performance and screenshots skills) are ported from Gitunia and adapted to Jira. Ideas carry over freely; Gitunia code is rewritten, not copied.

**Jira layer:** Jira Cloud only, REST API v3 over `HttpClient`, Basic auth with email plus API token (Cloud has no Data Center style PATs). Why: the owner's target is Cloud.

**Testing:** Live Jira work happens only on the owner's free dev site, guarded by `GEERATYA_LIVE_HOSTS`; the company site is never used by agents or tests. Default tests are offline against recorded, scrubbed fixtures.

**Process:** CI never runs automatically; local build and tests are the gate, and CI is dispatched by hand (before closing a milestone). Why: CI minutes are scarce (carried over from Gitunia).

**Architecture:** One active Jira site at a time, from saved profiles; switching is cheap and built in, several sites open at once is not included. Why: the owner uses one site, and side-by-side sites cost the most.

**Scope:** Company-managed and team-managed projects are both supported; Jira Service Management is not included. Attachments and images show as links, never rendered. Why: the owner's company project kind is unknown and the owner does not use JSM.

**Architecture:** A view is a source (JQL, filter, board, backlog) plus a layout (list, columns). Why: the owner wants boards flexible; new board kinds are then a new source or layout.

**UI:** The keymap is `keymap.default.json` embedded in Core and read with source-generated System.Text.Json; `docs/keymap.md` is generated from it by `--print-keymap-doc` through `scripts/gen-keymap-doc.sh` (no separate generator tool). Why: one code path renders help and the reference, and a test compares the committed file.

**Stack:** Secret store: `secret-tool` on Linux (token on stdin), advapi32 Credential Manager on Windows, no store on macOS yet (`GEERATYA_TOKEN`). The store is tried first, the variable is the fallback. Why: no native library dependency, AOT-safe, and a keychain binding can come later.

**Code structure:** Terminal column width lives in Core `DisplayWidth`; its wide-character table (`WideRanges`, East Asian Width W/F plus Emoji_Presentation, Unicode 17.0.0) is generated by `scripts/gen-display-width.py` and committed as a constant span (no runtime download, no startup cost, no dependency). Rerun the script to adopt a new Unicode version.

**Jira layer:** One `JiraTransport` per `JiraConnection`; clients take only the transport and no call takes a connection argument (supersedes the earlier "every call takes a `JiraConnection`" wording in CLAUDE.md and the rules; the "no global site" intent stands). Why: the token and `HttpClient` live in one place, and a profile switch just replaces the transport. The transport requires https (http only for loopback) and never follows redirects, so credentials cannot leak to another host.

**Stack:** The `GEERATYA_TOKEN` fallback applies only when exactly one profile exists; with several profiles a profile needs a stored token, and the status line says so (refines the entry on the secret store; issue #60). Why: the variable carries no site, so a profile switch would send one site's token to another host.

**UI:** M1 view commands and the source picker always open a new tab; `Tab`/`Shift-Tab` switch tabs (the vim jump list does not exist here); a board shows a trailing `Unmapped` column rather than hiding a loaded issue whose status maps to no column (issue #65, `ux-screens.md`); Jira's board endpoint never returns such issues (verified, #138), so the column is a safety net for stale data. Why: no data silently hidden, tabs are cheap.

**Architecture:** The cache is a host-owned `SiteCache` (memory plus disk per profile), not part of `AppState`; the reducer asks for writes by effect and the load handler answers with cached rows first. Why: LRU order and byte counts are infrastructure, and this keeps the reducer pure and cheap. Detail: `architecture.md`, "Cache and refresh".

**Architecture:** Load results are applied only if their per-tab request id is current and the host drops results of an older `SiteConnections.Generation`; refresh is the active tab only (60 s, 30 s on switch, `AsBackground()`, backoff to 5 min, injected `Tick`). Why: pure reducer, no stale data after a tab close or profile switch. Detail: `architecture.md`, "Views and tabs", "Loading".

**Architecture:** Switching profile drops the views and memory cache but keeps that profile's disk cache folder; removing the profile deletes it. Why: views reopen instantly when the profile comes back. Ids (`TabId`, request ids) come from one counter in `AppState` that survives a switch, so an old reply never matches a new tab.

## 2026-11-02

**UI:** The issue detail lists comments oldest first and loads further pages at the end (`Load more comments`, `Enter`), instead of the newest 20 with older ones above (supersedes that sentence of `ux-screens.md`, "Issue detail"; issue #84). Why: the comments client pages oldest first with offsets, and a thread of at most 50 comments reads the same either way; reversing the order needs a second client mode for no reader benefit yet. `q` still quits in the detail (Normal mode, `ux.md` "Focus model and key style"; workflow 4 says the same), although the issue text said otherwise.

**Architecture:** Write pipeline (#151, `architecture.md`, "Write pipeline"): running operations live in `SiteSession.Operations` (site level, origin tab stamped) so exclusion sees every tab and a tab close does not forget a sent write; a busy issue refuses a second write; row-visible changes are optimistic with per-field rollback; writes are never retried and a lost reply is verified by re-reading. A single transition does not confirm (Jira exposes no workflow side effects; overrides the wording in CLAUDE.md and `ux.md`; fallback in roadmap question 6). Why: Gitunia's M7 retrofit of the same rules. (The "no confirm for a single transition" part is superseded by the #159 entry of 2026-11-02.)

**Architecture:** Writes run through `NetworkRunner.StartDetached` (no scope dictionary), not a scope keyed by the operation id as the first draft of the write pipeline said: operation ids never repeat, so keyed scopes would pile up, and a tab close must not cancel a write anyway. After a write the read-back rows are used only if they show the change (`WriteRequest.IsShownBy`), because the search index can lag and a stale row would undo the optimistic one. Issue #154.

**UI:** Change status (#159): a single transition confirms when its target status is in the `done` category, or its workflow shows a screen with no fields to fill; every other single transition sends at once, and a transition with fields is confirmed by submitting its form. Why: Jira does not expose post functions, so these are the only hints of side effects, and the issue asked for a confirm for "a screen or side effects"; this resolves roadmap open question 6 with its fallback instead of its default. A column move (`Alt-l`/`Alt-h`) reads the issue's transitions before it moves the card (an invisible picker form), because only then is the transition id and the "exactly one leads there" test known; the card moves after that read, not at the key press.

**UI:** `<space>kk` (rank.to) is pick up and drop, not an issue picker (#169, overrides the picker wording of #152): the first press remembers the issue (`TabState.RankPickup`), the second drops it at the card under the cursor, above it when the cursor is above the picked-up issue, else below. Why: the cursor already shows the target in the list and the columns, a picker would need a searchable issue list for a move that is visible on screen; the picker returns with the cross-section rank of #182 if needed. Rank keys carry no status bar hints, to keep the hint row and its snapshots stable until the write hints are designed together.

**UI:** The link form (`<space>il`, #190) picks the link type and the side in one choice (`blocks`, `is blocked by`, ...; the field id carries type id, side and wording) instead of a type picker followed by a direction toggle, and takes the other issue by key. Searching by text waits for the suggestion popup (#214). Removing a link (`<space>iu`) works from the issue detail cursor only, because that is where a link id is known; the row of a link whose other key is malformed is not selectable. Why: one pick states the sentence ("this issue blocks the other") and avoids a wrong-direction link, the most common mistake with Jira's two-sided types.

**UI:** Suggestion popup (#214) drives labels, user and parent fields of the form; selects and multiple choices use it too since #293 (their allowed values are the pool, ranked locally, no Jira call; this replaces the inline option list kept by #214), so every picker field suggests in one style. The debounce (250 ms) and the "searching" notice (150 ms) run in `SuggestionHandler` on an injected `TimeProvider`, not in the reducer, because the app tick is one second and the reducer reads no clock. Enter and Tab accept the highlighted row (first row by default, fzf style); `Space` adds a typed label verbatim. Why: smallest change that meets the owner's context-trigger decision without touching the choice-field flow other open PRs edit.

**Process:** Milestones reordered (owner decision 2026-11-02): themes come earlier, so the roadmap is renumbered and the former M3-M6 are now M4 (Scrum and sprints), M5 (More views), M6 (Keymap and discoverability) and M3 (Themes, mouse and terminals). Goals and content are unchanged.

**UI:** Comment drafts are not kept across a restart (#288): the discard question already says the text is "not saved anywhere", a draft file would need the cache's secret-free rules and a cleanup story, and a comment is short-lived. A reopened editor starts empty. Revisit when the description editor (#164) shows long texts are lost in practice.

**UI:** Inline suggestions in the comment editor (#215): `@` (after a space or at the start) opens people who can see the issue, `#` plus a project key (`#GCM`, `#GCM-12`) opens issues; the popup is the shared `SuggestionState` shown as rows inside the box above the notes (not floating at the cursor, because the box already lays out by rows and a floating popup would need clipping at the terminal edge). A mention is inserted as `@[Name](mention:accountId)` and an issue as a link mark `[KEY](site/browse/KEY)`, not an inline card: a link mark renders as plain text in every Jira surface and in this app's renderer, while a smart card depends on the viewer resolving the link. Both stay atoms in the editor (`AdfMarkdownTokens`): one cursor step, one Backspace or Delete. Not done: showing a token as `@Name` instead of its full text (needs a text-to-screen column mapping in `EditorLayout`).

**Stack:** macOS secret store (#29, #202; supersedes "no store on macOS yet" in the 2026-11-01 Stack entry): `security -i` with `add-generic-password` on standard input (the token never reaches the process table), `find-generic-password -w` to read, `delete-generic-password` to remove (exit 44 = not found). Why: no native binding, AOT-safe. Written without a Mac, accepted by the owner: `SetAsync` reads the value back because `security -i` may exit 0 after a failed command, and the quoting (`"` and `\\` escaped, control characters refused) is assumed from the `security` man page. The owner checks it on a Mac.

## 2026-11-03

**UI:** Realigned with Gitunia's proven interaction design (source: Gitunia `docs/internal/ux.md`, `ux-keymap.md`, `ux-settings.md`) where Geeratya had diverged without a reason; issues #368 to #373 carry the work. Not adopted, with the reason: a Settings screen (not in the README features; `:set` and the palette are the UI), per-view key rows and a `view` field in the user file (Geeratya keeps the same keys in every view, so contextual help uses an applies-to tag on the action instead), repeat mode and pane focus keys (no panes to resize, no steppers), a third command level (two are enough until the keymap grows), and one merged `config.json` (`keymap.json` is never written by the app and already ships, `settings.json` stays app-written, so they stay two files).

**UI:** The palette (#368) is Gitunia's fuzzy list of every action with its keys, opened by `:` or `Ctrl-p`; typed commands with arguments (`jql <query>`, `tab ...`, `profile ...`) stay as a command line when the first word is a command name followed by a space. Why: Gitunia's actions take no arguments (its prompts ask for them), a Jira view command is naturally typed with its query, and the list is what makes the keymap findable and gives every action a mouse path. `Ctrl-p` is an accepted exception to the vim rule, as in Gitunia.

**UI:** Status messages (#369) have a severity, a lifetime (5, 15, 30 s) and a history; a key press no longer clears one. Why: writes finish after the user has moved on, and a one-string notice cleared by the next key loses their errors. The history is `<space>n`, not Gitunia's `<space>m`, because `m` is the comment group; `<space>x` dismisses.

**UI:** The Confirm question becomes a centred dialog with clickable `y` and `n` (#370, M3 with the mouse paths); a dialog that does not fit is not shown and the action does not start. Why: a question cut off at the terminal width cannot say what changes or that Jira has no undo, and the status line version has no mouse path. Keys unchanged (`Enter` never confirms).

**UI:** The which-key popup waits 250 ms and groups by noun and cluster, and `hints.statusBar` gets `minimal` (#372); the help overlay opens on the active view's keys with a filter and a `Custom` page (#371); levels hide and never disable, `<space>*` toggles (#196). All as Gitunia learned after shipping the flat versions.

**Stack:** Settings go through one registry (reader, writer, `:set`, doc table) and a writer that replaces only the changed value so the user's comments survive (#373); `Ctrl-c` is read before the keymap so a user file cannot remove it (#303). Both as in Gitunia.

**UI:** Themes (#198; source: Gitunia's theme files, which shaped every point; supersedes the first attempt, PR #356): a theme is a JSON file with a required `variant` (dark or light), twelve required colours and an optional `ansi` object; the built-in themes are the same files embedded in the binary, a user file `themes/<name>.json` wins over a built-in of the same name, and an invalid file is not offered but reported. There is no generic hardcoded dark or light palette: `dark` and `light` are aliases for `catppuccin-mocha` and `catppuccin-latte`, the defaults. Modes stay 24-bit, 16 colours and none; at 16 colours the variant picks a built-in table (the terminal's palette decides the look) and `ansi` overrides single colours. Only built-in themes are held to the contrast rules (a test over every built-in at 24 bits and 16 colours); user themes are not checked, as in Gitunia. Two differences from Gitunia: the 16-colour dark accent is bright cyan, because xterm bright blue does not reach 4.5 on black, and the 16-colour contrast test uses a table with darker normal colours for the light variant, because the xterm normal colours fail on white. Core knows no themes: `:theme` is an effect answered by `ThemeApplied`, and only an applied theme is saved. The `auto` setting (terminal background detection) is not part of this.
